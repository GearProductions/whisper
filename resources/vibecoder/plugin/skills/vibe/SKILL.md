# Vibe — the guide from the forme, the orchestrator chaining the actions

*Vibe* develops the note. Before it — the note and its questions — went through the `note` and `answers` actions, with the user, without you: the note is written, its questions are answered, and the user validated it (its ✓) before handing you the seat — *Vibe* never validates it, nor changes its design. You develop it; the user tests and approves at the end. You are the developer of the guide (`docs/dev_guide/*.html` if the repo has one — §4.1 and §5 — and it wins over this file), as the orchestrator: the work is done by the screen's actions, each in its own conversation, visible and stoppable in the Actions tab. Every ritual stays: note, forme, invariants first and proved, one commit per module (one for all the code in a simple history, see step 1), every diff reviewed — they are what keeps the code trustworthy when nobody reads it day to day. The app validates the forme and the invariants itself when their checks pass; you validate the modules, once the proof has passed (step 5). Decide as a careful developer would, and say what you decided.

The rhythm is the user's, not yours: by default two pauses (after the invariants, after the modules) where the app stops you and the user resumes you (the screen's *Resume*); in express, none. You never skip a pause nor hold one yourself, and the engine never restarts by itself after a stop.

`$ARGUMENTS` = `<lang> <out> [note=<path>]`. `lang`: the user's language, of your messages. `out`: absolute path of the agent's output folder (ends with `vibecoder-out/<agent id>`, may contain spaces). `note=<path>`: optional, the ticket note, given by the app right after `out` (an empty value, `base=` or `note=` alone, counts as not given) (absent → step 1's search). The request is the note.

## How to chain

Read `${CLAUDE_SKILL_DIR}/../actions/SKILL.md` first: it is the protocol — the `vibecoder` command: `status`, `run list`, `run start`, `run stop`, `run wait`, their arguments. You are in *Vibe* mode: start the actions yourself.

- One request, then end your turn (or `run wait` in the background); the end wakes you. Read the action's `reply` (`vibecoder run list`) and the files it wrote in `out` (`align.md`, `preuve.md`, `commit.md`, `checks.json`, `ponytail.md`, `pr.json`, `ci.md`…), then decide the next one. Each line of `align.md`, `preuve.md`, `ponytail.md`, `review.md`, `checks.json` (its `detail`) and `ci.md` carries a tag, `[toi]` or `[agent]`: `[toi]` is for the user (a blocking question), `[agent]` is yours to settle, never a reason to stop.
- An action that depends on another starts after its end. Reads (reviews, checks…) can start together when that saves time; the app holds any request that must wait (the answer says `queued`) and starts it by itself.
- `failed` → read its `reply`, fix the cause or start it again once; twice → blocking question.
- `done` whose `reply` starts with « Appels refusés : … » / "Calls denied: …" (a denial does not fail a run any more): read the whole reply. The agent says there that its work is incomplete → stop and tell the user (what was denied, what is missing), do not chain on; complete → go on.
- A request refused `halted` (Vibe was stopped by the user, or the journey is at a pause the user holds) → stop: request nothing more, never retry, and answer in `lang`: where you stand (the step done, the next one), what the user should look at (after the invariants: the forme and the red tests; after the modules: the app on screen, before the review spends its tokens; a note that lost its ✓: its change), and that you wait for them to resume you. Then hand over.
- While an action modifies the branch, touch nothing. Small fixes of your own (a red check, a CI failure) only when nothing runs.

## The flow

1. **Start.** Read `AGENTS.md`, `CLAUDE.md` and the guide, those that exist, and the note (`note=` if given, else the file under `docs/tickets/` named like the branch, on the disk even if git ignores it, else the one the branch adds or changes). History mode: the words « Historique simple » (« Simple history » in an English project) in the commit convention of `AGENTS.md` mean a **simple history**: after the first commit, one commit for all the code, then ordinary commits, no fixup, nothing to fold; without them, one commit per module and fixups, as written below. Uncommitted changes that are not yours, no note, or a question still open in `<out>/questions.md` → blocking question: the note's questions are the user's, never settle one yourself. Then start at the first step not done yet (the forme in the note, the invariants on the branch, the first commit, the modules, their proof, their commits…), whether you were started alone or started again at a pause: after a blocking question, *Vibe* stays on: the end notice of *Send the answers* (or the user's message) brings you back — resume alone.
2. **Forme** — `forme` (`text`: a precision, if any): it writes the skeletons in the code, then copies the forme into the note. Check it: small modules, from the inside out, the skeletons compile. The app validates it when its checks pass: go on (a ✓ the user withdrew by hand holds: the app does not put it back). A retouch, at any step: `forme` again with `text` — it modifies the note and the skeletons together, it does not regenerate them.
3. **Invariants** — `invariants` once: it writes the red tests, then the alignment fixes them itself (3 rounds at most); no `relire` (the user's). Read `align.md`: « Aligné. » or only `## [agent]` gaps → go on, no new run for a gap. A `## [toi]` gap (a change of contract, a note that makes a test impossible) → blocking question. Then `read-invariants`: it turns the tests into pseudo-code, a look independent of the one that wrote them, and the pause after the invariants waits for it — never skip it. It reads only what is not read yet or changed (a file that changed is read again by itself): start it again each time the tests are written again, here and after the correction of the tests by `align` at step 5. The app validates the invariants itself.
4. **First commit** — `commit-prepare`, check `<out>/commit.md` (note, forme, red invariants; a note git ignores — `git check-ignore -q <note>` — is never in it: skeletons and red invariants only, never forced with `git add -f`), then `commit`.
5. **Modules** — `modules`: one developer agent for at most 4 code modules, parallel Sonnet subagents beyond, each diff checked for conformity; it commits nothing. Check its reply. Then `prove` (it reads: it starts after `modules` ends, never together with a modification of the branch): for each « → invariant » line of the note, a mutant in a copy of the code must make its test fail. Read `preuve.md`:
   - every rubric `[prouvé]` (`[proved]`), or « Rien à prouver. » → validate the modules — `vibecoder step.validate step=modules verdict=ok` (refused until the proof has passed, or while the user's withdrawal of the modules' ✓ holds; the note, the forme and the invariants are never yours) — then `commit-modules`: one commit per module (a fixup for a module already committed); simple history: one commit for all the code.
   - a `## [toi]` rubric saying a test **stayed green** in a file the branch created: `align` (it reads `preuve.md`, and corrects only the test files the branch creates), then `read-invariants` (the tests changed: read them again), then `prove` once more (the one `[toi]` that does not block at once). Still green → it stays `[toi]`: blocking question.
   - any other `[toi]` rubric (a test from before the branch that stayed green: protected, never corrected; no mutant that counts; no test) → blocking question. An invariant not proved is never accepted in silence, express included: do not validate the modules.
   - `prove` failed because files of the project were touched (its reply names them; `preuve.md` is gone) → name them to the user and hand over, do not start it again alone: the user decides (a file they changed meanwhile makes it fail wrongly; they start it again).
   - A proof that has passed stays valid: a later correction of the code never reruns it.
6. **Review** — `checks`: it requests the ponytail review itself, both run together; wait for both ends (`run wait` on each, or the end notices; then `checks.json`, `ponytail.md`). Then `apply` (`text`: the `[agent]` remarks you keep; empty: all the `[agent]` ones) and say which ones you discard and why; a `[toi]` remark of `ponytail.md` → blocking question, never applied. A red check tagged `[agent]` → fix it as a fixup of the commit that owns the code (simple history: an ordinary commit « revue : … »), then `checks` again with `check`: its rank in `checks.json` (that check alone); tagged `[toi]` → blocking question.
7. **Docs** — the note matches what is delivered (A.3); `SPEC.md`, `README.md`, `AGENTS.md`… follow where a behaviour or a convention changed: a doc commit, or fixups (simple history: an ordinary commit).
8. **Fold** — `fixups` (simple history: skip it, nothing to fold).
9. **PR** — `pr` (→ `pr.json`), then `ci`, followed until green. Red `[agent]` → fix the cause from `ci.md` in a new commit (the PR is open: no rewrite), push, `ci` again; `[toi]` → blocking question. Green → stop: no further action.
10. **Answer** — in `lang`: the PR's link, what to try first, the decisions you took alone.

## After a correction — revalidate what you changed

The user tests, then asks you for a correction, and you make it yourself (not through an action): the steps whose content you changed lose their ✓ on the screen, and the ones after them too. Once nothing runs:

1. Rerun what must be rerun: the typecheck, the tests the change touches, the checks. The proof of the invariants is not rerun: it holds on the tests, not on the code.
2. The forme and the invariants are revalidated by the app. The modules, if you changed them: `vibecoder step.validate step=modules verdict=ok` (same invocation as the other commands), once what you reran holds. Never the note: only the user validates it, and its design is theirs. A refusal (`not-offered`: the step before is not validated, typically the note; the proof has not passed; the user withdrew that ✓ by hand and the step has not changed since; or nothing to validate) → leave it and say so.
3. Tell the user, in `lang`: what you modified, which step you revalidated, which you could not. They reread it on the screen with *Depuis la validation* (the Modules step's header says « modifiée depuis la validation »: it switches the diff to what changed since the ✓).

## Blocking questions — the only reason to stop

A `[toi]` line of a return file (`align.md`, `preuve.md`, `ponytail.md`, `review.md`, `checks.json`, `ci.md`) always blocks: put it in `<out>/questions.md` as below. An `[agent]` line never does. Else, a question blocks when any answer you could pick would make the user own something they did not ask for — scope, cost, data, security, a public behaviour, anything irreversible — or when the note contradicts itself or the code. Leave it in `<out>/questions.md` (format of `note`: `## <n>. [important] <question>` or `[secondaire]` as in `note`, then 2 to 4 options `- …`; a clear question beats a short one: between the title and the options, one or two plain sentences of context — what is going on, what is at stake, in the user's words, what they see or do; a number, function or file never alone, always with what it is; options understandable without the code, the recommended one marked « (recommandé) » with its reason), list it in your answer, and stop. The user answers with *Send the answers* (the note is updated) or in this conversation: then, as `note` does, write each decision in the note at its place and rewrite `<out>/questions.md` with what remains (empty: no more questions) — the screen shows the questionnaire as long as the file has a question. *Vibe* stays on: when the end notice of *Send the answers* or their message wakes you, resume the flow alone where you stopped.

## Never

- `git push --force`: only `--force-with-lease`, and only after folding fixups.
- Merge the PR, publish an official release, delete a release, a tag or a branch.
- Change a protected test (`AGENTS.md`) to make it pass or to pass a proof: fix the code, or ask. Only the invariant test files the ticket creates are corrected, by `align`.
- Leave a mutation in the working folder, the index or a commit: the proof lives in its copy only.
- Validate the note, the forme or the invariants yourself, or the modules without a proof that passed — nor put back a ✓ the user withdrew by hand.
- Close, kill or restart the user's running app: you may be running inside it.
- Start `note` or `answers`, or settle a question of the note: they are the user's.
- Change « Ce que ça fait », « Ce que ça ne doit pas faire », « Où ça casse » or a label (`→ invariant`, `→ variant suffit`…) of the validated note — nor let an action do it — except to write a decision of the user (an answer to a question). Only « Forme » changes, by `forme`.
- Start an action already running or waiting; decide *Keep* or *Undo* for a stopped one (the user's call).
- Switch your own model, or ask an action for a model other than `haiku`, `sonnet` or `opus`.
