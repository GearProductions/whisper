# 0.16.0 — La ligne d'état après la PR

Branche `fix/0.16.0-ligne-apres-pr`. Côté créateur.

## Ce que ça fait

- Symptôme (gt-plugins, PR #791 déjà ouverte, corrections après test, 2026-11-26) : la ligne d'état dit « La PR est ouverte, la CI tourne » avec *Reprendre*, alors que l'utilisateur doit valider sa note modifiée pour que le système applique le changement (forme, invariants, modules) ; et en fin de PR, *Reprendre* reste affiché quand il n'y a plus rien à faire. (« Il manque un petit reset d'état sur le message affiché et sur ce qu'on peut faire. »)
- **La CI lue par l'appli.** Cause : la ligne lit l'état de la CI dans `ci.md`, écrit la veille pendant que la CI tournait (« ⏳ 0/2 checks ») et jamais relu : la ligne dit « la CI tourne » pour toujours et, la CI jamais verte à ses yeux, le parcours n'est jamais fini (pas de *Reprendre* à côté d'un parcours fini, PR #105 : ne se déclenche jamais). Attendu : l'appli lit elle-même, en fond, l'état des checks du commit de tête de la PR sur GitHub, dans la lecture qui trouve déjà la PR de la branche (`prForBranch` : un champ de plus à son `gh pr view`, aucune lecture nouvelle) ; la lecture de l'état d'une PR suivie (`prState`) ne change pas ; la ligne et la carte de la PR le disent (la même chose). `ci.md` ne sert plus qu'au diagnostic d'un échec (cause, correctif), lu par le moteur ; l'action *Lire la CI* ne change pas. gh sans réponse : l'état de la CI est inconnu, la ligne ne la dit pas verte et le parcours n'est pas fini.
- Aucun check sur le commit de tête (juste après un push, ou un dépôt sans CI) : la CI compte comme en cours, jamais verte, et le parcours n'est pas fini. À mesurer avant de coder : ce que rend `gh pr view` pour les checks dans les secondes qui suivent un push.
- **La note modifiée d'abord.** Cause : une note dont la conception a changé depuis son ✓ compte encore comme faite une fois un module commencé (`stillOk` accepte « changée ») : pas de pause « note », et la ligne saute « la note a changé » pour tomber sur celle de la PR. Attendu : une note modifiée depuis sa validation passe en tête de la ligne, avant la PR — « La note a changé : vérifiez-la, puis validez-la » —, sans *Reprendre*. La pause « note » revient, comme avant les modules : le moteur s'arrête et ses demandes sont refusées jusqu'à la validation de l'utilisateur ; la Forme, les Invariants et les Modules faits le restent (rien ne se construit sur une note pas revue, et le parcours ne recule pas). Une fois revalidée, tant que le changement de la note n'est pas commité (le signe que lit déjà le moteur à sa reprise), la ligne propose de reprendre pour que le système l'applique.
- **Un module complet dès la Forme (T-47).** Cause : un module fait uniquement de types, complet dès le squelette du premier commit, n'est jamais touché par un commit ensuite ; le parcours le croit « pas commencé », l'étape Modules reste « en cours » et l'appli propose encore *Générer les modules* alors que tout est écrit, prouvé et commité (PR #106, module `src/shared/bridge/types.ts`). Attendu : un module dont le squelette est déjà le contrat complet compte comme commencé dès que chacun des autres l'est (l'appli propose alors la bonne action suivante), et comme fait une fois le code des autres commité. L'appli le reconnaît par ce qu'elle voit, sans règle nouvelle dans la Forme : ses fichiers sont restés tels que la Forme les a laissés, ils sont dans le premier commit, et chaque autre module a son commit (un module oublié par la génération se verrait aux vérifications et à la preuve). La règle ne vaut que s'il y a au moins un autre module dans la Forme : un module seul est toujours généré.
- Les trois ensemble : la PR verte pour son dernier commit, chaque étape faite → la ligne seule, sans *Reprendre*.
- SPEC (la ligne d'état, sous le fil) et README (la ligne d'état) suivent.

## Ce que ça ne doit pas faire

- Changer le relecteur : sa ligne, ses arrêts, son bouton *Préparer la revue* → variant suffit
- Changer le moteur et ses deux rythmes : les pauses après les invariants et après les modules, le moteur qui ne repart jamais seul (sauf à la première validation de la note, ou arrêté par le changement de la note) → variant suffit
- Changer les validations : la note n'est validée que par l'utilisateur, jamais par le système ni le moteur ; les ✓ des autres étapes comme aujourd'hui → variant suffit
- Faire reculer le parcours une fois un module commencé : la Forme, les Invariants, les Modules faits le restent quand seule la note a changé (note 0.15.0-stabilisation) → variant suffit
- Dire la CI verte (ou finir le parcours) d'après `ci.md`, ou sans réponse de gh → variant suffit
- Changer la lecture de l'état d'une PR suivie (`prState`, ses arguments figés par un test protégé) → invariant (déjà tenu par un test protégé)
- Compter comme fait un module dont un fichier a changé depuis son squelette sans être commité → variant suffit

## Forme

**La CI d'après gh, jamais d'après un fichier.** `prForBranch` demande un
champ de plus (`statusCheckRollup`) et rend l'état des checks du commit de
tête, réduit par une fonction pure (`ciOf`) ; le contrôleur ne change pas (la
PR trouvée passe telle quelle au parcours, même cache, mêmes 60 s). Le
parcours pose `pr.ci` d'après gh seul : une fiche (`pr.json`, `pr-<n>.json`)
ou `ci.md` ne le donnent jamais ; gh sans réponse : absent, donc inconnu.
`parseCi` n'a plus de lecteur et part.

**La note d'abord.** Le ✓ de la note ne vaut plus que pour sa conception
d'aujourd'hui, modules commencés compris ; les cas d'invariants gardent la
règle d'avant. La vue dit si la note est commitée (`note.git`, comme les
fichiers des modules) : la ligne propose de reprendre tant que le changement
revalidé n'est pas commité.

**Un module complet dès la Forme.** Reconnu par le parcours d'après ce qu'il
voit (fichiers restés squelette, tous dans le premier commit, un autre module
au moins) ; aucun champ nouveau dans la vue : `started` le dit, ses commits
restent vides.
