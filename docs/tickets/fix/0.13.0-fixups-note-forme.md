# 0.13.0 — Un fixup pour la note et la Forme modifiées après leur commit

## Ce qui ne va pas

- La note (et sa Forme, dans le même fichier) est commitée au premier commit
  de la branche. Si on la modifie ensuite (à la main, ou l'agent pendant la
  génération des modules), aucun bouton n'en fait de fixup :
  - *Commiter* et *Commiter les modules* ne la voient pas : ce n'est pas un
    module ;
  - *Préparer le commit* la repère mais la laisse de côté et répond
    « fixup », sans rien préparer (s'il n'y a qu'elle, aucun message) ;
  - l'étape Invariants n'est plus faite (la note pas commitée) et met
    *Préparer le commit* en avant : une impasse.
- Seul recours : taper `/gear-fix-up` dans la conversation.
- La SPEC promettait déjà un fixup à *Préparer le commit* : la doc et le
  comportement ne disaient pas la même chose.

## Ce que ça fait

- *Préparer le commit* prépare lui-même le fixup, comme un autre commit :
  avant la PR, un fichier déjà porté par un commit de la branche (la note,
  la Forme, un test d'invariant, un module) fait un fixup de ce commit,
  avant tout module ; message `fixup! <son sujet>` seul, dans la carte du
  commit proposé ; *✓ Commiter* le fait. La PR ouverte : un nouveau commit
  qui dit pourquoi, comme avant.
  - Pas un fixup : le fichier d'un module que seul le premier commit porte
    (un squelette) : il part avec le commit de son module.
- L'étape Forme dit le changement : la note commitée puis modifiée, elle
  n'est plus faite, ses faits disent « note modifiée depuis son commit » ;
  note et forme revalidées, *Préparer le commit* est sa prochaine action,
  puis *✓ Commiter*.
- La carte du commit proposé s'affiche aussi à l'étape Forme.
- *Replier les fixups*, à la Revue, les fond dans leur commit (inchangé).

## Ce que ça ne doit pas faire

- Jamais de fixup ni d'amend une fois la PR ouverte : son historique n'est
  pas réécrit. → vu en review (règle du skill, inchangée)
- Une note jamais commitée qui change ne déclenche rien : elle part avec le
  premier commit. → variant suffit
- Le fixup ne prend que les fichiers du commit visé ; le reste attend le
  commit suivant. → vu en review

## Ce que ça touche

- `resources/vibecoder/plugin/skills/commit-preparer/SKILL.md`,
  `actions.fr.json`, `actions.en.json` (l'aide de *Préparer le commit*).
- `src/main/core/vibecoder/journey.ts` : `noteChanged`, l'étape Forme.
- `src/renderer/app/panel/vibecoder/proposed-commit.tsx` (nouveau, sorti de
  `modules-view.tsx`), `forme-view.tsx`.
- `SPEC.md`, `README.md`.

## Forme

- `resources/vibecoder` — `commit-preparer` prépare le fixup (`fixup!
  <sujet>`) au lieu de le laisser de côté · utilisé par : l'action
  `commit-prepare`
- `src/main/core/vibecoder/journey.ts` — `noteChanged` : la note dans un
  commit de la branche et dans `dirty` ; la Forme pas faite, sa prochaine
  action `commit-prepare` puis `commit` · ne connaît pas : Electron, git ·
  utilisé par : app/controllers (vibecoder)
- `src/renderer/app/panel/vibecoder/proposed-commit.tsx` — `ProposedCommit`,
  `PROPOSED_ACTS` : la carte du commit proposé · ne connaît pas : le pont ·
  utilisé par : modules-view, forme-view
- `src/renderer/app/panel/vibecoder/forme-view.tsx` — la carte du commit
  proposé sous l'en-tête · utilisé par : step-views

## Invariants

Aucun nouveau : la règle « pas de réécriture une fois la PR ouverte » est
celle du skill, inchangée ; le reste est couvert par les variants
(`journey`, `forme-view`).
