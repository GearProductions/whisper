# 0.11.0 — CI : des tests lents sous Windows ne bloquent plus une release

## Ce que ça fait

Correctif vu sur la release candidate `v0.11.0-rc.1`, indépendant de la
PR #40 (à partir de `master`).

- En CI (`CI` posé), chaque test a 30 s, chaque préparation 60 s, et un
  test qui échoue est relancé deux fois avant de casser la CI. En local,
  rien ne change (5 s, 10 s, pas de relance).
- Aujourd'hui (run 39800903877, tag `v0.11.0-rc.1`) : le runner Windows deux
  fois plus lent que sur la PR (115 s contre 61 s pour
  `module-code.test.ts`). Premier essai : une préparation au-delà de 10 s
  (`module-code.test.ts`, invariant) et un test au-delà de 5 s
  (`vibecoder.test.ts`). Relance : un autre test, `runs.test.ts` (variant),
  dont le `settle()` de 300 ms n'a pas suffi. Un test différent à chaque
  fois, le même commit vert sur Linux et sur la PR ; `syntaxe` rouge, pas de
  `paquet`, pas de release. Vert à la deuxième relance.
- La cause : beaucoup de tests attendent un processus, un dépôt git ou un
  délai fixe (`settle`), plusieurs dans des invariants protégés. Les
  allonger un par un ne règle pas le suivant.

## Ce que ça ne doit pas faire

- Changer un test, protégé ou non : seule `vitest.config.mts` change. → vu
  en review
- Cacher un échec qui se répète : un test rouge trois fois de suite casse
  toujours la CI. → vu en review

## Où ça casse

- Une CI rouge peut prendre jusqu'à trois fois plus longtemps.

## Ce que ça touche

- `vitest.config.mts`.

## Pistes pour plus tard

- Remplacer les `settle()` à délai fixe par une attente d'une condition
  (comme `until` dans `family-commands.test.ts`) ; plusieurs sont dans des
  invariants protégés, à décider à plusieurs.
