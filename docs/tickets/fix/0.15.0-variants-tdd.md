# 0.15.0 — Les variants visibles dans la Forme et les Modules, écrits d'abord (TDD)

Constat : on ne voit jamais où vont les variants avant la PR. La Forme ne les nomme pas, l'écran ne les montre pas (le relevé les calcule, `VibeView.variants`, mais aucune vue ne les affiche), et sur une PR précédente ils étaient mal placés, découverts une fois sur GitHub. Et ils ne sont pas écrits en TDD : seuls les invariants sont écrits d'abord (rouges) ; l'agent développeur écrit les variants « à côté » du module, sans ordre, et le guide dit qu'ils sont « générés à partir du code » (§ 3.4).

## Ce que ça fait

- **La Forme nomme les variants de chaque module** (skill `forme`) : sous le contrat d'un module, une ligne `variants :` avec le chemin de son fichier de tests ordinaires (existant, ou `(à créer)`), là où le projet les range, puis les cas à couvrir, un par ligne. Un module sans variant le dit (`variants : aucun`, et pourquoi : de la doc, une donnée vérifiée ailleurs). On les challenge avec le contrat, avant le code.
- **Les variants sont écrits d'abord** (agent `developpeur`, skill `module`) : il écrit les cas de la Forme dans le fichier qu'elle nomme, les lance et les voit échouer pour la bonne raison (le code manque, pas une faute de frappe), puis écrit le code jusqu'à ce qu'ils passent, ainsi que les invariants du module. Un cas en plus, trouvé en écrivant, s'ajoute et se dit. Son compte rendu le dit : rouges avant, verts après.
- **La relecture le vérifie** (skill `modules`) : à la revue de chaque diff, les variants sont dans le fichier que nomme la Forme et couvrent ses cas, et le sous-agent a dit les avoir vus rouges ; sinon, la correction lui est renvoyée comme un autre défaut.
- **L'étape Modules montre les variants** (vue IDE) : les fichiers de tests ordinaires que change la branche (`VibeView.variants`) s'ajoutent à l'arborescence des fichiers des modules, rangés par dossier là où ils sont, avec leur couleur git ; on les ouvre comme un fichier de la branche. On voit ainsi où ils sont écrits, pendant et après la génération.
- **Le guide** (§ 3.4) : les variants s'écrivent d'abord, à partir des cas de la Forme, puis le code ; ils restent des tests ordinaires, régénérés avec leur module.

## Ce que ça ne doit pas faire

- Changer la lecture des modules de la Forme par l'écran : une ligne `variants :` est une ligne du contrat, pas un module → variant suffit
- Toucher au pont (`src/preload/`, `src/shared/bridge/channels.ts`) → structure
- Montrer deux fois un fichier, ou un test d'invariant parmi les variants → variant suffit
- Rendre les variants protégés : ce sont des tests ordinaires, qu'on corrige avec leur module → structure

## Ce que ça touche

- `resources/vibecoder/plugin/skills/forme/SKILL.md`, `module/SKILL.md`, `modules/SKILL.md`, `resources/vibecoder/plugin/agents/developpeur.md`.
- `src/renderer/core/vibecoder/ide-files.ts` (`ideFiles`) et son test ; `src/renderer/app/panel/vibecoder/modules-view.tsx` (son en-tête).
- `docs/dev_guide/guide-travail-dev-ia.html` (§ 3.4).
- `SPEC.md` (l'étape Modules, sa vue IDE ; les skills) et le README.
