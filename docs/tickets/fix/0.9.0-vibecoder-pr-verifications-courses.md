# 0.9.0 — VibeCoder : la PR fusionnée, des vérifications qui vérifient, des courses finies à la fin

## Ce que ça fait

Trois correctifs vus en déroulant le ticket du parcours guidé (PR #31,
release candidate `v0.9.0-rc.3`).

- **PR fusionnée : le bouton revient.** Étape PR, une fois la PR fusionnée,
  *PR mergée → revenir sur la base* (et *Release officielle*) s'affiche, sans
  avoir à le demander à l'agent. Aujourd'hui il reste masqué : l'état
  `MERGED` n'est pas vu, la PR compte comme ouverte. Cause à trouver (un état
  inconnu compte comme `OPEN` ; l'état vient de gh, en cache 60 s, sinon de
  `pr.json`, qui n'a pas d'état).
- **L'orchestrateur revient sur la base comme au clic.** Demandée par
  `<sorties>/actions/base.start`, *base* revient sur la base (sinon
  l'orchestrateur n'a aucun moyen de le faire). Aujourd'hui elle part en
  course d'agent (`startAction` → `startRun`), et cette course a répondu « je
  ne vois pas de tâche » sans rien faire : la cause se cherche et se corrige
  (le *via* l'agent doit marcher en course comme au clic). Si elle ne se
  trouve pas : une demande `.start` d'une action directe (F-114) passe par
  l'action directe.
- **Les vérifications lancent vraiment les commandes du projet**, là où il
  faut. L'appli passe au skill `verifier` le préfixe des commandes du projet
  dans son message (une variable de gabarit, à créer ; vide si l'agent tourne
  déjà dans la box, `agentCommand` : `distrobox enter dev -- mise exec --
  claude`) : l'appli connaît déjà ce préfixe (F-111, F-112), le deviner dans
  le skill serait fragile. Le skill garde la découverte des commandes du
  projet (l'appli ne les connaît pas) et reçoit le droit de les lancer.
  Aujourd'hui il a voulu lancer `distrobox enter dev -- npm …`, refusé en
  session non interactive : `checks.json` en échec sans rien avoir lancé.
- **Un ancien résultat ne compte pas.** Un `checks.json` dont le `time` est
  antérieur au départ de la course de vérifications est ignoré par l'appli
  (la garantie est dans le code, pas dans la bonne volonté du skill).
  Aujourd'hui, relancé, le skill a relu l'ancien `checks.json` et l'a annoncé
  vert sans rien exécuter.
- **Une course n'est finie que quand son travail l'est.** Elle reste « en
  cours » tant que le runtime lui voit des tâches de fond (`runningTasks`) :
  un seul endroit, valable pour tous les skills, présents et futurs ; les
  skills n'ont rien à changer. Aucune limite de temps : on l'arrête à la main
  (*Arrêter* ; une CI de paquets prend 10 à 15 min et varie, une limite
  couperait une course saine). Aujourd'hui *Générer les modules* a fini son
  tour (« Wave 1 is running ») pendant que ses sous-agents écrivaient et
  commitaient encore ; *Release candidate* a fini (« waiting for the CI »)
  avant la fin de la CI, sans installer la version ; l'onglet *Actions* et
  l'orchestrateur (`actions.json`) les voyaient « done » alors que la branche
  bougeait encore.

## Ce que ça ne doit pas faire

- Masquer *PR mergée → revenir sur la base* une fois la PR fusionnée, ou
  l'afficher tant qu'elle est ouverte. → variant suffit (le test rouge du bug
  d'abord, §4.2)
- Laisser sans effet *base* demandée par l'orchestrateur (`.start`). →
  variant suffit
- Compter un `checks.json` dont le `time` précède le départ de la course de
  vérifications (vert affiché sans rien avoir lancé). → invariant
- Rendre un résultat de vérification que le skill n'a pas produit : une
  commande pas lancée annoncée. → vu en review (comportement d'un modèle,
  §3.1 ; l'appli garde l'ancien `checks.json` à l'écart, ligne du dessus)
- Demander une autorisation qu'une course non interactive ne peut pas
  obtenir, ou repasser par la box depuis la box. → vu en review
- Dire une course finie (`done` dans *Actions* et `actions.json`) tant que
  le runtime lui voit des tâches de fond. → variant suffit
- Couper d'office une course qui attend (sa CI) au bout d'un délai. →
  variant suffit

## Forme

**La PR fusionnée : la cause.** Pas l'état de la PR : depuis l'environnement
de l'appli installée (l'AppImage sur l'hôte, préfixe `distrobox enter dev
--`), `gh pr view --json number,title,url,state,baseRefName,headRefName --
feat/0.9.0-parcours-guide` répond `"state":"MERGED"` (vérifié le 2026-10-20),
et `journey` masque déjà `base` et `release` d'après cet état (testé : PR
fusionnée → `['base', 'release']`). L'agent est en mode **Vibe** (`autonomy:
"vibe"`) : à la place du parcours et de l'étape, l'écran Vibe (`vibe-screen`)
ne montre que *Rédiger la note* et *Valider et développer* ; l'étape PR et ses
actions n'y sont jamais. Corrigé dans les pages : l'écran Vibe montre aussi
`base` et `release`, telles que le relevé les donne (masquées tant que la PR
n'est pas fusionnée).

**La course *base* : la cause.** Le message est bien parti et le skill bien
chargé : son sous-contexte (`context: fork`, Haiku, effort bas) a reçu le
texte de `base/SKILL.md` et a répondu « je ne vois pas de tâche » (transcription
du sous-agent, 2026-10-20 13:22). Le skill se lit comme une description, pas
comme un ordre : corrigé dans le skill ; la demande `.start` reste une course,
comme au clic.

**Le préfixe.** Celui des commandes *vu de l'agent* : celui du projet
(`commandPrefix`) sans la box où l'agent tourne déjà (`boxPrefix` de
`agentCommand`) ; vide ici. Une variable de gabarit `{{prefix}}`, en fin de
message (`<lang> <out> [préfixe…]` : `out` finit par `vibecoder-out/<id>`).
