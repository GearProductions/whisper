# 0.15.0 — Les tests de contrat élargis à toutes les commandes

Des tests, pas de comportement nouveau, hors de la fin d'une course qui a
essuyé un refus (« Un refus ne fait plus échouer une course »), de la
vérification de la note (le skill `conception`), de la pastille « ? » du robot,
des écarts entre la table et l'appli trouvés par le banc et de la consigne
d'outils commune à toutes les courses. À livrer avant la release candidate
0.15.0, qui figera l'état de l'appli.

## Ce que ça fait

`npm run test:contract` (`tests/contract/run.mjs`, avec
`tests/contract/fake-claude.mjs`) lance l'appli réelle, profil neuf et faux
`claude`, et l'interroge de l'extérieur par la CLI `vibecoder`, comme un agent.
Ce sont les seuls tests qui pourront juger le futur moteur Rust (étape 7 du
plan de pilotage par agents) : ils ne regardent que la commande et la réponse,
quel que soit le langage derrière. Une commande sans test de contrat ne pourra
pas être portée en confiance.

- Chaque commande de la table (`resources/vibecoder/commands.json`, 55
  commandes) a au moins un cas qui réussit et ses refus principaux, chacun avec
  le bon code d'erreur de la table (`busy`, `changing`, `disabled`,
  `invalid-args`, `no-run`, `not-offered`, `closed`…).
- Six commandes n'ont que leurs refus, faute de pouvoir réussir sans l'écran
  (décidé le 12 novembre) : `copy-artifact` (le dossier choisi dans une
  fenêtre), `vibe` (la note ne se valide qu'à l'écran), `request-review` (la
  liste des PR ouvertes n'est remplie que par la page), `new-worktree`,
  `pr-worktree` et `remove-worktree` (la question « faire confiance à ce
  dossier ? », une fenêtre du système). Elles comptent couvertes et le résumé
  les nomme. Pas de porte dérobée dans l'appli pour les faire réussir au banc.
- Sur la vraie appli et un vrai dépôt git d'essai, avec un `origin` local pour
  `pull`, `push`, `fetch` et `rebase`. Pas de GitHub réel : un faux `gh`, en
  tête du `PATH` de l'appli, répond une PR d'essai ; les commandes qui passent
  par `gh` (et `base`, qui attend une PR fusionnée) ont leurs cas qui
  réussissent, et GitHub ne peut jamais être joint, ni par une commande ni par
  le relevé de l'appli.
- Tous les cas passent par la porte d'un agent extérieur (le jeton lu dans
  `live.json`) ; la porte du robot (son environnement) n'est vérifiée que sur
  ce qu'elle seule change (un seul jeu de cas, plus court).
- Les familles :
  - les lectures : `status`, `next`, `actions`, `runs`, `run.wait`, `procs`,
    `logs`, `artifacts`, `artifact`, `draft` ;
  - les courses : `run.start`, `run.stop`, `run.keep`, `run.undo` ;
    `run.allow`, `run.always`, `run.deny` fermées aux agents (`closed`) ;
  - les processus : `proc.start`, `proc.stop`, `proc.restart` ;
  - les actions directes git : `pull`, `push`, `fetch`, `switch-branch`,
    `rebase`, `stash`, `commit`, `base`, `new-here`, `new-worktree`,
    `remove-worktree`, `unload-pr` ;
  - celles qui passent par `gh` : `load-pr`, `pr-here`, `pr-worktree`,
    `request-review`, `assign-pr`, `unassign-pr`, `publish` ;
  - les artefacts : `add-artifact`, `rename-artifact`, `new-artifact-file`,
    `new-artifact-folder`, `move-artifacts`, `copy-artifacts`,
    `duplicate-artifacts`, `trash-artifacts`, `copy-artifact` ; la corbeille
    du système est celle du profil du banc (l'appli reçoit aussi un
    `XDG_DATA_HOME` temporaire) ; `copy-artifact`, qui demande le dossier dans
    une fenêtre, n'a que ses refus (un id inconnu, une autre action en cours)
    et compte couverte (pas de changement de l'appli) ;
  - la revue : `draft.add`, `draft.edit`, `draft.remove` (et `publish`) ;
  - la conversation : `vibe`, `guide`, `new-request`, `propose-run`.
- Les droits des courses (PR #88, note `0.15.0-courses-droits`) vus de
  l'extérieur : le faux `claude` simule un refus d'outil, et `run.wait` répond
  que la course a fini *terminée*, le refus cité en tête de sa réponse (voir
  « Un refus ne fait plus échouer une course » ci-dessous). Rien d'autre (le mode donné à Claude Code au
  départ d'une course ne se voit pas par la CLI).
- Les codes que seul l'utilisateur provoque à l'écran (`halted`, après l'arrêt
  de *Vibe*) sont laissés de côté, et le résumé les liste comme codes non
  couverts (le banc reste un banc de la CLI, que le moteur Rust pourra rejouer
  sans la page).
- Les 17 vérifications d'aujourd'hui restent : l'accès (réglage *agents
  extérieurs* désactivé, jeton, dossier sans robot, `run.allow` fermé), `status`,
  `next`, `commands` et `schema` (de la CLI, hors de la table), `run start`,
  `list`, `wait`, la seconde course en attente, `proc list`, `restart`, `logs`,
  et le robot qui joint l'appli par son environnement.
- Le script reste lancé à la main, hors de `npm test` (comme
  `test:main-diff`), rapide et lisible : une liste de cas par commande, un
  résumé à la fin (combien de commandes couvertes sur combien). Une commande de
  la table sans aucun cas de contrat fait échouer le banc, et le résumé la
  nomme (une commande ajoutée à la table sans cas ne passe pas inaperçue avant
  le portage en Rust).

**Un refus ne fait plus échouer une course** (décidé le 12 novembre, au premier
essai des droits de la PR #88 : *Rédiger la note* a fini *en échec* parce que
son agent avait lu le guide par `sed … | grep …` au lieu de `Read`, alors que la
note était complète ; en *Vibe*, l'orchestrateur se serait arrêté). L'appel
reste refusé — la sécurité ne change pas —, seul l'état change : une course qui
s'est vu refuser un outil (le sien ou celui d'un sous-agent, à n'importe quel
tour) finit comme son travail, *terminée* s'il l'est ; la ligne en tête de sa
réponse cite toujours chaque appel refusé, en une seule liste (« Appels
refusés : … », lectures comprises, sans « le travail est incomplet ») : le tri
entre une lecture et un autre refus, qui ne servait qu'à décider de l'échec,
est retiré. C'est
l'orchestrateur, ou l'utilisateur, qui juge en lisant la réponse si le travail
est complet ; l'agent dit lui-même ce qu'il n'a pas pu faire. Remplace, dans la
note `0.15.0-courses-droits` et la SPEC (F-115, « Ses droits »), la règle « un
refus d'écriture ou d'une commande `Bash` fait finir la course *en échec* ».
Le skill `vibe` lit la réponse d'une course terminée qui cite des refus : si
l'agent y dit son travail incomplet, il s'arrête et le dit à l'utilisateur au
lieu d'enchaîner.

**La pastille « ? » du robot : des questions t'attendent** (décidé le 12 novembre). Sur le robot d'un agent, le « ? » orange voulait dire « une course attend ton autorisation » ; depuis la PR #88, une course ne demande plus rien, il ne s'allume donc plus pour elles. Il dit désormais « il me faut ta réponse » : il s'allume aussi tant que le questionnaire de l'agent (`<sorties>/questions.md` : les questions de la note, les suggestions de la vérification de conception, une question bloquante de *Vibe*) a une question sans réponse envoyée, et s'éteint quand le questionnaire est vide. Il reste allumé pour une demande d'autorisation de la conversation (en *Manuel*), qui existe toujours. Il prime, comme aujourd'hui, sur le « ! » d'une course en échec et sur le point vert d'une course finie. Une course qui a écrit des questions et a fini *terminée* montre donc le « ? », pas le point vert.

**Les écarts entre la table et l'appli, corrigés dans ce ticket** (décidé le
12 novembre). En couvrant les 55 commandes de l'extérieur, le banc a trouvé que
l'appli ne tient pas toujours ce que promet la table des commandes. Ils sont
corrigés ici, avant que la 0.15.0 fige le contrat qui jugera le moteur Rust :
- les commandes d'artefacts dont l'appli refuse le travail répondent ce refus,
  avec son code (`refused`, `unknown-artifact`…), au lieu de « ok » avec le
  refus seulement à l'écran : un agent ne croit plus avoir réussi ;
- `draft.edit` et `draft.remove` sur une remarque inconnue sont refusées, au
  lieu de répondre « ok » sans rien changer ;
- `add-artifact` dans un dossier inconnu est refusé, au lieu d'écrire à la
  racine des artefacts. Deux cas du test protégé
  `src/main/app/controllers/tests/invariants/artifact-ops.test.ts` (un
  fichier déposé avec un id de dossier `../..`, puis en chemin absolu)
  exigeaient que le fichier arrive à la racine : ils sont retouchés (décidé le
  12 novembre), et la retouche est signalée dans la PR. Ils ne gardent que
  l'essentiel, en plus strict : le dépôt est refusé et rien n'est écrit nulle
  part, ni dans le dossier d'artefacts ni hors de lui ; la protection (rien
  hors du dossier d'artefacts, I-37) reste vérifiée, et le refus rendu sert de
  témoin à la place du fichier arrivé à la racine ;
- les six codes d'erreur de la table jamais rendus : la table et l'appli
  s'accordent, chaque code de la table est rendu par l'appli là où la table le
  promet, ou retiré de la table (`halted` reste, provoqué à l'écran seulement) ;
- le banc vérifie chacun de ces refus et son code.

**Une consigne d'outils commune à toutes les courses** (décidé le 12 novembre).
Depuis les droits de la PR #88, presque chaque action essuie des refus parce que
ses agents enchaînent leurs commandes (`cd …;`, `&&`, `|`, `>`) ou lisent avec
`sed` et `awk` ; ils ne font plus échouer la course, mais laissent parfois un
travail incomplet (la préparation du commit n'a pas pu indexer la note).
L'appli ajoute au lancement de chaque course une consigne courte, la même pour
toutes : un appel `Bash` par commande, sans `cd`, enchaînement, redirection ni
variable ; lire avec `Read`, `Glob`, `Grep`, écrire avec `Write` ; seulement
les commandes de sa liste, écrites comme elles. Un seul endroit pour toutes les
courses, au lieu de répéter la règle dans chaque skill (le skill `conception`
l'a déjà, et n'a plus de refus).

## Ce que ça ne doit pas faire

- Changer le comportement de l'appli ou de la CLI, hors de la fin d'une course qui a essuyé un refus (« Un refus ne fait plus échouer une course ») et de la vérification de la note (le skill `conception` : la note vérifiée gardée sous son nom, un appel `Bash` par commande ; remplace `conception-checked.md` de la note `0.15.0-courses-droits`), de la pastille « ? » du robot (des questions t'attendent), des écarts entre la table et l'appli (« Les écarts entre la table et l'appli, corrigés dans ce ticket ») et de la consigne d'outils commune à toutes les courses : un ticket de tests → vu en review
- Ajouter à l'appli une porte dérobée pour faire réussir au banc une commande qui ne réussit qu'à l'écran → vu en review
- Joindre GitHub réel, depuis une commande ou depuis le relevé de l'appli → vu en review
- Lire ou écrire le `~/.config` de l'utilisateur, ou sa corbeille : tout vit dans le profil temporaire du banc (`XDG_CONFIG_HOME`, `XDG_DATA_HOME`) → vu en review
- Juger autre chose que la commande et sa réponse (code de sortie, sortie, code d'erreur) : un cas qui vérifierait l'état interne de l'appli ne jugerait pas un autre moteur → vu en review
- Changer ce que compare `test:main-diff` en retouchant le lancement partagé (`tests/main-diff/launch.mjs`) → vu en review
- Entrer dans `npm test` → vu en review
- Laisser passer une commande de la table sans cas de contrat → structure (le banc lit la table et échoue)

## Où ça casse

- 55 commandes, chacune avec un succès et ses refus : la durée du banc n'est
  pas mesurée. Aujourd'hui, chaque lancement de l'appli attend 4 s
  (`launch.mjs`) et une course *forme* du faux `claude` dure 4 s (`HOLD_MS`).
  Pas de cible : on mesure le premier banc complet, puis on décide.
- La corbeille d'Electron (`shell.trashItem`) suit-elle `XDG_DATA_HOME` ? À
  vérifier avant de coder `trash-artifacts` : sinon, le banc écrirait dans la
  vraie corbeille de l'utilisateur.

## Forme

**Ce qui est déjà écrit d'abord, puis du dedans vers le dehors.** Le refus qui
ne fait plus échouer et le skill `conception` sont repris tels quels du dossier
de travail, une entrée chacun. Puis la pastille « ? » (le pur, puis le
contrôleur qui lui passe le questionnaire), puis le banc de contrat (ses
fournitures, son décor, son résumé, une famille de cas par fichier, le script
qui les enchaîne), le skill `vibe`, la doc. Puis, décidés le 12 novembre et
ajoutés après ces entrées commitées, du pur vers le dehors : la remarque
connue, le refus traduit par l'exécuteur, la consigne d'outils (le pur), puis
les refus des artefacts avec leur clé et le contrôleur qui attend leur fin et
refuse une remarque inconnue, puis le banc qui vérifie chaque nouveau refus, la
doc.

**La pastille.** `controllers/agents.ts` ne change pas : son robot passe déjà
par `runSignalOf`, qui lit désormais le questionnaire. Le libellé du robot
(« attend ta réponse », `activity.asking`) existe déjà ; « attend votre
autorisation » de la conversation reste.

**Le banc.** `tests/main-diff/launch.mjs` ne change pas : son `setup` crée
l'`origin` local, son `env` donne le `PATH` du faux `gh` et `XDG_DATA_HOME`.
`package.json` non plus (`test:contract` lance toujours `run.mjs`). Le faux
`gh` s'appelle `gh` (le `PATH` le trouve) : exécutable, commité en mode 755.

**Les artefacts répondent fini.** Leurs actions tournent en fond (`runDirect`,
`track`) et répondaient « ok » au départ : l'opération rend désormais `done`, la
fin de son travail, que l'exécuteur attend avant de répondre (la même réponse
pour toutes les portes). `copy-artifact` n'attend pas sa fenêtre : un id inconnu
est refusé avant elle. Les clés : un id inconnu (élément ou dossier d'arrivée,
`add-artifact` compris) → `unknown-artifact` ; un nom refusé → `invalid-args`
(`arg: name`) ; le disque en échec → `failed` ; tout autre refus → `refused`.
Une remarque inconnue du brouillon → `invalid-args` (`arg: id`).

**Les six codes jamais rendus par le banc, code par code.** Tous sont rendus
par l'appli : aucun n'est retiré de la table (`resources/vibecoder/commands.json`
et son test ne changent pas) ; le résumé nomme ceux que le banc n'atteint pas,
avec leur raison :
- `changing` : rendu quand une course écrit et qu'une action qui lit veut
  partir (`lockCode`, `core/vibecoder/runs.ts`) ; le banc ne monte pas ce
  croisement → reste, nommé par le résumé ;
- `halted` : après l'arrêt de *Vibe*, à l'écran seulement → reste, nommé ;
- `worktree` : une action qui change la branche, dans un worktree
  (`runDirect`, `startAction`) ; le banc n'a pas de worktree (la fenêtre de
  confiance) → reste, nommé ;
- `refused` : rendu désormais par les refus des artefacts → reste, vérifié par
  le banc ;
- `failed` : une opération qui lève (le `catch` de l'exécuteur), le disque en
  échec d'un artefact ; le banc ne provoque pas de panne → reste, nommé ;
- `bad-token` : rendu par le socket (`BAD_TOKEN`), avant l'exécuteur ; la CLI
  n'envoie rien sans jeton → reste, nommé.

**La consigne d'outils.** Là où l'appli passe ses instructions au SDK
(`queryOptions`, `systemPrompt.append`) : ajoutée quand la session a des droits,
c'est-à-dire une course ; la conversation n'en a pas. `controllers/runs.ts` et
`agents.ts` ne changent pas.
