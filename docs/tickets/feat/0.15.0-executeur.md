# 0.15.0 — L'exécuteur des commandes de VibeCoder

Étape 2 du plan « VibeCoder pilotable par agents » (artefact `actions/pilotage-par-agents.html`, « Le plan », étape 2). L'étape 1, la table des commandes, est fusionnée (note `0.15.0-registre-commandes.md`, PR #80) ; l'étape 3 (la porte : socket et CLI) vient après.

Ce ticket fait l'exécuteur seul, prouvé par ses tests : aucune porte ne l'appelle encore, ni l'écran ni la boîte aux lettres, et rien ne change à l'écran (décidé : les branchements font le ticket suivant, voir les pistes).

## Ce que ça fait

- Une seule entrée exécute une commande de la table (`resources/vibecoder/commands.json`, `core/commands`). Elle reçoit la cible (le dossier du dépôt, son chemin réel, jamais l'id d'un robot), le nom de la commande, ses arguments et la porte d'où vient la demande (l'écran, un agent). Elle répond tout de suite : `{ ok: true, result }` ou `{ ok: false, error }`.
- Une erreur est une donnée, sans langue (décidé : le moteur doit marcher sans l'appli, qui n'a alors pas de langue à donner) : un code stable (`busy`, `same`, `changing`, `invalid-args`, `closed`, `unknown-command`, `not-offered`…), les détails utiles (l'argument fautif et son chemin, l'action qui retient…), un message en anglais pour un modèle et ce qu'il faut faire, en anglais aussi. C'est l'appelant qui l'interprète : l'écran la traduit d'après son code dans la langue de l'appli (ses textes d'aujourd'hui, `ERRORS`, `blockedBy`, `requestNotice`), un agent la lit et la dit à l'utilisateur dans sa langue. La liste des codes fait partie du contrat (dans la table, à côté des commandes). Un motif de grisé que le relevé ne donne qu'en texte (`disabled`) passe tel quel dans les détails, en attendant d'avoir son code.
- Les arguments sont vérifiés contre le schéma de la commande (`schemaError`), après une conversion tolérante quand elle est sans ambiguïté (`"2"` → `2`, `"true"` → `true`).
- Elle appelle ce qui existe, sans le refaire :
  - lancer une course (`startAction`), l'arrêter, la garder, l'annuler (`runOp`) ;
  - les opérations des processus (`proc.stop`, `proc.restart`) ;
  - les actions directes (`runDirect`) ;
  - les lectures (`status`, `next`, `actions`, `runs`, `procs`, `logs`), calculées d'après le relevé (`statusOf`, `nextOf`, `actionsOf`, `runsOf`, `procsOf`, `logsOf`).
- Les mêmes gardes que l'écran : `blockedBy` (une seule action qui écrit à la fois, les lectures ensemble), l'action proposée et pas grisée au relevé, `okRef` et les autres arguments vérifiés des actions directes, la liste fermée de I-39.
- L'entrée charge la table à l'exécution, pour la première fois (vérifiée par `parseCommands`).
- L'ouverture aux agents décidée à l'étape 1, dans l'entrée : à la porte « agent », tout ce que la table ouvre aux agents s'exécute, actions `DIRECT_ONLY` comprises (pull, rebase, pousser, publier une revue…) ; seules les commandes fermées (`run.allow`, `run.always`, `run.deny` : répondre à une autorisation) sont refusées. Un agent n'y accède vraiment qu'une fois la boîte aux lettres branchée (ticket suivant).
- `verdict` s'ajoute à `run.start` (les clés que garde un `.start`, `KEEP` dans `parseRequest`, et le schéma de la table) : `approve`, `comment` ou `request-changes`, lu par `publish` (le seul gabarit qui a `{{verdict}}`). Un `.start` le garde donc aussi (`KEEP` et le schéma de `run.start` restent égaux, variant de l'étape 1), et la section des arguments du skill `actions` le cite.

## Ce que ça ne doit pas faire

- Ouvrir à un agent une commande fermée (`run.allow`, `run.always`, `run.deny` : répondre à une autorisation), par quelque porte que ce soit → invariant
- Exécuter une commande sans les gardes de l'écran : deux actions qui écrivent en même temps, une action pas proposée ou grisée au relevé, un argument que l'écran refuserait → invariant
- Changer les gardes existantes de I-39 (jamais `--force` seul, un rebase en échec annulé aussitôt, `git status` relu avant un changement de branche…) → invariant (ceux de I-39, existants)
- Exposer quoi que ce soit hors du principal : ni socket, ni CLI (étape 3) → structure
- Toucher au pont (`src/preload/`, `src/shared/bridge/channels.ts`) ou à la page (`src/renderer/`) → structure
- Refaire ce qui existe (`startAction`, `runOp`, `runDirect`, les opérations des processus, les lectures de `core/commands`) au lieu de l'appeler → vu en review
- Brancher l'entrée sur une porte (l'écran, la boîte aux lettres) : ticket suivant → vu en review
- Changer ce que font les boutons de l'écran et la boîte aux lettres (hors `verdict`, gardé par un `.start`) : mêmes refus, mêmes avis, mêmes résultats → variant suffit
- Accepter un argument hors du schéma de sa commande, ou le convertir quand c'est ambigu → variant suffit
- Une réponse qui ne suit pas son schéma (lectures), ou qui contient un id de robot → variant suffit
- Une erreur sans code de la liste, ou dont le message dépend de la langue de l'appli → variant suffit
- Une erreur qui ne dit pas ce qui s'est passé et quoi faire → vu en review
- Une section d'arguments d'un skill qui diffère de ce que produit la table → variant suffit

## Ce que ça touche

- L'entrée elle-même, dans `app/controllers` (le plan) : à créer.
- `resources/vibecoder/commands.json` : `verdict` dans `run.start`.
- `src/main/core/commands/` : la table (`parseCommands`), le schéma (`schemaError`), les lectures (`reads.ts`), le texte des skills (`skill-text.ts`).
- `src/main/core/vibecoder/runs.ts` : `parseRequest`, `KEEP`, `REQUEST_ARGS` (`verdict`) ; `blockedBy`, `requestNotice` (leurs messages).
- `src/main/app/controllers/runs.ts` : `runOp`, `startRun`, appelés ; `runRequests` (la boîte aux lettres) inchangé.
- `src/main/app/controllers/processes.ts` : l'arrêt et le relancement d'un processus, appelés ; les demandes `run/<nom>.stop|.restart` (`processView`) inchangées.
- `src/main/app/controllers/vibecoder.ts` : `startAction` (son refus des `DIRECT_ONLY`, levé pour l'entrée seulement), `runDirect`, `lastView`, `ERRORS` (leurs messages) ; `runVibeAction` et `vibeRunOp` inchangés.
- `src/main/app/settings.ts` : là où se charge le catalogue (`vibeActions`).
- `resources/vibecoder/plugin/skills/actions/SKILL.md` : sa section des arguments (`verdict`).
- `SPEC.md` : F-116 (« Elle déclare, elle n'exécute rien » : l'exécuteur existe, aucune porte ne l'appelle), le tableau des modules du principal ; le README (« Les commandes »). I-39 et F-115 ne changent qu'avec les branchements.

## Forme

**Du dedans vers le dehors.** Le pur d'abord : la conversion des arguments
(`core/commands/schema`), le code d'une course qui retient et `verdict`
(`core/vibecoder/runs`), la liste des codes d'erreur dans la table
(`commands.json`, puis `parseCommands`), puis l'exécuteur
(`core/commands/execute`). Puis le principal : là où se charge la table
(`app/settings`), les fonctions existantes qui disent en plus *pourquoi* elles
refusent (`reason` : une clé, à côté de leur texte d'aujourd'hui, inchangé),
l'opération d'un processus tirée de la boîte aux lettres (`processOp`), et le
mince branchement `runCommand`. Puis le skill `actions` et la doc.

**Les gardes ne sont pas refaites.** L'exécuteur ne vérifie que ce qui est à
lui : la commande dans la table, la porte, le schéma, l'action présente au
relevé et pas masquée (pour `run.start` : présente, masquée ou non, la règle
de la boîte aux lettres et de l'écran — décidé : *Écrire les invariants* est
masquée sans griser et reste possible, l'invariant `commands-guards` la lance ;
une action masquée et grisée, `startAction` la refuse), le nom d'un processus. Le reste (une course ou une
action directe qui retient, le grisé du relevé, les arguments que vérifie
`buildMessage`, `okRef`, la liste fermée de I-39) reste dans `startAction`,
`startRun` et `runDirect`, qui rendent désormais la clé de leur refus ;
l'exécuteur la traduit en code. Les commandes `DIRECT_ONLY` vont à
`runDirect`, jamais à `startAction` : son refus des `DIRECT_ONLY` reste, rien
à lever. Les commandes nommées d'une action de `DIRECT_ACTIONS` (`load-pr`,
`pr-here`, `pr-worktree` comprises) passent par `runDirect` ; `comment`,
`case-ko` (remplissent le champ de la page) et `add-artifact` (un dépôt sur
le panneau) sont refusées (`not-offered`) : le ticket suivant tranche.

**La cible.** `runCommand` reçoit le robot (choisir le robot d'un dossier,
c'est le ticket suivant) ; l'exécuteur ne voit que son relevé
(`lastView`). Les tests des invariants (porte agent : `run.allow`,
`run.always`, `run.deny` refusés par `execute` ; les gardes de l'écran
traversées par l'entrée) partent avec le premier commit (note, forme,
invariants).

## Pistes pour plus tard

- Le ticket suivant, les branchements (décidé pour lui) :
  - un seul chemin pour tous : l'écran et la boîte aux lettres passent par l'entrée. Pour l'écran, les canaux du pont ne changent pas : leurs gestionnaires (`runVibeAction`, `vibeRunOp`, `processAction`) deviennent de minces adaptateurs qui appellent l'entrée avec la porte « écran » ; ce qui est propre à l'écran reste dans son adaptateur, avant l'appel (la boîte de dialogue d'un processus qui tourne ailleurs, le choix « direct » ou « via l'agent », les fichiers déposés sur le panneau) ;
  - la boîte aux lettres (`actions/<id>.start`, `.stop`, `run/<nom>.stop`, `.restart`) passe par l'entrée : mêmes refus, mêmes avis, un `.start` retenu reste en attente ; elle accepte ce que la table ouvre aux agents (un `.start` pour une action `DIRECT_ONLY` n'est plus refusé) ;
  - elle sert toute commande de la table, lectures, `run.keep` et `run.undo` compris : un fichier de demande générique (la commande et ses arguments), la réponse de l'entrée écrite dans un fichier à côté, et un avis d'une ligne à la conversation qui la signale et réveille l'agent ; les fichiers d'aujourd'hui restent jusqu'à l'étape 3 ;
  - les skills `actions` et `processus` suivent (leur section produite par la table) ;
