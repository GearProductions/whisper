# 0.16.0 — La revue essentielle

Branche `feat/0.16.0-revue-essentielle`, à partir de `master` après la fusion de la PR #105 (l'écran de l'essentiel, `docs/tickets/feat/0.16.0-ecran-essentiel.md`), qui n'a rien changé pour le relecteur d'une PR.

## Ce que ça fait

La PR #105 a donné au créateur un écran qui ne montre que ce qu'il regarde ou décide. Le relecteur d'une PR a gardé l'écran d'avant : six étapes, une rangée de boutons par étape, une étape Forme où il n'a rien à juger, une étape des commits très chargée. Ce ticket fait pour lui ce que la PR #105 a fait pour le créateur (demandé le 25 novembre 2026, la PR #105 fusionnée) : une revue plus agréable, qui va à l'essentiel, sans les frictions qui ne servent à rien.

**Le principe.** Le développeur se tient sur la note, les invariants et l'essai manuel à l'écran ; le reste est un contrôle secondaire, automatique. Tout ce qui suit vaut pour le relecteur ; rien ne change pour le créateur.

1. **Le fil du relecteur en quatre arrêts.** La note (la lire et la juger : le seul regard indépendant sur ce qui a été demandé), les règles (les invariants), l'essai (le plan de test à l'écran), publier (les constats de l'agent sur le code, le brouillon de remarques et le verdict). Le créateur garde son fil de six étapes. Le « N commits » au bout du fil, et la liste qu'il déplie, disparaissent (on ne relit plus l'histoire des commits ; la PR s'ouvre sur GitHub depuis sa carte).
2. **Une ligne dit où il en est**, comme pour le créateur : sous le fil, une seule phrase, ce que le système est en train de lire ou ce qu'il attend du relecteur, d'après ce que le relevé sait déjà (la PR chargée ou non, les lectures en cours, la note jugée, les tests jugés, les cases du plan cochées, la revue publiée). À côté d'elle, le seul bouton du relecteur, *Préparer la revue* (visible à tous les arrêts, comme *Reprendre* chez le créateur).
3. **La Forme disparaît du fil** : il n'y a rien à y juger (aujourd'hui elle est faite avec la Note). Avec elle partent l'arbre des modules, *Structure* / *Code* et les remarques par module.
4. **L'étape des commits se vide.** Ni éditeur façon IDE (les modules en lecture seule, *Vue IDE* / *Vue liste*, le code d'un module), ni blocs de commits (une carte par commit, ses fichiers, *Voir le diff*, *GitHub*, *Validé* / *À revoir* par commit, le fichier d'un commit ouvert sous sa carte). Une seule chose : la relecture du code par l'agent, et ses constats à l'écran, chacun avec sa bulle pour le mettre dans le brouillon de revue. Pour lire le code soi-même : l'éditeur externe (*Ouvrir dans l'éditeur*).
   - Les constats se lisent à l'arrêt « publier », au-dessus du brouillon (c'est là qu'on décide ce qui part dans la revue, et le fil reste à quatre arrêts) : l'étape des commits n'est plus un arrêt.
   - La bulle d'un constat ouvre une zone de remarque déjà remplie avec le constat, à corriger puis *Ajouter* : il arrive dans le brouillon, juste en dessous (la revue part sous le nom du relecteur ; c'est déjà ainsi pour le point d'attention d'un test).
   - Sans carte de commit, plus de verdict par commit : le verdict proposé à la publication vient de la note et des tests.
5. **La relecture du code, en une passe sur tout le diff de la PR**, plus commit par commit (le skill `relire-commits`).
   - Elle garde ce qui est utile : les quatre questions du guide (§ 5.1), la duplication avec du code existant, le code suit-il la note et sa Forme, les bugs, les en-têtes de fichiers.
   - Elle ne relit plus l'histoire des commits : un premier commit avec la note, la forme et les invariants, un commit par module, pas de commit `wip` ou `fix`, un fichier dans le mauvais commit, un module trop gros (tous les projets de l'utilisateur fusionnent en squash : ces remarques ne seraient corrigées par personne, et elles coûtent des tokens ; divergence assumée avec le guide, § 5.2 et § 5.4).
   - Un test d'invariant d'avant la branche que la PR modifie est dit par l'appli elle-même, sur ce test, dans la vue des règles (son texte à la base diffère : le relevé le sait déjà, sans agent ni token, avant tout *Préparer la revue*) ; la relecture du code n'en dit rien.
6. **Les règles : la même vue que le créateur.** Une règle par ligne « → invariant » de la note, ses tests en pseudo-code, *Validé* / *À revoir* sur chaque test ; une ligne sans test dite « aucun test », les tests sans ligne dans « Autres tests » ; en tête, l'alignement, qui dit si chaque règle a son test. Elle remplace les anciennes cartes du relecteur (une carte par cas et son *Pseudo-code* / *Code*, *Tout valider*, le résumé et la barre de progression, l'arbre des tests et *Invariants seuls*, *Voir le fichier* et le menu de diff, « non rattaché »).
   - *À revoir* va dans le brouillon de revue comme aujourd'hui (il propose d'ajouter une remarque ; rien n'est ajouté sans le clic) ; la bulle d'une règle ou d'un test ouvre une remarque pour le brouillon (chez le créateur, elle cite dans la conversation).
   - Sur une PR, l'alignement écrit aussi `liens.md` (quel test garde quelle ligne, tests d'avant la branche compris), dans le dossier de sorties seulement, rien dans la branche : la vue range les tests comme chez le créateur (skill `aligner`, mode `HEAD`).
   - Pas de preuve chez le relecteur : ni « écrite », « prouvée », « non prouvée », ni détail au clic (la preuve est faite sur la machine du créateur et n'est pas dans la PR ; rien à dépenser, rien à changer côté créateur).
   - L'arrêt est fait comme aujourd'hui : chaque test jugé.
7. **Un seul geste, *Préparer la revue*.** Il lance d'un coup les cinq lectures — la relecture de la note par l'agent, le pseudo-code des tests, l'alignement, la relecture du code, le plan de test à l'écran — pour que le relecteur trouve tout prêt. L'arrêt « la note » montre la relecture de l'agent au-dessus de la note, comme aujourd'hui, sans bouton à lui.
   - Jamais automatique : charger une PR, ou l'ouvrir pour regarder, ne lance rien et ne dépense aucun token.
   - Une revue déjà préparée : le bouton ne lance que ce qui manque ou a été lu sur une autre tête de la PR (chaque lecture retient le commit de tête d'où elle est partie, une marque comme `commit:<hash>` posée quand elle finit bien, qu'elle vienne de *Préparer la revue* ou de la CLI ; échouée ou arrêtée, elle ne la pose pas et sera relancée ; les lectures des tests suivent déjà leur empreinte) — rien n'est payé deux fois, et la revue suit la PR, sans comparer d'heures.
   - Les boutons de chaque lecture (*Relire la note*, *Lire en pseudo-code*, *Relire*, *Tout relire*, *Vérifier l'alignement*, *Relire les commits*, *Plan de test à l'écran*, *Relancer*) quittent les arrêts ; chaque lecture reste lançable seule par l'agent et sa CLI.
8. **Ce qui ne change pas** : juger la note (*Valider* / *À revoir*, les remarques sur ses lignes), le plan de test à l'écran et ses cases, le brouillon de remarques, le verdict et *Publier la revue*, le chargement d'une PR et ses choix de lieu ; tout le côté créateur.

`SPEC.md` et `README.md` suivent.

## Ce que ça ne doit pas faire

- Lancer une lecture (dépenser des tokens) sans geste du relecteur : charger une PR, l'ouvrir, changer d'arrêt ou un simple relevé ne lancent rien ; seuls *Préparer la revue* ou une demande à l'agent le font → invariant
- En relecteur, écrire un fichier ou lancer ce qui édite, génère ou commite : *Préparer la revue* ne lance que des lectures (I-37, I-39, déjà gardés par `src/main/app/controllers/tests/invariants/reviewer.test.ts`, protégé) → variant suffit
- Mettre quoi que ce soit au brouillon de revue, ou publier, sans le geste du relecteur : un constat de l'agent n'entre au brouillon que par sa bulle, rien ne part sur GitHub avant *Publier la revue* → variant suffit
- Cacher ce qui demande le regard du relecteur : une ligne « → invariant » sans test, un test hors de toute règle, un écart de l'alignement, le point d'attention d'un test, un test protégé que la PR modifie → variant suffit
- Relire l'histoire des commits : aucun constat sur l'ordre des commits, le premier commit, un commit par module, un commit `wip` ou `fix`, un fichier dans le mauvais commit, un module trop gros → vu en review
- Toucher au côté créateur : son fil de six étapes, sa ligne d'état, ses vues, le moteur → variant suffit
- Changer ce qui ne devait pas changer chez le relecteur : juger la note, le plan de test et ses cases, le brouillon, le verdict, *Publier la revue*, le chargement d'une PR et ses choix de lieu → variant suffit
- Retirer une lecture à l'agent : chaque lecture reste lançable seule par la CLI → variant suffit (`npm run test:contract`)
- Toucher aux ponts et à leurs canaux (`src/preload/`, `src/shared/bridge/channels.ts` : frontière de sécurité) → structure

## Où ça casse

- Une grosse PR : 16 modules (gt-plugins, PR #774) ; la relecture du code lit tout son diff en une passe.
- Cinq lectures lancées d'un coup, sur la même PR, dans le même dossier.

## Forme

**Le parcours du relecteur se sépare de celui du créateur.** `journey` rend
quatre étapes au relecteur (la note, les invariants, la revue, la PR, sous les
noms « Note », « Règles », « Essai », « Publier ») et toujours six au
créateur. Les vues d'étape restent les mêmes fichiers : la Forme et les
Modules ne servent plus qu'au créateur, et chaque vue perd sa partie du
relecteur ou la remplace.

**Préparer la revue, c'est la page qui demande.** Le relevé dit quelles
lectures il reste à lancer (`prepare`) ; le bouton du fil d'Ariane demande
chacune par le canal qui existe (une demande par lecture) : ni canal, ni
commande de plus au registre. Rien dans le principal ne lance une lecture.

**Chaque lecture retient sa tête.** À la fin d'une lecture réussie, le
principal pose la marque « read:<pr>:<action> » pour le commit de tête d'où
elle est partie, qu'elle vienne du bouton, de la CLI ou de la file. La marque
porte la PR : relire la PR A, passer à B puis revenir à A ne relance aucune
lecture déjà faite. Le nouveau module `readings` porte cette règle et la
liste de ce qu'il reste à lancer.

**En relecteur, toute course lit.** L'alignement, qui corrige les tests chez
le créateur, devient une lecture sur une PR (`roleDefs`) : il n'écrit que dans
le dossier de sorties, et les cinq lectures courent ensemble.

**Les constats remplacent les commits.** La relecture du code garde son
action (`review-commits`), son skill (`relire-commits`) et sa sortie
(`pr-<n>-commits.md`) : seuls son libellé et son contenu changent (un titre
par constat). La page la montre à l'arrêt « Publier », dans une vue neuve.

**Ce qui part, ce qui reste.** Partent avec les vues du relecteur ce que plus
rien n'appelle et qu'aucun test protégé ne garde : les cartes de commits, les
cartes par cas, « non rattaché », la rangée d'actions des étapes. Restent
dans le dépôt, sans appel de la page : le fichier d'un commit, l'éditeur en
lecture seule et le menu de diff (piste plus bas).
