# 0.16.0 — L'écran de l'essentiel

Branche `feat/0.16.0-ecran-essentiel`, à partir de `master` après la fusion de la PR #103 (le contrôle en trois points). Part de l'état laissé par `docs/tickets/feat/0.15.0-ecran-epure.md` (les en-têtes d'étape sans doublon).

## Ce que ça fait

Depuis la PR #103, le système enchaîne seul : l'utilisateur valide la note, regarde aux deux pauses (après les invariants ; après les modules, pour son essai), répond aux questions `[toi]`, et c'est tout. Il ne lit pas le code ; quand quelque chose coince, il le demande à l'agent, qui a la CLI `vibecoder` (un bouton n'apporte rien de plus). L'écran, lui, est resté celui d'un parcours manuel, très chargé (constat sur quatre captures du 24 novembre 2026, gt-plugins, PR #774).

**Le principe.** L'expérience est simple et fluide : l'écran donne au développeur l'information qu'il lui faut, le laisse intervenir là où c'est important, et le reste se déroule sans lui. Il ne montre que ce que l'utilisateur doit regarder ou décider ; tout ce que le système fait passe par le moteur ; une action à la demande se demande à l'agent. Au plus un geste par écran, et seulement s'il est à l'utilisateur. Une information n'apparaît qu'une fois. Tout ce qui suit vaut pour le créateur ; le relecteur d'une PR ne change pas.

1. **Une ligne dit toujours où on en est.** En haut de l'écran, sous le fil des étapes, une seule phrase : ce que le système est en train de faire, ou ce qu'il attend de l'utilisateur, avec à côté le bouton du moteur quand il sert. Par exemple : « Demandez la note à l'agent, dans la conversation », « 2 questions : répondez dans le questionnaire », « Vérifiez, puis validez la note », « Le système écrit les modules », « Regardez vos règles, puis reprenez », « Essayez l'appli, puis reprenez », « La PR est ouverte, la CI tourne », « La PR est verte : à vous de la fusionner ». La ligne de pause d'aujourd'hui (« La note a changé : elle attend sa validation ») en est un cas. Le compte « 24 commits » du fil disparaît.
2. **Plus de boutons d'action dans les étapes.** *Rédiger la note* et *Nouvelle demande* (on demande la note à l'agent, dans la conversation), *Poser la forme*, *Valider la forme*, *Écrire les invariants (rouges)*, *Tout valider*, *Lire en pseudo-code*, *Prouver les invariants*, *Générer*, *Relire le diff*, *Lancer les vérifications* (et la ponytail review), *Appliquer* et *Tout appliquer*, *Plan de test à l'écran*, *Valider la feature*, *Diagnostiquer la CI*, *Relancer*, *Me retirer de la PR*, et les autres boutons d'action des étapes disparaissent de l'écran. Ces actions restent lançables par la CLI (l'agent), avec le même contrat : rien n'est retiré du registre des commandes. Restent à l'écran : la note (*Vérifier*, *Valider la note*, le questionnaire), le fil des étapes, l'interrupteur *Express* et le bouton du moteur (*Arrêter* / *Reprendre*).
3. **Plus d'édition du code à la main.** Le code et les tests se lisent, ils ne se modifient plus dans l'appli : ni éditeur, ni *Enregistrer*. Une correction se demande à l'agent. *Ouvrir dans l'éditeur* reste, une icône discrète par fichier : la sortie de secours vers l'éditeur du développeur. La note, elle, reste modifiable à l'écran : c'est le document de l'utilisateur. La page ne propose plus l'écriture ; les ponts et leurs canaux ne changent pas dans ce ticket.
4. **Plus de réglages de lecture du code.** Le menu « Depuis la base de la branche », *En ligne* / *Côte à côte*, *Structure* / *Code*, *Vue IDE* / *Vue liste*, *Invariants seuls* disparaissent. Un seul affichage : le diff depuis la base de la branche, en ligne. Une seule exception, et seulement quand elle sert : après une correction, l'en-tête de l'étape dit « modifiée depuis la validation », et un clic dessus bascule le diff sur ce qui a changé depuis le ✓.
5. **Forme : la liste des modules, sans code.** Une ligne par module : son chemin, et ce qu'il fait en une phrase. Ni arbre, ni diff, ni badge « touché », ni « 1 commit », ni icônes. Le code n'est plus qu'à l'étape Modules : un seul endroit pour l'arbre et le diff.
6. **Invariants : rangés par ligne « → invariant » de la note.** En titre, le texte de la ligne, tel que l'utilisateur l'a écrit, et son état : écrite (ses tests sont rouges), prouvée, non prouvée (un état par ligne : c'est ce que la preuve donne, et c'est la ligne que l'utilisateur juge). Dessous, les tests qui la gardent, en pseudo-code. C'est ce que l'utilisateur regarde à la pause après les invariants : chaque règle critique de sa note, et ce qui la garde, dans ses mots.
   - Le pseudo-code vient de la lecture existante (*Lire en pseudo-code*), que le moteur lance lui-même après chaque écriture des tests d'invariants : après *Écrire les invariants*, avant la pause, et après une correction des tests par l'alignement de la preuve. C'est un regard indépendant de celui qui a écrit les tests. Le skill du moteur (`resources/vibecoder/plugin/skills/vibe/SKILL.md`, qui l'exclut aujourd'hui) et `journey.ts` (« Lire en pseudo-code : jamais prochaine action ») changent en conséquence.
   - Une ligne sans test s'affiche quand même, signalée « aucun test » ; les tests qui ne gardent aucune ligne vont dans un dernier groupe, « Autres tests » : rien n'est caché, un trou dans la garde se voit.
   - Le résultat de la preuve ne s'affiche qu'ici, sous chaque ligne, pas à l'étape Modules.
   - L'alignement suit la règle de la Revue : ses écarts `[toi]` en avant, les `[agent]` repliés avec leur nombre, sans *Relancer* ; rien quand tout est aligné.
   - Plus de validation cas par cas, plus de chiffres en tête (fichiers, cas, validés, à lire), plus de barre « 0 / 3 validé », plus de « GARDE non rattaché » ni de « Pas de lecture pour ce cas ».
   - La bulle de remarque reste sur une ligne de la note et sur une règle de cette étape : c'est par elle que l'utilisateur dit quelque chose à l'agent en montrant de quoi il parle. Elle disparaît du code.
7. **Modules : l'arbre et le diff du code, en lecture seule, sans boutons.** En tête, une seule ligne d'état (« 16 modules écrits · commités »). La preuve a lieu à cette étape, mais son résultat ne s'affiche qu'à l'étape Invariants, sous chaque ligne « → invariant ». Plus de « 16 commité · 0 en cours · 0 à faire ».
8. **Revue : une seule carte.** Avant la revue, une ligne : « la revue part après votre essai » au rythme par défaut, « la revue part après les modules » en express. Après : le résultat des vérifications (une ligne par vérification en échec, rien quand tout passe), les remarques `[toi]` de la ponytail review en avant, sans bouton (on y répond dans le questionnaire ou à l'agent, comme le moteur le fait déjà), les `[agent]` repliées avec leur nombre. Plus de liste « Avant la PR » (guide § A.3), plus de cartes vides (« Pas encore de vérification », « Pas encore de ponytail review », « Pas encore de plan de test »).
9. **PR : la carte de la PR et l'état de la CI, sans bouton.** Une ligne par vérification en échec, rien quand tout passe.
10. **Le ✓ retiré à la main, par le badge de l'étape.** Le moyen de l'utilisateur de dire « pas d'accord » (décidé dans la PR #103 : il met le parcours en pause) a besoin d'un geste, les boutons de validation partis : le badge d'état de l'étape, dans son en-tête, porte le ✓ (« faite ✓ » validée ; « faite · ✓ retiré » tant que le retrait tient) et se clique pour retirer ou rendre le ✓ — à la Forme, aux Invariants et aux Modules, les étapes dont le ✓ se retire (PR #103). Une étape faite que le système n'a pas validée (une preuve qui ne passe pas, un contenu changé depuis) : le badge sans ✓ et sans clic, il ne valide jamais à la place du système. Rien d'autre.

`SPEC.md` et `README.md` suivent.

## Ce que ça ne doit pas faire

- Retirer une possibilité : toute action retirée de l'écran reste lançable par la CLI, avec le même contrat (registre des commandes inchangé) → variant suffit (`npm run test:contract`)
- Cacher ce qui demande l'utilisateur : une question `[toi]`, une pause, un invariant non prouvé, une ligne « → invariant » sans test, une vérification en échec restent toujours visibles → variant suffit
- Montrer une même information à deux endroits (l'arbre et le diff du code ailleurs qu'à l'étape Modules, le résultat de la preuve ailleurs qu'à l'étape Invariants, un compte répété) → vu en review
- Faire du clic sur le badge d'une étape autre chose que retirer ou rendre son ✓ (lancer une action, valider la note, valider une étape que le système n'a pas validée) → variant suffit
- Laisser modifier du code ou un test depuis l'écran ; retirer la modification de la note → variant suffit
- Toucher au parcours du relecteur d'une PR (*Relire la note*, *Relire les commits*, *Validé* / *À revoir*, le brouillon de revue, *Publier la revue*) → variant suffit
- Toucher aux ponts et à leurs canaux (`src/preload/`, `src/shared/bridge/channels.ts` : frontière de sécurité) → structure

## Forme

**L'écran change, le principal presque pas.** Tout se joue dans la page : les
vues d'étape du créateur perdent leurs boutons, la page ne propose plus
d'écrire le code. Le relevé garde tout ce qu'il porte (les actions, la liste
« Avant la PR », le réglage de la vue Modules, que la page ne lit plus) : la
CLI garde le même contrat. Deux choses bougent dans le principal : *Lire en
pseudo-code* devient une action du moteur, et le relevé dit, pour chaque
étape, si son ✓ a été retiré à la main.

**Le créateur et le relecteur dans les mêmes vues.** Chaque vue d'étape garde
la partie du relecteur telle qu'elle est et remplace celle du créateur. Deux
vues neuves pour lui : les règles (l'étape Invariants rangée par ligne
« → invariant ») et un fichier de retour montré selon ses étiquettes.

**Le ✓ sur le badge.** Le clic sur le badge d'une étape passe par la
validation d'étape qui existe (la même que les anciens boutons *Annuler* et
*Valider*) : aucun canal de plus.

**Un seul diff.** Le code ne se montre qu'à l'étape Modules, depuis la base de
la branche, en ligne ; « modifiée depuis la validation », dans l'en-tête de
cette étape, bascule sur ce qui a changé depuis le ✓. L'éditeur de code reste
dans le dépôt (des tests protégés le gardent), la page du créateur ne
l'appelle plus. Le menu de diff reste dans le code pour le relecteur, à
l'étape Invariants : seul le créateur le perd.
