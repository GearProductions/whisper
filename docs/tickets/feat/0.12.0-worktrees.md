# 0.12.0 — Les worktrees : la recette du projet, Relire et Créer au choix

## Ce que ça fait

### La recette du projet

- Le fichier du projet quitte le dossier de l'appli
  (`userData/vibecoder/projets/<dossier>.json`, F-111) pour `.vibecoder/` à
  la racine du dossier du parent, comme `.zed` ou `.claude` : tout au même
  endroit, réglages compris. Ignoré par git : l'appli ajoute `.vibecoder/` à
  `.git/info/exclude` s'il ne l'est pas déjà (rien à commiter). Un ancien
  fichier du dossier de l'appli est repris s'il n'y a pas encore de fichier
  dans `.vibecoder/`.
- Le fichier du projet gagne :
  - `setup` : les commandes qui préparent le projet (ex. `yarn install`) ;
  - `worktree` : `{ create, remove, dir }`. Pour gt-plugins :
    `yarn setup-worktree "$VIBECODER_BRANCH" "$VIBECODER_BASE"`,
    `yarn cleanup-worktree "$VIBECODER_BRANCH"`,
    `../gt-plugins-worktrees/{branch}` ;
  - `prWorktree` et `featureWorktree` : où va une PR à relire, où va une
    nouvelle demande — `ask`, `here` ou `worktree` (`ask` par défaut).
- Le skill `lancement` propose `setup` et `worktree` **une seule fois** par
  projet (il repère les scripts de worktree, lit AGENTS.md, CLAUDE.md, le
  README, `package.json`). Au relevé, l'appli adopte la proposition pour les
  clés que le fichier n'a pas encore, jamais par-dessus (I-42). Ensuite,
  l'appli exécute ces commandes elle-même, sans IA (les jetons ne se paient
  qu'à la découverte), derrière le préfixe des commandes (F-111).
- Créer un worktree : `worktree.create`, sinon `git worktree add` puis
  `setup`. Le worktree créé et préparé, un robot enfant s'y ouvre (F-51).
- Retirer un worktree : `worktree.remove`, sinon `git worktree remove`,
  refusé s'il reste des modifications. Le worktree retiré, son robot part
  avec lui (son dossier quitte les favoris, le panneau passe au parent).
- Une commande de la recette qui attend une réponse au clavier (le y/N de
  `cleanup-worktree`) ne bloque pas : son entrée est fermée, son échec est
  affiché.
- Le volet *Processus* gagne *Préparer le projet* (lance `setup`), pour un
  projet neuf.
- Le clic droit d'un robot gagne *Ouvrir un terminal ici* : le terminal du
  système, dans le dossier de l'agent.
  - Le terminal et ses arguments viennent du réglage `terminalCommand`,
    découpé comme `agentCommand` (F-58, guillemets respectés) ; `{dir}` y
    est remplacé par le dossier de l'agent, comme un argument entier. Ex. :
    `konsole --workdir {dir}`, `konsole --workdir {dir} -e distrobox enter
    dev`, `wt.exe -d {dir}`.
  - Réglage vide : le premier terminal trouvé dans une liste par système,
    comme les éditeurs (F-56), lancé avec le dossier pour répertoire
    courant. Linux : konsole, gnome-terminal, kitty, alacritty, wezterm,
    xterm ; Windows : `wt`, sinon `cmd`.
  - Entrée grisée si aucun terminal n'est trouvé.

### Relire, ici ou dans un worktree

- Au chargement d'une PR, l'appli demande où la mettre (sauf si
  `prWorktree` le dit déjà) :
  - *Ici* : `git switch` sur la branche de la PR. Grisé, avec sa raison,
    s'il y a des modifications en cours. L'état de *Créer* reste rangé par
    branche (F-95) et revient avec elle ;
  - *Dans un worktree* : la recette crée le worktree (la même commande
    `worktree.create`, avec `VIBECODER_BASE` = la branche de la PR au lieu
    de la base, pour que le dossier ait le code de la PR, et
    `VIBECODER_BRANCH` = `pr-<n>`, une branche locale neuve même si celle
    de la PR existe déjà sur la machine ; rien à changer
    dans les scripts de gt-plugins), puis un robot enfant s'y ouvre en
    *Relire*, avec la PR, sa fiche et son brouillon de revue repris.
- La lecture par référence (`refs/vibecoder/pr/<n>`) reste le socle des
  étapes Note, Invariants et Commits.
- *Ouvrir dans un worktree* (F-110) et son skill `worktree-pr` sont
  remplacés.

### Créer, ici ou dans un worktree

- *Nouvelle demande dans un worktree* (sauf si `featureWorktree` dit
  `here`), toujours visible dans VibeCoder, même si le dossier du parent est
  sur une PR en cours : l'agent du parent nomme la branche d'après la
  demande, selon la convention des branches (`<type>/<ticket>-<intitulé>`, sans ticket
  `<type>/<version>-<intitulé>`, comme en *Créer* aujourd'hui) ; le
  worktree se crée sur cette branche, puis un robot enfant s'y ouvre en
  *Créer* et lance aussitôt *Rédiger la note* avec la demande. Le robot du
  parent reste sur sa branche (une PR en cours n'empêche pas de commencer
  autre chose).

### Fin de vie

- La PR fusionnée, un enfant propose *Retirer le worktree* au lieu de *PR
  mergée → revenir sur la base*. Le skill `retirer-worktree` disparaît.

## Ce que ça ne doit pas faire

- Mettre un nom de branche dans le texte d'une commande : il passe par les
  variables `VIBECODER_BRANCH` et `VIBECODER_BASE`. → invariant
- Lancer autre chose que les commandes du fichier du projet (I-42 étendu à
  `setup` et `worktree`). → invariant
- Lire le fichier du projet ailleurs que dans `.vibecoder/` du dossier du
  parent : jamais celui d'un worktree (une PR pourrait y apporter ses
  propres commandes). → invariant
- Changer de branche dans un dossier qui a des modifications. → invariant
- Créer un robot de PR sans la question de confiance, toujours posée (ses
  réglages `.claude` sont ceux de la PR). → invariant (réécriture d'I-41)
- Retirer un worktree qui a des modifications. → invariant
- Lancer le terminal par un shell (I-27). → invariant
- Perdre les commandes d'un projet déjà réglé dans le dossier de l'appli.
  → variant suffit
- Supposer une box, un bureau ou un système : ce qui est propre à une
  machine vient de `terminalCommand` ou du fichier du projet. → structure

## Forme

**Six thèmes, dans cet ordre**, chacun de l'intérieur vers l'extérieur ; un
fichier touché par plusieurs thèmes revient à chacun (un commit par passage).

**Le fichier du projet, dans `.vibecoder/`.** `<dossier du parent>/.vibecoder/project.json`.
Le dossier du parent : celui de la tête de famille présente (familyOwner) ;
un enfant dont le parent est parti n'a pas de fichier (ni commandes, ni
recette) : jamais celui d'un worktree. À sa première lecture dans la session,
pour chaque dossier : l'ancien `userData/vibecoder/projets/<slug>.json` copié
s'il n'y a rien dans `.vibecoder/` (l'ancien reste : on peut revenir en
arrière) ; `.vibecoder/` ajouté à `<dossier>/.git/info/exclude` si `.git` y
est un dossier (la copie principale) et que la ligne n'y est pas.

**La recette, sans IA.** `setup`, `worktree.create`, `worktree.remove` se
lancent comme les autres commandes du fichier (préfixe, shell du fichier),
une étape après l'autre, l'entrée fermée (stdin ignoré : le y/N lit une fin
de fichier), 15 min au plus chacune, leur sortie dans `<sorties>/recipe.log`,
la dernière ligne utile affichée en cas d'échec ; une recette à la fois par
famille. La branche et la base passent par l'environnement
(`VIBECODER_BRANCH`, `VIBECODER_BASE`). Sans `worktree.create` :
`git -C <parent> worktree add -b <branche> <dossier> <départ>`, puis `setup`
dans le worktree ; sans `worktree.remove` : `git -C <parent> worktree remove
<dossier>` (sans `--force`) — la branche y est un argument à part, sans shell,
jamais dans un texte de commande. Avant tout retrait : `git status
--porcelain` dans le worktree ; une ligne, ou pas de réponse → refusé, quelle
que soit la commande.

**Relire, Ici ou Dans un worktree.** Deux actions directes de l'étape PR
(comme load-pr : `args.direct`, F-114), montrées une fois la PR chargée :
`pr-here`, `pr-worktree`. `prWorktree` réglé : la suite d'un chargement réussi
lance la bonne, seule. *Dans un worktree* : `git fetch origin <tête>` d'abord
(`origin/<tête>` existe pour le script de gt-plugins), `VIBECODER_BRANCH` =
`pr-<n>`, `VIBECODER_BASE` = la tête de la PR ; le départ du repli git :
`refs/vibecoder/pr/<n>`. Le worktree créé, l'appli écrit elle-même la fiche
`pr-<n>-worktree.json` et le robot naît comme aujourd'hui (adopt : la question
de confiance toujours posée, I-41).

**Créer, dans un worktree.** `new-worktree`, une action à texte sans étape (le
lien sous le champ, comme *Demander sans modifier*), sur une tête de famille :
le message part à l'agent du parent (skill `nouvelle-demande`), qui écrit
`<sorties>/new-worktree.json` `{ branch }` ; la demande reste dans le principal
(en mémoire), pas dans ce fichier. Au relevé, cette fiche avec une demande en
attente → le worktree sur la branche (`VIBECODER_BASE` = la base du dépôt,
départ `origin/<base>`), puis l'enfant (la question de confiance d'un dossier
neuf), affiché, en Créer ; à son premier relevé, *Rédiger la note* part avec
la demande. Une fiche sans demande : supprimée, rien d'autre.

**Pas de canal nouveau.** `pr-here`, `pr-worktree`, `new-worktree`,
`remove-worktree` passent par `conv:vibeRun` ; *Préparer le projet* par
`conv:vibeProcess` (op `'setup'`, une valeur de plus de `VibeProcessOp` dans
`shared/bridge/types.ts`, non protégé) ; le terminal par le menu natif du
principal. `src/preload/` et `shared/bridge/channels.ts` inchangés.
