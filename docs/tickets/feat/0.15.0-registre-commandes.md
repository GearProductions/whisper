# 0.15.0 — Le registre des commandes de VibeCoder

Étape 1 du plan « VibeCoder pilotable par agents » (artefact `actions/pilotage-par-agents.html`, sections « Brique par brique » et « Le plan »). Les étapes 2 (l'exécuteur) et 3 (la porte : socket et CLI) viennent après.

Le but de fond : VibeCoder utilisable comme un moteur, sans ouvrir l'appli, pour que d'autres devs montent leur propre interface (l'étape 7 du plan, devenue l'objectif). La table est donc le contrat public de ce moteur : une donnée versionnée, indépendante d'Electron et de TypeScript, que le futur moteur (en Rust) lira telle quelle.

Le principe (celui du guide) : tout ce que fait l'interface, un agent peut le faire, avec les mêmes règles, par n'importe quelle porte (l'écran, l'agent intégré, un agent extérieur, MCP…), à une courte liste d'exceptions près.

## Ce que ça fait

- Une table unique des commandes que VibeCoder sait faire : un fichier JSON versionné, `resources/vibecoder/commands.json` (`schemaVersion`), chargé et vérifié par un module pur du principal, `core/commands` (à part de `core/vibecoder` : c'est l'API du moteur). Chaque commande a :
  - un nom (`run.start`, `run.stop`, `proc.restart`, `status`…) ;
  - une description écrite pour un modèle, en anglais (comme les skills techniques, F-108) : ce qu'elle fait, ce qu'elle répond, ce qui la fait échouer (les libellés pour l'humain restent dans `actions.<langue>.json`) ;
  - un schéma JSON de ses arguments ;
  - un schéma JSON de sa réponse, pour les lectures (une interface tierce lit ce qu'elles rendent) ;
  - lecture ou écriture ;
  - ouverte aux agents ou non : ouverte par défaut ; fermée (`agent: false`) seulement pour une exception de la liste ci-dessous, avec sa raison écrite à côté.
- Les exceptions, fermées aux agents (le guide : un agent ne s'accorde pas de droits, et ne quitte pas l'appli) :
  - répondre à une demande d'autorisation d'une course (`allow`, `always`, `deny` ; I-13 à I-18) ;
  - ce qui accorde des droits : faire confiance au dossier `.claude` d'un projet (hooks, serveurs MCP), le futur réglage « autoriser les agents extérieurs » ;
  - quitter ou redémarrer l'appli.
  Seule la première est dans la table de cette étape ; les autres y entrent avec les réglages (voir les pistes), fermées de même.
- La cible d'une commande est un dossier (le dépôt, son chemin réel), jamais l'id d'un robot de l'appli : un dev sans l'appli n'a pas de robot. Trouver le robot d'un dossier reste l'affaire de l'appli (étapes 2 et 3). Le rangement des données (`vibecoder-out/<agent>/`) ne change pas dans cette étape.
- Elle reprend ce qui existe, sans le refaire, ouvert aux agents :
  - les actions qui courent à part (`ownRun`, catalogue `actions.<langue>.json`) : une seule commande `run.start`, l'id de l'action en argument (`action`, parmi les `ownRun`) ; ses autres arguments, exactement ceux que garde un `.start` (`parseRequest` : `text`, `module`, `commit`, `file`, `pr`, `check`, `model`, `effort`, `answers`) ; pas `verdict`, qu'un `.start` jette aujourd'hui (l'ajouter changerait le comportement : étape 2) ;
  - arrêter, garder ou annuler une course (`run.stop`, `run.keep`, `run.undo`) ;
  - les opérations des processus : `proc.stop`, `proc.restart` (qui lance aussi une commande arrêtée) ;
  - les actions `DIRECT_ONLY` (pull, rebase, pousser, changer de branche, les artefacts…), avec le schéma complet de leurs arguments (ceux que vérifie déjà `controllers/vibecoder` : branche `okRef`, PR, identifiant `okLogin`, artefacts…) ;
  - les 9 actions ni `ownRun` ni `DIRECT_ONLY` (`load-pr`, `pr-here`, `pr-worktree`, `vibe`, `guide`, `new-request`, `comment`, `case-ko`, `propose-run`).
- Des commandes de lecture, nouvelles, calculées d'après le relevé (`VibeView`) :
  - `status` : la branche, l'étape en cours, la note, la PR, ce qui court ;
  - `next` : les actions proposées, et pourquoi les autres sont grisées (`disabled`, déjà calculé par `journey` et `blockedBy`) ;
  - `actions` : pour chaque action, les arguments qu'elle lit vraiment (d'après son gabarit, `READ_BY`) ;
  - `runs` : les courses ;
  - `procs` : les processus du projet ;
  - `logs` : le journal d'un processus, son nom seul en argument ; la fin du journal, comme le relevé (`LOG_BYTES`, 32 Ko).
- Dans cette étape, la table déclare, elle n'exécute rien : aucune porte ne sert les lectures (pas de socket, pas de CLI), et ce qu'un agent peut faire aujourd'hui ne change pas (la boîte aux lettres refuse toujours un `.start` pour une action `DIRECT_ONLY`). L'ouverture réelle vient avec l'exécuteur (étape 2).
- La section des arguments des skills `actions` et `processus` est produite à partir de la table : un test régénère le texte et le compare au `SKILL.md` du dépôt, et échoue s'il a pris du retard. Rien n'est réécrit au démarrage (un skill retouché par l'utilisateur n'est jamais remplacé, I-35). Cela corrige le décalage actuel du skill `actions` : il cite `ask`, qui n'existe pas, et `guide`, `new-request`, `propose-run`, qui ne courent pas à part (un `.start` pour elles est refusé).
- I-39 change de nature (décidé, appliqué à l'étape 2) : la liste fermée des commandes git et gh et leurs arguments vérifiés restent (jamais `--force`, un rebase en échec annulé aussitôt…) ; « au clic de leur bouton » devient « par une commande du registre, d'où qu'elle vienne ». Pousser et publier une revue compris : c'est le principe de VibeCoder (en mode Vibe, l'agent pousse seul), et l'agent utilise le GitHub de la machine, comme l'écran. Ce qui protège, ce sont ces gardes, pas le clic (l'orchestrateur a déjà Bash, et pourrait taper `git push` lui-même).

## Ce que ça ne doit pas faire

- Changer le comportement actuel : la boîte aux lettres (`actions/<id>.start`, `.stop`, `run/<nom>.stop`, `.restart`) marche comme avant, mêmes refus, mêmes avis → variant suffit
- Toucher au pont (`src/preload/`, `src/shared/bridge/channels.ts`) ou à la page (`src/renderer/`) → structure
- Ouvrir à un agent une commande de la liste d'exceptions (répondre à une autorisation, accorder des droits, quitter ou redémarrer l'appli) → invariant
- Fermer une commande aux agents hors de la liste d'exceptions, ou sans sa raison → variant suffit
- Un id de robot de l'appli dans le contrat (argument ou réponse) → variant suffit
- Deux commandes du même nom → variant suffit
- Un argument sans schéma → variant suffit
- Un schéma de `run.start` qui ne correspond pas aux arguments que garde `parseRequest` (un de plus ou un de moins), ou un argument que ni `buildMessage` ni l'action ne lit → variant suffit
- Une réponse de lecture qui ne suit pas son schéma → variant suffit
- Une section d'arguments d'un skill qui diffère de ce que produit la table → variant suffit

## Ce que ça touche

- `resources/vibecoder/commands.json` : la table, à créer.
- `src/main/core/commands/` : son chargement, sa vérification et les lectures, à créer.
- `src/main/core/vibecoder/actions.ts` : `parseActions`, `buildMessage` (les arguments vérifiés, `READ_BY`), `DIRECT_ONLY`, `DIRECT_ACTIONS`.
- `src/main/core/vibecoder/runs.ts` : `ownRun`, `blockedBy`, `parseRequest` (les arguments gardés d'un `.start`, `KEEP`), `runsFile`.
- `src/main/core/vibecoder/journey.ts` : `vibeView` (étapes, actions proposées, `disabled`).
- `src/main/app/controllers/runs.ts` (`runOp`, `runRequests`), `processes.ts` (`processView`, `LOG_BYTES`, les demandes `run/<nom>.stop|.restart`) et `vibecoder.ts` (les arguments vérifiés des actions directes) : lus pour reprendre ce qui existe, inchangés.
- `resources/vibecoder/actions.fr.json`, `actions.en.json` : le catalogue.
- `resources/vibecoder/plugin/skills/actions/SKILL.md`, `processus/SKILL.md` : leur section des arguments, produite par la table.
- `SPEC.md` : la table et sa liste d'exceptions, F-115, le tableau des modules du principal ; et le README. Le texte d'I-39 change à l'étape 2, avec le comportement.

## Forme

**Du dedans vers le dehors, rien dans `app/` ni dans la page.** Deux petits
ajouts à `core/vibecoder` (ce qu'une action lit, ce que garde un `.start`),
puis le module pur `core/commands` en un seul commit (son barrel exporte
tous ses fichiers : séparés, les premiers commits ne compileraient pas) : le
schéma, la table, la donnée, les lectures, le texte des skills. Puis les deux skills
(leur section des arguments, comparée par un test), et la doc. Rien ne charge
la table à l'exécution dans cette étape : ses seuls lecteurs sont les tests
(l'exécuteur de l'étape 2 la chargera). La cible d'une commande (le dossier
du dépôt, son chemin réel) n'est dans les arguments d'aucune : elle est dite
une fois, en tête de la table (`target`), et portée par l'enveloppe des portes
(étapes 2 et 3). Les tests des invariants (une commande de la liste
d'exceptions ouverte aux agents) partent avec le premier commit (note, forme,
invariants).

## Pistes pour plus tard

- Étape 2 : l'exécuteur, une seule entrée pour toutes les portes, une réponse immédiate `{ok, result | error}` ; il ouvre aux agents ce que la table leur ouvre (dont les actions `DIRECT_ONLY`), réécrit I-39, et ajoute `verdict` à `run.start`.
- Étape 3 : la porte, un socket local et la CLI `vibecoder`, qui exposent les lectures ; les jetons qui distinguent un agent d'une interface, pour appliquer la liste d'exceptions.
- La couverture (étape du guide) : les réglages, la gestion des robots, la confiance à un projet, quitter et redémarrer deviennent des commandes ; ceux de la liste d'exceptions fermés aux agents.
- Le moteur autonome (étape 7) : il lit `commands.json` ; le rangement des données par projet et par branche ; un essai jetable de `claude -p` en `stream-json`, avec les autorisations par un outil MCP, avant d'en dépendre en Rust.
