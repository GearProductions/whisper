# 0.13.0 — Les agents de code sur Sonnet, un modèle fixé pour chaque course

## Ce que ça fait

- Les sous-agents qui écrivent un module (`vibecoder:developpeur`, lancés par
  *Générer les modules restants*) travaillent sur Sonnet · élevé, plus sur Opus ·
  élevé (surdimensionné pour écrire un module dont la Forme pose déjà le
  contrat).
- *Générer ce module* (`module`) passe aussi sur Sonnet · élevé : tous les agents de
  code travaillent sur Sonnet, Opus reste au choix sur le bouton (F-99).
- L'orchestrateur de `modules` tourne sur Opus · élevé et relit chaque diff
  en entier (les quatre questions du §5.1). Un petit défaut, il le corrige
  lui-même ; sinon il renvoie la correction précise au même sous-agent Sonnet
  (`SendMessage` : celui-ci garde son contexte, rien à relire). Au second
  échec seulement, il relance le module sur Opus (le paramètre `model` de
  l'appel `Agent`, qui prime sur l'en-tête de `developpeur`).
- Un sous-agent lance le typecheck et seulement les tests de son module (ses
  invariants et ses variants) ; la suite complète tournait une fois par vague,
  lancée par l'orchestrateur : ce n'est plus la règle, voir
  `docs/tickets/fix/0.13.0-fix-and-improvements.md` (sujet 2).
  `module/SKILL.md` et `developpeur.md` disent la
  même chose (aujourd'hui l'un demande toute la suite, l'autre les tests du
  module).
- Le prompt de chaque sous-agent porte ce qu'il doit savoir du ticket : l'entrée
  de Forme du module, ses lignes « ne doit pas » et les chemins de ses
  invariants. Il lit toujours `AGENTS.md` ; il ne relit pas le skill
  `ponytail`, déjà préchargé (aujourd'hui lu deux fois).
- Une course (F-115) prend le modèle et l'effort de l'en-tête de son skill,
  qu'il tourne en sous-contexte ou non (aujourd'hui `forkedModel` exige
  `context: fork`, sinon c'est le modèle de l'agent). Le bouton dit qui
  travaille et propose les autres modèles (F-99, F-106) pour ces skills aussi.
- Fixent ainsi leur modèle : `modules` (l'orchestrateur) sur Opus · élevé ;
  `module`, `rc` et `release` sur Sonnet ; *Appliquer la revue* sur Sonnet.
- *Rédiger la note*, *Poser la forme* et *Envoyer les réponses* gardent le
  modèle de l'agent (la pastille *✦ Fable · élevé* de ces étapes, F-109 ;
  *Envoyer les réponses* reprend la session de la note : en changer le modèle
  en perdrait le cache).
- *Relire le diff* (`relire`) reste sur Opus · élevé.
- *Valider → commit → suivant* (`suivant`) commite sur Sonnet, dans une
  course comme *Commiter ce module* (`commiter-modules`), puis génère le module
  suivant dans une seconde course, au modèle de *Générer ce module*, donc sur
  Sonnet (aujourd'hui le tout sur Opus · élevé).
- On mesure le coût d'un ticket en *Vibe* avant et après ce ticket (journaux
  de session). Le double contexte d'une course reste : mesuré, le processus
  d'une course dont le skill a `context: fork` n'appelle aucun modèle, tout
  passe par le sous-contexte ; il ne coûte rien.
- Le README dit comment mettre l'orchestrateur *Vibe* sur Sonnet : il tourne
  dans la conversation de l'agent, passer l'agent sur Sonnet avant *Vibe* le
  fait déjà, sans code.

## Ce que ça ne doit pas faire

- Faire travailler Fable de lui-même : un en-tête, le `model` qu'un skill
  passe à un sous-agent restent `haiku`, `sonnet` ou `opus` → invariant
  (existant, I-36, `fable.test.ts`)
- Une variante générée sur un autre modèle que `haiku`, `sonnet` ou `opus`,
  y compris pour un skill sans `context: fork` → variant suffit (existant,
  `tests/variants/defaults.test.ts`, qui parcourt les skills livrés : les
  variantes ne prennent leur modèle que dans `SKILL_MODELS`, ce ticket n'y
  change rien)
- Donner `context: fork` à la variante d'un skill qui tourne sans
  sous-contexte (`modules` lance des sous-agents : en sous-contexte, il ne le
  pourrait plus) → variant suffit
- Ignorer le modèle de l'agent pour *Rédiger la note*, *Poser la forme* et
  *Envoyer les réponses*, ou retirer la pastille *✦ Fable · élevé* → variant
  suffit
- Changer le modèle d'une conversation en cours : `vibe`, `processus`,
  `actions`, *Demander sans modifier*, *Où j'en suis ?* restent au modèle de
  l'agent (cache) → vu en review
- Générer le module suivant quand le commit de *Valider → commit → suivant*
  échoue (un hook) → vu en review (seul le texte de `suivant` le dit)
- Finir une vague de `modules` sans la suite complète des tests → vu en review
  (remplacé : une suite par vague n'est plus la règle, voir
  `docs/tickets/fix/0.13.0-fix-and-improvements.md`)
- Alléger le prompt d'un sous-agent au point qu'il ignore une règle
  d'`AGENTS.md` ou un fichier protégé → vu en review
- Changer le modèle des skills qui demandent du jugement (`invariants`,
  `aligner`, `ponytail`, `relire`, `relire-note`, `relire-commits` restent sur Opus ·
  élevé) ou de ceux déjà sur Haiku → vu en review

## Où ça casse

- Une vague lance autant de sous-agents que de modules indépendants ;
  aujourd'hui chacun lance toute la suite en même temps sur le même dépôt
  (`/tmp`, cf. `0.13.0-tests-remplissent-tmp.md`).

## Forme

**Un modèle par skill, avec ou sans sous-contexte.** `forkedModel` devient
`skillModel` : le `model` de l'en-tête s'il est l'un de `SKILL_MODELS`, que le
skill ait `context: fork` ou non. Une course le prend (`startRun`), le relevé
propose les autres (F-99, F-106) — pour une action qui court, ou dont le skill
a `context: fork` (*Nouvelle demande*, *Charger la PR*, *Proposer les
commandes* gardent leur choix) : un skill sans sous-contexte envoyé à la
conversation (`vibe`…) garde le modèle de l'agent. Les variantes recopient `context: fork` seulement si le
skill l'a (`modules--sonnet` lance encore ses sous-agents).

**Appliquer la revue : un skill.** Le texte de `apply` passe dans un skill
neuf, `appliquer-revue` (comme `publier-revue`), sur Sonnet, sans sous-contexte ;
le gabarit devient `/vibecoder:appliquer-revue {{lang}} {{out}} {{text}}`. Rien
de neuf dans le code : son modèle, son « qui travaille », ses variantes et le
choix au bouton viennent du chemin des skills.

**Valider → commit → suivant : deux courses, par une demande.** `suivant`
(Sonnet) commite comme `commiter-modules`, puis, le commit fait, écrit
`<out>/actions/module.start` vide (le premier module qu'aucun commit ne
touche, `targetModule`) au lieu de générer lui-même. La demande attend la fin
de `next` (les deux modifient la branche : `blockedBy`, « en attente »), puis
`module` part dans sa course, au modèle de *Générer ce module*. Un hook qui
échoue : `suivant` s'arrête sans écrire la demande. Rien de neuf dans le code :
les demandes de l'orchestrateur (`runRequests`) sont lues hors du mode Vibe,
seul `halted` les refuse.

**La mesure : une procédure dans le README, sans dépendance.** Les journaux de
Claude Code (`~/.claude/projects/<dossier>/<session>.jsonl`, et
`<session>/subagents/*.jsonl` pour un sous-agent ou un `context: fork`) : la
somme de `message.usage` (entrée, cache écrit, cache lu, sortie) par
`message.model`, sur les sessions du ticket, par un `node -e` de quelques
lignes. Mesurée sur un ticket fait en *Vibe* avant ce ticket et sur le
suivant ; les chiffres dans cette note.

Avant, mesuré sur ce ticket même (*Générer les modules restants* tournait
encore sur l'ancien skill : 18 modules, 11 par des sous-agents Opus · élevé,
7 par l'orchestrateur), en jetons :

| `modules` | cache écrit | cache lu | sortie |
|---|---|---|---|
| orchestrateur, Opus | 110 328 | 3 693 323 | 25 055 |
| sous-agents, Opus | 463 692 | 3 071 384 | 50 391 |

Après : le prochain ticket fait en *Vibe*. Le double contexte : les sessions
des courses en `context: fork` (`commit-preparer`, `commit`, `verifier`,
`ponytail`…) n'ont aucun appel au modèle, seulement leurs `subagents/`.
