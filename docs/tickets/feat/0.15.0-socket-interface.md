# 0.15.0 — Le socket TCP, et l'interface qui passe par lui

Étape 3a du plan « VibeCoder pilotable par agents » (artefact `actions/pilotage-par-agents.html`, « Le plan », étape 3 ; guide « Logiciel pilotable par agents », brique 3). Les étapes 1 (le registre, note `0.15.0-registre-commandes.md`, PR #80) et 2 (l'exécuteur, note `0.15.0-executeur.md`, PR #81) sont fusionnées. L'étape 3b, la CLI, vient après.

## Ce que ça fait

- **Le moteur public** (décidé) : la table des commandes est le contrat public du moteur, pas la liste de tout ce que fait l'interface. Une fonction y entre si le moteur possède quelque chose qu'un client ne fait pas aussi bien lui-même : un état (les courses, les processus, le relevé), une règle de coordination (une seule écriture à la fois, pas de changement de branche pendant une action), une garde (jamais `--force`, un rebase en échec annulé). Le contrat reste petit, donc stable, documentable et portable en Rust. Un agent peut tout faire : par une commande du moteur, ou avec ses propres outils quand le moteur n'apporte rien de plus.
  - Dans le contrat : les actions du parcours, les courses (arrêter, garder, annuler, répondre à une autorisation), les actions git et gh, les processus, les lectures, la gestion des artefacts (où ils sont, les lire, en ajouter, les renommer, créer un fichier ou un dossier, les déplacer, les coller, les dupliquer, les mettre à la corbeille, en copier un dans le projet), et le brouillon de revue (ci-dessous).
  - Fonctions de l'interface, hors du contrat, en appel direct comme aujourd'hui : *Commenter* et *À revoir* (des gestes de la page, qui remplissent le champ) ; modifier le code ou la note dans le panneau (un éditeur) ; ouvrir dans l'éditeur, un lien, un fichier (le système) ; la dictée et la lecture à voix haute (l'appareil) ; les réglages de l'interface (thème, micro…).
  - La table perd donc `comment` et `case-ko`. Elle garde toute la gestion des artefacts (décidé : une IA, surtout un agent cloud sans accès au disque, ne peut gérer le dossier d'artefacts que par ces commandes ; elles portent aussi leurs gardes : rester dans le dossier, ne jamais écraser, la corbeille plutôt qu'un effacement), et gagne deux lectures : `artifacts`, le dossier des artefacts du projet (son chemin réel : seul le moteur connaît la clé du projet) et la liste de ses fichiers ; et la lecture du contenu d'un artefact (une taille maximale), pour un client qui n'a pas accès au disque.
  - **Le brouillon de revue** entre dans le contrat (décidé) : un état que le moteur garde pour chaque PR jusqu'à *Publier la revue* (déjà dans le contrat), que l'agent principal peut préparer à la demande (« ajoute une remarque sur cette fonction : elle ne gère pas le cas vide »). Quatre commandes, ouvertes aux agents : lire le brouillon (les remarques de la PR chargée), ajouter une remarque (sa cible, son texte), en modifier une, en retirer une, par son id. Elles reprennent ce qui existe (`addComment`, `editComment`, `removeComment`, `core/vibecoder/marks`). Aucun numéro de PR en argument : c'est la PR chargée au relevé, comme pour *S'assigner la PR* (un agent n'écrit jamais dans le brouillon d'une autre PR) ; sans PR chargée, la commande est refusée. À ne pas confondre avec *Commenter*, le geste de la page qui remplit le champ, qui reste hors du contrat.
- Le principal ouvre un socket TCP au lancement : sur `127.0.0.1` seulement, sur un port libre, un objet JSON par ligne.
- L'enveloppe est celle de Gear Render : `{ cmd, args, token }` en entrée, plus le dossier visé (la table : « the target … carried by the door's envelope, never an argument ») ; en sortie, la réponse de l'exécuteur (`runCommand`), `{ ok: true, result }` ou `{ ok: false, error }`. (TCP plutôt qu'un socket Unix : le même protocole que les autres applis Gear, pour qu'un agent puisse un jour en piloter plusieurs.)
- Un jeton aléatoire, tiré à chaque lancement. Une commande sans le bon jeton est refusée.
- Une ligne qui n'est pas une commande ferme la connexion (cela bloque les requêtes d'un navigateur vers `localhost`).
- Le fichier de découverte `live.json`, dans `~/.config/whisper-dictation/`, porte dès ce ticket le port seul, sans le jeton (décidé : le jeton de l'écran ouvre la porte « écran », qui répond aux autorisations ; un agent qui lirait le fichier pourrait répondre lui-même à ses demandes ; le jeton viendra avec la CLI) ; il est supprimé à la sortie (le plan, I-43). La version de dev et l'AppImage, qui ne tournent pas en même temps, s'y retrouvent.
- L'interface passe par lui : les commandes de mes boutons qui sont dans le contrat partent du principal, client de son propre socket, vers l'exécuteur (`runCommand`, porte « écran »). (But : l'interface est déjà un client TCP le jour où le moteur sortira de l'appli, et mes clics de tous les jours éprouvent le protocole.) Ce sont :
  - lancer une action, l'arrêter, la garder, l'annuler ;
  - répondre à une demande d'autorisation d'une course : *Autoriser*, *Toujours*, *Refuser* (`run.allow`, `run.always`, `run.deny`, fermées aux agents ; décidé : par le socket comme les autres boutons, c'est ce qui éprouve pour de vrai la règle « jamais par un agent ») ;
  - les actions directes ;
  - *Copier dans le projet* un artefact (`copy-artifact`) ;
  - les gestes de l'explorateur des artefacts : renommer, nouveau fichier, nouveau dossier, déplacer, coller, dupliquer, corbeille ;
  - le brouillon de revue : ajouter, modifier, retirer une remarque (le canal `conv:vibeDraft`, `draftVibe`, en devient l'adaptateur) ;
  - *Déposer* des fichiers sur le panneau des artefacts : `add-artifact` reçoit, pour chaque fichier, soit son chemin (un client de la machine : la page, un agent local), soit son nom et son contenu encodé (base64, une taille maximale par fichier et par demande), pour un client qui n'a pas accès au disque (décidé : un agent cloud doit pouvoir dire « ajoute-moi ça à mes artefacts ») ; le nom reste un nom de fichier sûr, le dossier d'arrivée reste dans les artefacts, jamais rien d'écrasé ;
  - les processus : *Lancer*, *Arrêter*, *Relancer* (`proc.start`, ajouté à la table et ouvert aux agents comme `proc.restart` ; `proc.stop`, `proc.restart`) ; voir le journal, modifier la liste des commandes du projet et préparer le worktree restent des appels directs pour l'instant.
- Les pièces jointes du champ (images, fichiers, texte sélectionné) entrent dans le schéma des commandes dont le gabarit les lit, ouvertes aussi aux agents.
  - Sur le fil, les images sont en base64 et une ligne tient 128 Mio de caractères (`LINE_MAX`) : l'écran borne donc le total des images d'une action à 64 Mio décodés (~85 Mio de caractères, de la marge pour le texte, la sélection et le JSON), avant l'envoi. Au-delà : un vrai refus de l'écran, « Pièces jointes trop lourdes (64 Mio d'images au plus) » (fr et en), jamais « socket indisponible » (décidé après la revue : avant le socket, vingt images de 50 Mio partaient ; la limite de `prepareMessage` par image, 50 Mio, ne change pas). Un client du socket qui dépasse la ligne voit sa connexion fermée.
- Le dossier visé : mes boutons envoient le dossier du robot affiché (la règle quand plusieurs robots sont sur le même dossier se décide au ticket de la CLI, quand d'autres que moi pourront envoyer des commandes).
- Avant chaque commande qui modifie quelque chose, l'état du dépôt est relu exprès (`refreshVibe({ fresh: true })`) : l'exécuteur ne juge pas sur un relevé qui date.
- Le socket écoute dès le lancement, l'écran en dépend ; l'accès des agents extérieurs, et son réglage, viennent avec la CLI (3b).
- Le socket ne démarre pas (aucun port, une erreur) : mes boutons refusent avec un message « socket indisponible », l'appli reste ouverte (décidé : je vois tout de suite le problème, c'est le but d'éprouver le TCP ; pas de repli direct sur l'exécuteur).
- Le pont entre la page et le principal ne change pas : la page ne parle pas TCP et ne détient jamais le jeton (le pont reste la frontière de sécurité). Les gestionnaires des canaux d'aujourd'hui (`runVibeAction`, `vibeRunOp`, `vibeProcess`, `dropOnArtifacts`) deviennent les adaptateurs de l'écran : ce qui est propre à l'écran y reste, avant l'envoi :
  - la boîte de dialogue d'un processus qui tourne ailleurs (`processAction`) ;
  - le choix « direct » ou « via l'agent » (`direct: true`) ;
  - les fichiers déposés sur le panneau, dont la page lit les chemins.
- L'adaptateur traduit la réponse en ce que l'écran montre aujourd'hui : l'erreur, d'après son code, dans la langue de l'appli (`ERRORS`, `blockedBy`, `requestNotice` : décidé à l'étape 2).
- Les fonctions de l'interface (voir « Le moteur public ») gardent leur appel direct ; leur comportement ne change pas.
- L'affichage ne change pas : le relevé poussé à la page toutes les 4 s, les fils, les autorisations restent comme aujourd'hui (un flux d'évènements par le socket, plus tard, quand le moteur sortira).
- L'agent principal ne change pas : sa boîte aux lettres (`actions/<id>.start`, `.stop`, `run/<nom>.stop`, `.restart`) reste telle quelle. Il passe directement à la CLI à l'étape 3b (décidé : la boîte aux lettres ne passe pas par l'exécuteur entre-temps, contrairement aux pistes de la note de l'exécuteur).

- Les formes directes de *✓ Commiter*, *Publier la revue* et *PR mergée → revenir sur la base* entrent aussi dans la table (décidé, après la génération : ce sont des actions git et gh, donc du contrat, et sinon trois boutons garderaient un second chemin) : trois commandes nommées de leur id, comme les autres actions directes (`commit`, `publish` avec son verdict, `base`), ouvertes aux agents ; leurs boutons directs passent par le socket. Leurs formes « via l'agent » restent `run.start`.
- Les tests d'invariants protégés qui cliquent les vrais boutons (`src/main/app/controllers/tests/invariants/` : action-fable, artifact-moves, artifact-ops, artifacts, commands-guards, family-commands, module-code, note-and-tests-save, page-text, place-switch, pr-place, reviewer, run-last-turn, runs, stash ; et `core/commands/tests/invariants/execute-closed.test.ts`) adaptent leur seul harnais (décidé : c'est une refonte, les boutons passent par le socket, les tests doivent l'ouvrir comme l'appli le fait au lancement) : ouvrir le vrai socket avant, le fermer après, attendre une réponse devenue une promesse, les deux opérations factices nouvelles (`artifact`, `draft`) ; aucune assertion changée.
- Une seule assertion protégée change (décidé) : dans `src/main/technicals/direct/tests/invariants/direct.test.ts`, le cas qui vérifie que les actions directes (pull, pousser, commiter…) ne sont lancées que par `runVibeAction`, sur un clic « direct », devient « les actions directes ne sont lancées que par l'exécuteur (une commande de la table), jamais au relevé » : les boutons passant par le socket, c'est l'exécuteur (`controllers/commands`) qui les lance. Les autres gardes du fichier (la liste fermée des commandes git et gh, `runDirect` seul à appeler le lanceur, jamais au relevé) restent telles quelles.

## Ce que ça ne doit pas faire

- Une fonction de l'interface (un geste de la page, de l'éditeur, du système, de l'appareil) dans la table, ou une commande du contrat que mes boutons appellent sans passer par le socket → variant suffit
- Écouter ailleurs que sur `127.0.0.1` → invariant
- Accepter une commande sans le bon jeton → invariant
- Garder ouverte une connexion qui a reçu une ligne qui n'est pas une commande → invariant
- Donner le jeton à la page (par un canal, un relevé, un message) → invariant
- Écrire le jeton sur le disque (`live.json` compris) → invariant
- Laisser `live.json` après la sortie de l'appli → invariant (I-43)
- Ouvrir à un agent une commande fermée (`run.allow`, `run.always`, `run.deny`), par quelque porte que ce soit → invariant (celui de l'exécuteur, existant)
- Copier un fichier déposé autrement qu'aujourd'hui : jamais écraser, un lien jamais suivi (`technicals/file-tree`) → invariant (existant)
- Toucher au pont (`src/preload/`, `src/shared/bridge/channels.ts`) ou à la page (`src/renderer/`) → structure
- Changer ce que font mes boutons : mêmes refus, mêmes textes, mêmes résultats, mêmes boîtes de dialogue → variant suffit
- Un bouton qui passe outre le socket quand il est indisponible, au lieu de refuser → variant suffit
- Une commande qui modifie, jugée sans relire l'état du dépôt → variant suffit
- Changer l'affichage (le relevé toutes les 4 s, les fils, les autorisations) → vu en review
- Changer la boîte aux lettres de l'agent principal → variant suffit
- Mettre de la logique métier dans le socket ou dans les adaptateurs (les gardes restent dans l'exécuteur et ce qu'il appelle) → vu en review

## Forme

**Le banc d'abord, puis du dedans vers le dehors.** Le scénario de
`test:main-diff` est étendu en premier : vert contre `master` dès le premier
commit, il doit le rester à chaque commit (mes boutons font la même chose
qu'avant). Puis le pur : la table, ses lectures, le tri des fichiers déposés,
le protocole d'une ligne. Puis `technicals/` : écrire un fichier sans écraser,
le serveur et le client TCP, qui ne connaissent que `node:net`, `node:crypto`
et le protocole ; le jeton naît dans le serveur, reste en mémoire dans le
contrôleur du socket, ne va ni sur le disque ni vers la page. Puis `app/` :
`live.json`, l'ouverture et l'envoi (le contrôleur du socket), les opérations
nouvelles (ajouter un contenu, lire un artefact, le brouillon, lancer un
processus) et les adaptateurs de l'écran. L'exécuteur (`execute`) et
`runCommand` viennent ensuite, ensemble, pour que chaque commit compile (ses
`CommandOps` nouvelles exigent les opérations d'`app/`) ; enfin le
branchement au lancement, le skill `actions`, la doc.

**L'écran par le socket.** Un adaptateur envoie au socket la commande du
contrat, la cible = le chemin réel du dossier du robot affiché ; le serveur
rend l'enveloppe, `commandFromSocket` retrouve le robot (le robot affiché s'il
est sur ce dossier, sinon le premier robot de ce dossier, chemins réels
comparés : `/home` et `/var/home`) et appelle `runCommand` porte « écran ».
Une connexion par commande. Avant une commande `write`, `runCommand` relit
l'état (`refreshVibe({ fresh: true })`). Les canaux du pont restent ; ceux qui
ne rendent rien à la page (`conv:vibeRunOp`, `conv:vibeProcess`,
`conv:vibeDraft`) restent muets sur un refus, comme aujourd'hui ; socket
indisponible : une boîte de message du principal (le pont ne change pas).
Les tests des invariants (127.0.0.1, le jeton, la connexion fermée, le jeton
ni vers la page ni sur le disque, `live.json` supprimé à la sortie) partent
avec le premier commit (note, forme, invariants).

## Pistes pour plus tard

- Étape 3b, la CLI : `vibecoder status|next|run …|proc …`, `run wait`, la suppression de la boîte aux lettres (l'agent principal passe à la CLI), l'accès des agents extérieurs (désactivé par défaut, un réglage), un jeton par agent qui dit qui appelle et sa porte, et le jeton des agents dans `live.json`. À trancher alors : le robot visé quand plusieurs robots sont sur le même dossier ; un relevé ancien pour un robot qui n'est pas affiché. Les points laissés par la note de l'exécuteur y restent (`load-pr`, `pr-here`, `pr-worktree` demandées par un agent ; l'échec d'une action directe appris par un agent ; « L'agent travaille » à la porte agent ; la réécriture des invariants qui disent le contraire de l'ouverture ; I-39 dans `SPEC.md`).
- Les validations (✓ de la note, des cas d'invariants, du plan de test) : un état que le parcours utilise et qu'une interface tierce voudra ; dans le contrat, mais une question reste : un agent peut-il valider son propre travail (le mode Vibe le fait déjà) ?
- Les réglages du moteur (le modèle et l'effort par action, les commandes du projet) dans le contrat ; ceux de l'interface non ; ceux qui accordent des droits fermés aux agents.
- Un flux d'évènements par le socket (relevé, fils, autorisations), quand le moteur sortira de l'appli.
- Le mode `--headless` : pas au plan pour l'instant.
- Un agent cloud joint VibeCoder : le socket n'écoute que sur 127.0.0.1, il faudra un relais sur la machine (un serveur MCP local auquel l'agent est connecté, ou un tunnel sécurisé), après la CLI et MCP. Le contenu encodé d'`add-artifact` le prépare dès ce ticket.
- Une convention de découverte commune aux applis Gear (un dossier où chaque appli ouverte dépose son `live.json`), pour qu'un agent pilote plusieurs applis à la fois.
