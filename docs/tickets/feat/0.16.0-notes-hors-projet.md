# 0.16.0 — Les notes hors du projet

Branche `feat/0.16.0-notes-hors-projet`.

## Ce que ça fait

- Des projets Gear deviennent publics, ou codent en anglais : une note de ticket en français n'a pas sa place dans leur dépôt. La note reste `docs/tickets/<type>/<ticket>-<slug>.md`, mais un projet peut l'exclure de git, à la main (`docs/tickets/` dans `.git/info/exclude`, partagé par le dépôt et ses worktrees : rien n'est écrit dans le dépôt). Une note ignorée par git est une note hors du projet : jamais commitée, jamais attendue dans un commit. Il n'y a ni case ni réglage : git dit si la note est ignorée. Le prix : la note vit dans la copie de travail, et retirer le worktree de la branche l'efface (décision de l'utilisateur : d'abord cette version simple ; la note rangée dans le dossier d'artefacts, avec une case par projet, plus tard si besoin).
- Le README dit comment exclure les notes d'un projet (la ligne à ajouter à `.git/info/exclude`).
- VibeCoder retrouve la note d'une branche par le nom de la branche, sur le disque, et plus seulement parmi les fichiers que git dit changés (aujourd'hui `findNote` ne cherche que là : une note dans un `docs/tickets/` ignoré par git est invisible). Deux cas : la note que git voit (commitée ou modifiée), et la note dans `docs/tickets/` ignoré par git. Parmi les notes ignorées, seule compte celle nommée exactement comme la branche : git ne retire jamais un fichier ignoré au changement de branche, et les notes des branches passées restent sur le disque (décision de l'utilisateur). Une branche sans ticket ni version trouve sa note par son nom exact, sans son type (`feat/teams-admins` → `teams-admins.md`), dans tous les projets, ignorés ou non ; un agent qui suit une PR dans un worktree sur une branche locale `pr-<n>` la cherche d'après la branche de la PR (décisions de l'utilisateur, après son essai sur Gear Authenticator et gt-plugins).
- Note hors du projet (ignorée par git) : aucun skill ne la commite ; le premier commit de la branche ne garde que les squelettes de la Forme et les tests d'invariants rouges ; la PR ne pointe pas vers elle. Le parcours suit la note trouvée : ignorée par git, il n'attend aucun commit d'elle, et le plus ancien commit de la branche tient lieu du commit de la note (celui des squelettes, qui n'est pas un module fait, et des tests de l'étape Invariants).
- Relecture d'une PR sans note : le relecteur n'a pas la note (elle est restée chez l'auteur). Si son propre dépôt ignore `docs/tickets/`, l'écran dit simplement qu'il n'y a pas de note, et la relecture de la note est sautée, sans reproche ; sinon, le reproche d'aujourd'hui reste.
- Hors de ce ticket : la langue des notes.

## Ce que ça ne doit pas faire

- Changer quoi que ce soit pour un projet qui n'ignore pas `docs/tickets/` : la note commitée, retrouvée comme aujourd'hui → variant suffit
- Commiter ou pousser une note ignorée par git (même en forçant), la recopier ailleurs dans le dépôt, la citer dans la PR (ni lien ni chemin) → vu en review
- Laisser le parcours attendre un commit de la note quand elle est ignorée par git : la note commitée n'est plus le signe du premier commit (le commit de la note, la case « note commitée » de la liste de l'étape PR) → variant suffit

## Ce que ça touche

- `src/main/core/vibecoder/note.ts` : `findNote` (parmi les fichiers changés, sous `docs/tickets/`, la clé ou le nom de la branche) ; `noteKey` ; savoir si la note est ignorée par git (`git check-ignore`, `src/main/technicals/git`).
- `src/main/app/controllers/vibecoder.ts` : le relevé (`findNote(repo.changed, …)`, la note lue par `diskOf`, relative au dossier de l'agent).
- `src/main/core/vibecoder/journey.ts` : `noteCommit`, `noteChanged`, la case « note commitée » (`a3`), les tests d'invariants de l'étape (`stepTests`) : tous supposent la note dans les commits ou dans les fichiers modifiés de la branche.
- `src/main/core/vibecoder/step-checks.ts`, `marks.ts`, `note-ref.ts`, `files.ts` : la note par son chemin.
- `src/main/core/vibecoder/actions.ts` : la variable `{{note}}` existe déjà (le chemin de la note, refusée sans note) ; `resources/vibecoder/actions.fr.json`, `actions.en.json` : les gabarits des skills, aucun ne la passe aujourd'hui ; `resources/vibecoder/README.md` (la table des variables).
- `src/main/core/commands/reads.ts` : `note`, relatif au dossier de l'agent.
- Les skills qui citent `docs/tickets/` (`resources/vibecoder/plugin/skills/`) : `note`, `nouvelle-demande`, `conception`, `forme`, `invariants`, `lire-invariants`, `aligner`, `commit-preparer`, `commiter-modules`, `modules`, `relire`, `relire-note`, `relire-commits`, `ponytail` ; l'agent `developpeur` ; et `vibe`, `pr` (le premier commit « note, forme, invariants rouges », la PR).
- La relecture sans note : `resources/vibecoder/plugin/skills/relire-note/SKILL.md` (aujourd'hui, sans note, il s'arrête sur « une fonctionnalité sans sa note ») ; `journey.ts` (le relecteur).
- `SPEC.md`, `README.md`.

## Forme

**Du pur vers le dehors.** La note retrouvée (pur), la lecture des fichiers
ignorés (git), le parcours (pur), le relevé qui les relie, puis les skills, la
doc.

**Ignorée, pas cachée.** Git dit seul si la note est hors du projet : `status
--ignored` liste les fichiers de `docs/tickets/` qu'il ignore (sur le disque,
jamais dans `changed`). `status` est déjà dans `GIT_READ` : la liste des
sous-commandes, que fige un invariant protégé, ne change pas (pas de
`check-ignore`). Les skills, eux, demandent `git check-ignore -q <note>`.

**Le commit de la note.** Ignorée, le plus ancien commit de la branche en tient
lieu (les squelettes et les tests rouges de l'étape Invariants) ; la case
« note commitée » de l'étape PR suit ce premier commit.

**Ce qui reste.** `findNote`, `step-checks`, `marks`, `note-ref`, `files`,
`reads` : la note par son chemin, ignorée ou pas, sans changement. Les
gabarits des actions ne passent toujours pas `{{note}}` : chaque skill
retrouve la note lui-même, par le nom de la branche d'abord.
