# 0.15.0 — Des boutons sans modèle, le code d'un seul invariant, des validations qui suivent les modifications

Branche `feat/0.15.0-ecran-statuts`, créée depuis `master`. À livrer avant la release candidate 0.15.0.

## Ce que ça fait

**Plus de modèle sur les boutons d'action.** Un bouton d'action affiche aujourd'hui son libellé suivi de qui le fait (le modèle, « Sonnet », « Opus »…) ; le petit bouton « via » aussi. Le modèle ne s'y affiche plus : il se règle dans les paramètres, où on le retrouve vite. Il passe dans l'infobulle du bouton, sous son explication (« — Sonnet »).
- La marque « direct » (l'appli fait l'action elle-même, sans agent) reste sur le bouton : elle dit ce qui va se passer, pas un réglage.
- « via » reste, seul, sans le modèle ; son infobulle le donne.
- Le reste du bouton ne change pas (la raison d'un bouton grisé, « en cours » et ⏹).

**Le code d'un invariant : son bloc seul.** À l'étape Invariants, ouvrir le code d'un cas montre aujourd'hui le fichier de test entier, défilé jusqu'au cas : on s'y perd, et le défilement se mêle à celui de l'écran. Désormais, l'éditeur d'un cas ne montre que le bloc de ce test, comme sa lecture en pseudo-code ne montre que lui.
- Le bloc reste modifiable : enregistré, il remplace ce bloc dans le fichier, le reste du fichier intact.
- Le fichier entier reste accessible par *Ouvrir* (l'éditeur de code de l'utilisateur), comme aujourd'hui.

**Une étape modifiée perd sa coche, et celles qui suivent aussi.** Aujourd'hui, quand on corrige en cours de course (après avoir testé les modules, à la main ou par un agent), on devient aveugle : rien ne dit quelle étape ne tient plus, ni ce qui a changé. Pour la note, c'est réglé : *Vu* fixe une référence, et toute modification se voit. Désormais, toute la course fonctionne ainsi.
- Une validation par étape, le même geste partout : *Valider la note*, *Valider la forme*, *Valider les invariants* (offert quand tous les cas ont leur ✓, ou ✓ Rien à écrire ; les cas gardent leurs verdicts) et *Valider les modules* (nouveau). *Commiter les modules* n'est disponible qu'une fois les modules validés.
- Valider retient ce que l'étape a validé : la note, sa conception (« Ce que ça fait », « Ce que ça ne doit pas faire », et les sections de conception qui suivent, hors la section Forme) ; la Forme, la section Forme de la note ; les invariants, les fichiers de test ; les modules, tout ce que la branche change d'après git, hors la note et les tests d'invariants (décision de l'utilisateur : on suit git, la doc comprise, pour que le développeur revoie chaque modification ; en Vibe, l'agent revalide seul). Elle retient aussi le texte de chaque fichier de l'étape, pour le diff « Depuis la validation ». Tout est gardé dans le dossier de sorties de l'appli ; rien n'est écrit dans le dépôt ni sous `.git/`.
- Quand ce qu'une étape a validé change, par qui que ce soit, l'étape perd sa coche. Son en-tête dit « modifiée depuis la validation » ; un clic dessus passe le menu de diff de la vue IDE sur *Depuis la validation*.
- Une modification de la seule section Forme de la note ne décoche pas la note (elle décoche la Forme).
- La cascade : une étape décochée décoche celles qui suivent (note → Forme → Invariants → Modules) ; leur en-tête dit pourquoi, « à revoir : la note a changé » (la première étape décochée). Revalider une étape ne recoche pas les suivantes : chacune se revalide, puisqu'elle ne tient peut-être plus.
- Un commit ne change pas une validation.
- Le fil d'Ariane suit les validations (décision de l'utilisateur, qui remplace « le ✓ du fil reste celui du parcours ») : pour la note, la Forme, les invariants et les modules, vert si l'étape est validée et rien n'a changé depuis, jaune (la couleur d'attention) si du contenu validé a été modifié depuis ou est à revoir en cascade, gris si elle n'a jamais été validée ; l'infobulle le dit. Le parcours (l'étape en cours, la prochaine action) ne change pas.
- Une étape dont celle d'avant n'est pas validée l'attend (décision de l'utilisateur) : son *Valider* (ou *Revalider*) est grisé, avec « En attente : valider d'abord l'étape … » à côté et dans l'infobulle du fil d'Ariane.

**Le menu de diff porte sur toute la vue IDE.** Aux étapes Forme, Invariants et Modules, le choix de la référence du diff vaut pour toute la vue IDE, plus pour le seul fichier affiché. L'arborescence ne liste que les fichiers qui diffèrent de cette référence :
- *Depuis la base de la branche*, par défaut : tous les fichiers de l'étape, comme aujourd'hui, plus tout ce que git dit changé depuis la base (suppressions comprises) ;
- *Depuis le dernier commit* : les fichiers qui diffèrent du dernier commit, tous ceux du git status, de l'étape ou non ; grisé tant que la branche n'a aucun commit (décision de l'utilisateur : le dernier commit est alors la base), ou que rien ne diffère du dernier commit (idem : l'utilisateur voit ainsi s'il y a quelque chose à relire) ;
- Les listes suivent git, sans autre règle (décision de l'utilisateur) : un fichier supprimé, ou hors des chemins de la Forme, apparaît comme dans `git status`. Un fichier que la Forme ne nomme nulle part est grisé, avec l'infobulle « Modifié, mais non déclaré dans la Forme » : un oubli possible de la Forme (décision de l'utilisateur, à garder).
- À l'étape Invariants, une lecture en pseudo-code périmée grise *Validé*, *À revoir* et *Tout valider* de ses cas jusqu'à *Relire* (décision de l'utilisateur) ; sans lecture, ils restent actifs. Un test modifié depuis la validation de ses cas les décoche, comme aujourd'hui.
- À l'étape Invariants, une case *Invariants seuls* à côté du menu (décision de l'utilisateur), cochée par défaut : l'arborescence ne liste que les tests d'invariants ; décochée, le reste de la référence aussi, en retrait.
- *Depuis la validation*, présent seulement si l'étape a une validation : les fichiers qui diffèrent de leur version validée.
- Le fichier choisi montre son diff depuis cette référence, ou son texte (*Fichier*) ; *En ligne* · *Côte à côte* ne change pas. Un fichier créé depuis la référence est tout en ajouts, un fichier supprimé tout en retraits. Aucun fichier : « Rien de modifié depuis … » à la place de l'arborescence.
- On retire ce qui avait été fait d'abord : les accordéons « Validé » et « Modifié depuis la validation », le *Valider* / *Annuler* de chaque fichier, *Revalider* et « périmée ».

**L'agent principal revalide.** Aujourd'hui, seul l'écran valide une étape. La CLI `vibecoder` gagne la validation d'une étape (valider, retirer la validation) pour la Forme, les invariants et les modules ; jamais la note, dont la conception est à l'utilisateur. Quand l'utilisateur, après avoir testé, demande une correction à l'agent principal et que celui-ci corrige lui-même, il relance ce qu'il faut et revalide les étapes, puis dit à l'utilisateur ce qu'il a modifié et revalidé ; l'utilisateur le relit avec *Depuis la validation*.

## Ce que ça ne doit pas faire

- Retirer du bouton la marque « direct », la raison d'un bouton grisé ou « en cours » et ⏹ → variant suffit
- Perdre le modèle : il reste dans l'infobulle du bouton et dans les paramètres → variant suffit
- Modifier, en enregistrant le bloc d'un cas, une autre ligne du fichier de test que celles de ce bloc → invariant
- Enregistrer le bloc d'un cas dans un fichier qui a changé sur le disque depuis son ouverture → variant suffit
- Toucher à l'index du dépôt (ce que `git commit` prend) en validant, en retirant une validation ou en lisant les validations → invariant
- Écrire quoi que ce soit dans le dépôt ou sous `.git/` en validant ou en retenant une version (elles vont dans le dossier de sorties de l'appli) → invariant
- Modifier un fichier du projet (note, Forme, tests, modules) en validant, en retirant une validation ou en décochant une étape → invariant
- Valider la note par la CLI → variant suffit
- Recocher une étape sans un geste de validation (de l'utilisateur, ou de l'agent par la CLI) → variant suffit
- Laisser cochée une étape dont ce qu'elle a validé a changé, ou qui suit une étape décochée → variant suffit
- Décocher la note pour une modification de sa seule section Forme → variant suffit
- Lister, depuis le dernier commit ou depuis la validation, un fichier identique à sa référence, ou omettre un fichier qui en diffère → variant suffit
- Offrir *Commiter les modules* avant que les modules soient validés → variant suffit

## Forme

**Du pur vers l'extérieur.** D'abord le pur du principal : la conception de la
note, les fichiers retenus, la validation des étapes et leur cascade, les
marques. Puis le pur de la page : le bloc d'un cas, l'arborescence filtrée. Puis
le relevé, le fichier qu'on suit, la CLI, le contrôleur qui valide et retient
les versions. Puis la page : le bloc d'un cas à l'éditeur, les boutons de
validation, les boutons sans modèle et l'en-tête d'une étape décochée, le menu
de diff, la vue IDE, les étapes. Enfin SPEC, README et le skill `vibe`.

**Ce que la retouche fait des modules déjà commités.** On garde : `noteDesign`
(note.ts), `versionName` et `FileBlobs` (validated.ts), le relevé des empreintes
du disque et du dernier commit, l'écriture dans `<sorties>/validated/`
(controllers/vibecoder), le bloc d'un cas, les boutons sans modèle. On reprend :
validated.ts (une liste de fichiers par validation d'étape au lieu d'une marque
par fichier), marks.ts, journey, files.ts (`r<i>` : un fichier supprimé du menu
de diff), module-code (`at.validations`), ide-files, ide-view, StepHead, les
vues d'étape. On retire, avec leurs tests : stale.ts (remplacé par
step-checks.ts), review-files.tsx, `FILE`, `fileMark`, `gestureFiles`,
`fileReview`, `reviewRows`, `fileGesture`, les marques « file: » et « step: »,
`VibeValidation`, `VibeReviewFile`, `step.stale`, `at.validated`, les accordéons
et `tools` d'IdeView, Revalider et « périmée ».

**Les validations d'étape.** Une marque par étape (`note`, `forme`, `invariants`,
`modules`), posée par le ✓ que la page envoie déjà (conv:vibeMark, sans nouveau
canal) ou par la CLI (`step.validate`, sauf la note). Elle porte l'empreinte de
ce que l'étape valide, `after` (l'empreinte de la marque de l'étape d'avant) et
`files` (l'empreinte de la liste de ses fichiers). La cascade se calcule sans
rien écrire : une étape est cochée si son empreinte tient, si l'étape d'avant
l'est et si son `after` est encore la marque de l'étape d'avant — revalider la
note change sa marque, la Forme n'est donc plus cochée tant qu'on ne la
revalide pas. La liste et le texte de chaque fichier vont dans le dossier de
sorties de l'agent, `validated/<empreinte>` ; jamais dans le dépôt ni sous
`.git/`. Le dernier commit se lit par `git show HEAD:<chemin>` (déjà en lecture,
GIT_READ inchangé) : l'index n'est jamais touché.

**Le menu de diff de la vue IDE.** Un seul DiffPicker en tête de la vue (Fichier ·
Depuis la base · Depuis le dernier commit · Depuis la validation) ; la référence
filtre l'arborescence d'après `view.diffs`, rempli par le relevé ; le fichier
choisi lit sa référence dans `code.at` (base, head, validations de l'étape).

**Le bloc d'un cas.** La page coupe et recoud : les lignes du bloc (caseRange,
sur file.source), le fichier du disque dont seul ce bloc change (replaceRange),
envoyé par l'enregistrement d'aujourd'hui (saveCode, canal inchangé).
