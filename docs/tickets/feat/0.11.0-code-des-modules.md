# 0.11.0 — Voir le code des modules

## Ce que ça fait

- Étape **Modules** de *Créer* (F-100) : sous la ligne d'un module touché
  par la branche (commité ou en cours), un accordéon *Voir le code*. Déplié :
  l'arborescence des fichiers du module, et le fichier choisi dans un
  éditeur de texte classique — monospace, numéroté, coloré (F-113), comme
  *Code* et *Voir le fichier* de l'étape Invariants. (Aujourd'hui, regarder
  le code d'un module n'est pas pratique ; le voir là sert aussi à
  apprendre.)
- Seul le fichier ouvert dans l'accordéon est lu : à l'ouverture, puis à
  chaque changement sur le disque (pas au rythme du relevé). Pendant la
  génération, on voit ainsi le code s'écrire. L'accordéon reste sur le
  fichier que l'utilisateur a choisi, sans en changer.
- Le code est modifiable, enregistré sur le disque au geste : Ctrl+S ou
  *Enregistrer*. L'édition est grisée pendant une course qui génère ce
  module (*Générer*, *Générer les modules restants*) et pendant un tour de
  la conversation (on ne sait pas d'avance quels fichiers il touche ; une
  demande faite par 💬 ou *Retour → fixup* vise souvent ce fichier). Grisée,
  la vue suit toujours le disque.
- Un clic sur une ligne, ou un bloc sélectionné : 💬 le cite dans le champ
  (« À propos de « … » : », F-98) pour une question ou une vérification ;
  *Retour → fixup* pour une correction. Un bloc est cité en entier, sans
  limite de lignes (F-98 limite sinon la citation à une ligne de 300
  caractères).

## Ce que ça ne doit pas faire

- La page ne désigne un fichier du module que par son id dans le dernier
  relevé, jamais par un chemin ; le principal ne lit que le fichier ouvert,
  d'un module touché par la branche, rien hors du dossier de l'agent (I-37,
  élargi aux fichiers des modules) → invariant
- Enregistrer n'écrit que le fichier affiché, désigné par son id, dans le
  dossier de l'agent, et seulement au geste de l'utilisateur (exception à
  I-39, qui interdit sinon au principal de modifier le dépôt hors des quatre
  actions directes ; exception validée par l'équipe) → invariant
- Pas d'enregistrement pendant une course qui génère le module ni pendant un
  tour de la conversation (édition grisée ; le principal recalcule codeLock
  avant d'écrire, sans se fier à la page) → invariant
- Le code s'affiche en morceaux de texte, jamais en HTML (I-40) → invariant

## Où ça casse

- Taille d'un fichier affiché, nombre de fichiers par module : mesuré le
  2026-10-22 sur whisper-dictation, gt-plugins et GT-2020 (465 modules,
  2 355 fichiers `.ts`/`.tsx`/`.rs`). Fichier : médiane ~2 Ko, 99 % sous
  23 Ko, les plus gros ~1 Mo (générés). Fichiers par module (dossier
  d'`index.ts`) : médiane 2 ; avec les sous-dossiers, tests compris,
  95 % sous 20, au plus 304 (un module qui en contient d'autres).
  → la limite d'1 Mo du relevé suffit ; au-delà, le fichier n'est pas
  affiché. Mais le relevé parcourt tout le dossier (sorties de build,
  dépendances), toutes les 4 s : il saute `node_modules`, `target`, `dist`,
  `build` et les fichiers et dossiers cachés, et liste au plus 1 000 fichiers par module
  (au-delà, les premiers trouvés seulement).

## Ce que ça touche

- `src/renderer/app/panel/vibecoder/modules-view.tsx` : la ligne d'un
  module (*Générer*, *Relire le diff*, *Ouvrir*), qui gagne l'accordéon.
- `src/renderer/app/panel/vibecoder/invariants-view.tsx` : *Code* et *Voir
  le fichier*, l'affichage du code à reprendre.
- `src/renderer/core/vibecoder` : `syntax.ts` (`codeLines`, F-113),
  `module-row.ts`.
- `src/shared/bridge/types.ts` : `VibeModule` (aujourd'hui `file` seul, ni
  ses fichiers ni leur texte) ; `src/shared/bridge/channels.ts` (protégé,
  accord donné) : lire un fichier de module, suivre ses changements,
  l'enregistrer.
- `src/main/core/vibecoder/files.ts` (`itemPath`, `safePath`) et
  `src/main/app/controllers/vibecoder.ts` : le relevé (F-94).
- `resources/vibecoder/actions.fr.json`, `actions.en.json` : les actions
  `prefill` `comment` (💬) et `fix` (*Retour → fixup*).
- `SPEC.md` : F-100 (étape Modules), F-94, F-113, F-98, I-37, I-39.

## Forme

**Désigner.** Le relevé donne à chaque module touché ses fichiers,
`VibeModule.files` (ids `m<rang>/<i>`, comme `c<rang>/<i>` pour un commit) ;
un module pas touché n'en a aucun. La page suit un fichier par cet id ; le
principal le traduit d'après son dernier relevé (`codeFile`), le lit (1 Mo au
plus), le surveille et pousse son texte (`conv:vibeCode`) — lui seul, pas au
rythme du relevé.

**Griser.** Une course retient le module qu'elle génère (`Run.module` :
*Générer*, *Suivant* → son chemin ; *Générer les modules restants* → `*`).
`codeLock` dit pourquoi l'édition est grisée ; le relevé le donne à la page
(`VibeModule.locked`) et le principal le recalcule lui-même avant d'écrire,
sans se fier à la page.
