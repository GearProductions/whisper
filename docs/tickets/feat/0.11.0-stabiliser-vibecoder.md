# 0.11.0 — Stabiliser VibeCoder

PR de nettoyage : ajuster et améliorer ce qui existe pour stabiliser
VibeCoder, sans nouvelle étape.

## Ce que ça fait

**Partout : l'alignement.** Une passe sur tous les boutons et tous les
écrans du panneau : plus d'écarts énormes, plus de boutons qui poussent le
texte, une interface bien alignée.

**Mode Vibe.**
- *Valider et développer* n'est plus proposé pendant que la course qu'il a
  lancée tourne (aujourd'hui, il reste cliquable pendant que la course
  *Poser la forme* travaille : seule la forme finie le masque).
- Les étapes que le mode Vibe a passées sont validées aussi en mode Guide :
  en passant en Guide, pas besoin de recliquer sur ✓ pour voir les étapes
  suivantes (F-102, F-103).
- Pas de lecture des invariants (*Lire les invariants*, le pseudo-code) dans
  l'enchaînement Vibe : l'orchestrateur n'en a pas besoin (*Écrire les
  invariants* vérifie déjà l'alignement des tests, trois tours au plus). Elle
  reste à la main dans l'étape Invariants.

**Note.** La note s'affiche aussitôt, sans grand espace vide au-dessus ;
l'édition s'ouvre par un bouton *Modifier*.

**Étape Modules.**
- *Voir le code* montre, en option, ce qui a été modifié : le diff git du
  fichier, en plus du fichier tel qu'il est. Un sélecteur choisit la
  référence : la base de la branche (tout ce que le ticket a changé) ou le
  dernier commit (ce qui n'est pas encore commité).
- Les trois boutons du module (*Générer*, *Relire le diff*, *Ouvrir*)
  quittent le côté du code : ils passent sous le code, en barre d'outils de
  l'accordéon.
- Générer et commiter sont deux gestes séparés (l'utilisateur peut
  maintenant coder dans les modules) : générer un module ou tous les modules
  restants ne commite pas. Un bouton *Commiter* par module, et *Commiter les
  modules* pour tous (un commit par module).
- En Vibe, l'orchestrateur enchaîne toujours seul : générer, puis
  commiter.

**Étape Revue.**
- Chaque vérification se relance seule (corriger les tests qui échouent ne
  demande pas de tout relancer).
- Une action n'est pas proposée quand l'état des courses la rend sans objet :
  par exemple *Appliquer* sur une remarque de la ponytail review une fois
  *Tout appliquer* lancé.
- La ponytail review appliquée se voit dans son encart, une fois la course
  *Appliquer* finie : chaque remarque appliquée marquée ✓ et grisée, et un
  bandeau « Appliquée » sur l'encart quand tout l'est.

**Robots (F-55, F-115).**
- Le robot d'un agent clignote pendant qu'une de ses courses travaille,
  du même clignotement qu'un tour de la conversation (aujourd'hui, seule la
  conversation le fait clignoter : il faut aller voir soi-même).
- La question d'une course (par exemple, en Vibe, la confirmation
  d'appliquer la revue) reste sur le robot tant qu'elle n'a pas de réponse,
  même si l'utilisateur passe à un autre agent entre-temps (aujourd'hui,
  l'ouvrir dans l'onglet Actions suffit à l'effacer).

**Onglet Processus : les commandes du projet (F-111).**
- Une commande ajoutée au fichier du projet et enregistrée apparaît dans
  l'onglet sans relancer l'appli.
- *Proposer les commandes* reste disponible une fois le fichier du projet
  créé (aujourd'hui, le bouton disparaît dès que le fichier existe). Le
  fichier existant, seules les commandes proposées dont le nom n'y est pas
  encore s'y ajoutent ; celles qui y sont restent telles quelles (le fichier
  appartient à l'utilisateur : ses retouches ne sont jamais écrasées).

**Demandes de l'orchestrateur (F-115).** Une demande que l'appli ne lance
pas, ni ne met en attente, n'est plus perdue en silence : l'agent est
prévenu. Un argument qui ne s'applique pas à l'action est ignoré : l'action
démarre, et l'agent est prévenu de l'argument ignoré. (Cas vu : en Vibe,
*Générer les modules restants* demandé avec `model: opus` ; l'action ne prend
pas de modèle, la demande est refusée sans que l'agent le sache, et rien ne
démarre.)

## Ce que ça ne doit pas faire

- Générer un module, ou les modules restants, ne commite rien → variant suffit
- Relancer une vérification ne relance ni les autres ni la ponytail review
  → variant suffit
- La question d'une course ne quitte le robot qu'à sa réponse → variant suffit
- Une demande de l'orchestrateur refusée n'est jamais jetée sans avis à
  l'agent ; un argument inutile ne la fait pas refuser → variant suffit
- Le diff ne lit que les fichiers des modules touchés par la branche,
  désignés par leur id, jamais par un chemin venu de la page (I-37)
  → invariant (existant)
- Le diff s'affiche en morceaux de texte, jamais en HTML (I-40)
  → invariant (existant)
- Une proposition de commandes ne modifie ni ne retire une commande déjà
  dans le fichier du projet → variant suffit
- Pas de bouton qui pousse le texte ni d'écart vide ; pas d'action proposée
  qui n'a plus d'objet → vu en review

## Forme

**Processus : reproduire d'abord.** La cause du bug « une commande ajoutée
au fichier du projet n'apparaît pas sans relancer l'appli » n'est pas
trouvée : `processView` relit pourtant le fichier à chaque relevé. Premier
geste, avant tout correctif : un test rouge qui la reproduit, au plus bas
niveau où elle se montre (le contrôleur ; vert là → le relevé ; vert encore
→ la page). Le module du correctif se déduit de ce test ; il prend sa place
dans l'ordre ci-dessous (`controllers/processes` en attendant).

**Vibe → Guide.** Au passage en Guide, les étapes que Vibe a passées
reçoivent leur ✓ pour le contenu qu'elles ont aujourd'hui (note, forme, cas
des invariants) ; une validation déjà donnée pour ce contenu (✓ ou ✗) reste.

**Le diff d'un fichier de module.** Le principal pousse, avec le texte du
fichier suivi, son texte à la base de la branche (`git log --boundary`) et au
dernier commit ; la page fait le diff (`lineDiff`) et l'affiche en texte.
Seulement pour un fichier de module touché (`m<rang>/<i>`), jamais la note
ni un test.

**Générer, puis commiter.** Un skill de commit à part (`commiter-modules`),
appelé par deux actions : un module (`commit-module`, `{{module}}`) ou tous
ceux qui ont des changements pas commités (`commit-modules`), un commit
chacun. `modules` ne commite plus ; `suivant` (*Valider → commit →
suivant*) reste un geste explicite de commit, et suit ce même skill.

**Tranché à la forme.** *Valider → commit → suivant* reste (la note ne le
retire pas ; il ne commite que sur un clic). Noms gardés : skill
`commiter-modules`, actions `commit-module` et `commit-modules`,
`ponytail-applied.json` (remarques repérées par `<fichier>:L<ligne>`). Sur le
robot, `working` passe après `asking`, `failed` et `done` : ce qui attend
l'utilisateur prime sur ce qui travaille seul.
