# 0.16.0 — Un flow à la taille du ticket

Branche `feat/0.16.0-flow-allege`.

## Ce que ça fait

Une évaluation de VibeCoder (23 novembre 2026) a mesuré de la friction qui ne protège rien. Ce qui protège reste tel quel : la note validée par l'utilisateur, la vérification de conception, les invariants écrits avant le code et alignés, le TDD des variants, la revue ponytail indépendante, la pause pour l'essai à l'écran. Les mesures : la PR #101 compte 90 lignes de code pour 263 de tests, 133 de note et 14 skills retouchés ; les PR sont fusionnées en squash, souvent 15 à 30 minutes après leur ouverture (personne ne lit l'historique commit par commit) ; *Appliquer la revue* cumule 14,8 h de course contre 17,4 h pour *Générer les modules* ; chaque skill répète le même paragraphe pour retrouver la note et la branche de base.

Cinq améliorations, dans une seule PR.

1. **L'historique par module devient un choix du projet.** Le mode d'aujourd'hui reste le défaut : un commit par module, les corrections en fixups du commit qui possède le code, repliés avant la PR (un projet d'équipe où un développeur relit commit par commit en a besoin). Nouveau mode « historique simple », déclaré par une ligne de `AGENTS.md` (la convention de commit du projet, dans git et partagée par l'équipe, que les skills de commit lisent déjà ; sans cette ligne : le défaut ; ni case dans l'appli, ni clé de `.vibecoder/project.json`) : le premier commit ne change pas (note, forme, invariants rouges), puis un seul commit pour le code de tous les modules.
   - Ce commit prend tous les fichiers modifiés ou nouveaux du dossier, et la réponse de *Commiter les modules* nomme ceux qui ne sont dans aucun module de la Forme (rien n'échappe, et l'utilisateur voit ce qui est parti).
   - Une correction faite après ce commit (*Appliquer la revue*, une vérification rouge, un retour d'essai) est un commit ordinaire, « revue : … » : rien à replier, aucune réécriture d'historique, la fusion en squash efface ces commits. *Appliquer la revue* ne cherche plus le commit propriétaire de chaque ligne, et reçoit le droit de faire un commit ordinaire.
   - Le parcours de l'écran ne lit pas le mode : il convient déjà aux deux (l'étape Modules faite quand chaque module a un commit hors du premier et que rien n'est à commiter, ce que le commit unique remplit ; *Replier les fixups* déjà masquée sans commit `fixup!` ; l'étape Revue faite sans fixup). Seul le libellé de la case « Un commit par module, fixups repliés » devient « Chaque module commité, aucun fixup à replier ».
   - Ce dépôt passe en historique simple (ses PR sont fusionnées en squash depuis la PR #79) : son `AGENTS.md` le dit, et le skill du projet `gear-commit-message`, qui dit encore « fusionnées sans squash », est corrigé. Le guide « Développer avec l'IA » ne change pas : un commit par module reste la règle par défaut de l'équipe.
2. **Un petit ticket n'a pas un sous-agent par module.** Quand la Forme compte au plus 4 modules de code, sans compter ceux qui n'ont pas de variants (la doc, les textes de skills), *Générer les modules* confie tous les modules à un seul agent développeur : à la suite, dans l'ordre de la Forme, dans un seul contexte, les variants rouges d'abord pour chacun. Au-delà, les vagues parallèles restent. Le seuil se compte dans la Forme, sans estimation de lignes ; il n'est pas réglable.
3. **L'appli passe aux actions ce qu'elle sait déjà** : le chemin de la note et la branche de base, par les variables des gabarits des actions. `{{note}}` ne va qu'aux actions qui n'ont pas de sens sans note : un gabarit qui le porte est refusé sans note, donc *Rédiger la note* (qui s'ouvre avant toute note) et toute action qu'on lance aujourd'hui sans note ne le reçoivent pas et gardent leur recherche. Les skills ne recherchent plus eux-mêmes une valeur donnée ; ils gardent la recherche seulement quand elle ne l'est pas (un skill lancé à la main).
4. **Dans *Générer les modules*, la relecture de chaque diff par l'orchestrateur devient un contrôle de conformité** (guide §5.1 : « une lecture de conformité plutôt qu'une chasse aux bugs ») : les quatre questions du guide, vite lues (le périmètre et les fichiers permis, une dépendance ajoutée, une lecture ou une écriture dans une boucle ou un appel bloquant, une donnée lue ou écrite hors de son périmètre), l'en-tête fidèle au contrat, les variants dans le fichier nommé et vus rouges puis verts, les invariants verts et intacts. La chasse aux défauts (cas limites, doublons, sécurité, code mort) et les lignes « ne doit pas » du module reviennent à la revue ponytail, qui relit toute la branche juste après et trouve déjà ces défauts.
5. **La Forme de la note s'allège.** Depuis que *Poser la forme* écrit des squelettes qui compilent, les signatures typées existent deux fois. Dans la note, pour chaque module : son chemin, ce qu'il expose en une ou deux lignes de prose, ce qu'il ne connaît pas, qui l'utilise, et sa ligne « variants : » avec ses cas. Les signatures vivent dans les squelettes et les en-têtes de fichiers. La mise en page que lit l'écran ne change pas : le chemin en début de ligne, les suites indentées, une ligne vide entre deux entrées.

`SPEC.md`, `README.md` et les textes des skills suivent.

## Ce que ça ne doit pas faire

- Changer quoi que ce soit pour un projet qui garde l'historique par module (le défaut, sans réglage) → variant suffit
- Affaiblir un garde-fou : les tests protégés jamais modifiés, les variants rouges avant le code, la revue ponytail, les étiquettes `[toi]` / `[agent]`, les droits de chaque action (le `allowed-tools` de son skill ; I-57 ne change pas), hors le commit ordinaire que reçoit *Appliquer la revue* → vu en review
- Réécrire l'historique d'une PR ouverte, quel que soit le mode → vu en review
- Perdre un fichier au commit en historique simple (un fichier hors de la Forme a déjà échappé deux fois à *Commiter les modules*) → variant suffit
- Modifier la note validée par l'utilisateur hors de sa rubrique Forme → vu en review

## Ce que ça touche

- Le parcours, `src/main/core/vibecoder/journey.ts` : inchangé dans ses règles (il convient déjà aux deux modes) ; seul le libellé de la case « Un commit par module, fixups repliés » de la liste de l'étape PR change.
- `AGENTS.md` : la ligne qui déclare l'historique simple, lue par les skills de commit ; celui de ce dépôt la reçoit (sa rubrique « PR » dit aujourd'hui « un commit par module »).
- Les variables des gabarits, `src/main/core/vibecoder/actions.ts` : `{{note}}` (le chemin de la note ; sans note, l'action est refusée), `{{base}}` et `{{branch}}` existent déjà ; aucun gabarit de `resources/vibecoder/actions.fr.json` ni `actions.en.json` ne passe `{{note}}` ni `{{base}}`. Un `actions.<langue>.json` modifié par l'utilisateur n'est jamais remplacé : ses gabarits ne passent pas ces valeurs, et ses skills les recherchent. La table des variables : `resources/vibecoder/README.md`.
- Les skills (`resources/vibecoder/plugin/skills/`) :
  - l'historique : `commiter-modules` (un commit par module, un fixup pour un module déjà commité ; « les fichiers qu'aucun module ne possède : laissés »), `commit-preparer`, `appliquer-revue` (chaque remarque en fixup du commit propriétaire), `fixups`, `vibe`, `pr` ; les skills du projet qu'ils suivent, `.claude/skills/gear-commit-message` et `.claude/skills/gear-fix-up`, décrivent l'historique par module ;
  - la génération : `modules` (un sous-agent par module, par vagues ; sa relecture de chaque diff : les quatre questions du guide §5.1, les doublons, l'en-tête, les lignes « ne doit pas », les invariants, les variants, ~400 lignes), `module`, l'agent `resources/vibecoder/plugin/agents/developpeur.md` ;
  - la revue : `ponytail` (ses étiquettes `edge`, `duplicate`, `security`, `dead`, `note` couvrent déjà les cas limites, les doublons, la sécurité, le code mort, l'écart avec la note) ;
  - la Forme : `forme` (aujourd'hui : « ce qu'il expose (noms et signatures typées) », chaque signature sur sa ligne) ;
  - le paragraphe répété (la note sous `docs/tickets/`, la base par `git symbolic-ref`) : `aligner`, `commit-preparer`, `commiter-modules`, `conception`, `ecran`, `fixups`, `forme`, `invariants`, `lire-invariants`, `modules`, `note`, `ponytail`, `pr`, `relire`, `relire-commits`, `relire-note`, `vibe`, et l'agent `developpeur`.
- La lecture de la Forme par l'écran, `src/main/core/vibecoder/note.ts` : inchangée (la mise en page ne change pas).
- `SPEC.md`, `README.md` (dont la table des droits des actions), `resources/vibecoder/README.md`.

## Forme

**Presque tout est du texte.** Le parcours convient déjà aux deux historiques,
et les variables `{{note}}` et `{{base}}` existent déjà : un libellé, des
gabarits, puis les skills et la doc. Aucune signature ne change ; un seul
squelette, l'en-tête de `journey.ts`.

**Le mode, deux mots d'`AGENTS.md`.** Dans la convention de commit du projet
(ici, sa rubrique « PR »), les mots « Historique simple » (« Simple history »
dans un projet en anglais). Les skills de commit les lisent ; sans eux : un
commit par module, comme aujourd'hui.

**La note et la base, des arguments nommés.** Après le dossier de sorties :
`note=<chemin>` et `base=<réf>`. Un skill qui les reçoit ne cherche pas ;
lancé à la main, ou par un gabarit retouché qui ne les passe pas, il cherche
comme avant.
