# 0.15.0 — La CLI de VibeCoder, et l'agent principal qui connaît son rôle (T-19)

Étape 3b du plan « VibeCoder pilotable par agents » (artefact `actions/pilotage-par-agents.html`, « Le plan », étape 3 ; `run wait` vient de l'étape 4). L'étape 3a, le socket TCP et l'interface qui passe par lui (note `0.15.0-socket-interface.md`, PR #82), est fusionnée. Avec T-19 (liste des tickets, artefact `actions/tickets.html`).

## Ce que ça fait

**Le résultat attendu.** Un Claude Code lancé dans un terminal de la box demande « où j'en suis ? » et lance *Écrire les invariants* sans toucher au panneau ; un refus arrive dans la seconde ; le mode Vibe enchaîne les actions par la CLI.

**La commande `vibecoder`**

- Un client du socket TCP de l'étape 3a. Elle trouve l'appli par `live.json` (`{ port, pid }`, plus le jeton extérieur quand le réglage est activé, voir « Qui appelle »), dans `~/.config/whisper-dictation/` (la version de dev et l'AppImage ne tournent pas en même temps). Un robot, lui, ne lit jamais `live.json` : le port lui est donné avec son jeton, par son environnement (décidé le 9 novembre : sinon un programme qui réécrirait le port dans `live.json` recevrait le jeton du robot).
- Une forme générale pour toute commande de la table : `vibecoder <commande> [clé=valeur…]` (par exemple `vibecoder draft.add target=… text=…`). (Décidé : un seul code, et le contrat entier sans rien ajouter à la main.) Les raccourcis ci-dessous s'y ajoutent.
- Les lectures : `vibecoder status`, `next`, `commands`, `schema`.
- Les courses : `vibecoder run start <action> [model=… effort=… text=…]`, `run stop`, `run list`, et `run wait <id>`, qui garde la connexion ouverte jusqu'à la fin de la course : lancé en tâche de fond par un agent, il le réveille (c'est l'avis de fin des agents que l'appli ne possède pas).
- Les processus : `vibecoder proc list`, `proc restart <nom>`, `proc stop <nom>`, `proc logs <nom>`.
- Code de sortie 0 si tout va bien ; `--json` ; jamais de question interactive.
- Un refus arrive dans la seconde : c'est la réponse de l'exécuteur, rendue par le socket.
- Un script dans le plugin. L'agent principal l'appelle par son chemin dans le plugin ; pour un terminal, le README explique le lien à poser à la main dans `~/.local/bin` (décidé : rien d'installé par l'appli, I-26, et c'est réversible).

**L'agent principal passe à la CLI**

- Les skills `actions` et `processus` disent « appelle `vibecoder …` » au lieu d'« écris tel fichier », et lisent l'état par la CLI.
- Ensuite, la boîte aux lettres disparaît : les fichiers `actions/<id>.start`, `.stop`, `run/<nom>.stop`, `.restart` ne sont plus lus, et `actions.json` n'est plus écrit (décidé : un seul chemin, aussi pour lire ; `vibecoder run list` dit la même chose).
- Une demande qui tombe pendant une autre action reste en attente, comme aujourd'hui : « occupé » devient « en attente », la CLI répond aussitôt que la demande attend, et l'appli la lance seule quand la voie est libre (décidé : le mode Vibe et les skills continuent de marcher pareil, dont le skill d'un module qui demande *Relire le diff* pendant qu'il s'écrit). Les autres refus arrivent tout de suite. Une demande en attente part quand sa cause tombe, même panneau caché ou écran verrouillé (T-31) : l'appli relève le robot à neuf avant de relire la file, à la fin d'une course, d'un tour, d'un Garder ou d'un Annuler, sans dépendre de l'affichage ; une demande que ce relevé grise (étape passée, PR fusionnée…) quitte la file au lieu d'y rester.

**Qui appelle**

- Un jeton par robot, passé par une variable d'environnement à ce que VibeCoder lance (l'agent principal et ses courses), jamais écrit : il dit quel robot appelle. (Décidé : si les jetons des robots étaient dans `live.json`, que tout programme de la machine peut lire, un agent extérieur pourrait se faire passer pour n'importe quel robot, même désactivé.)
- Un agent ne lance que ce que sa porte autorise (la porte agent de l'exécuteur : `run.allow`, `run.always`, `run.deny` restent fermées). Un agent extérieur a ainsi les capacités de l'interface sur le projet de son dossier (il change de projet en changeant de dossier), sauf ce qui est une décision de l'utilisateur : répondre aux demandes d'autorisation, les réglages (dont le modèle, l'effort et l'accès des agents extérieurs), la confiance à un projet ; ces deux derniers ne sont pas des commandes de la table et ne le deviennent pas (décidé le 9 novembre).
- Les agents extérieurs (un Claude Code lancé dans un terminal, hors de l'appli) sont désactivés par défaut, par un réglage de la page des réglages (le plan : « Autoriser les agents extérieurs », par le canal `settings`, qui existe). Activés : `live.json` porte un jeton « extérieur », écrit seulement tant que le réglage est activé (le seul jeton écrit est celui qui est permis). Il est distinct des jetons des robots et ne désigne aucun robot : il dit seulement « un agent extérieur, permis » ; son robot est trouvé par son dossier courant.
- Un agent extérieur est rattaché à un robot par son dossier courant (le chemin réel : `/home` contre `/var/home`), avec la règle des boutons : le robot affiché s'il est sur ce dossier, sinon le premier robot de ce dossier ; un sous-dossier compte comme son projet (décidé : la même règle partout).
- Le robot d'un agent est relevé à la demande, à chaque commande d'un agent, même s'il n'est pas affiché (décidé : c'est ce qui permet de travailler sans toucher au panneau).
- Le jeton de l'écran ne change pas : en mémoire seulement, jamais sur le disque ni vers la page (I-50).

**T-19 : l'agent principal connaît son rôle**

- La consigne de sa conversation dit le rôle affiché (créateur ou relecteur, `view.flow`). (Aujourd'hui, en relecteur, il croit pouvoir modifier la branche.)
- En relecteur, à une demande, il propose des remarques pour le brouillon de revue (les commandes `draft`, `draft.add`, `draft.edit`, `draft.remove`, dans le contrat depuis l'étape 3a) plutôt que de modifier la branche.

**Les tests de contrat vus de l'extérieur**

- Les premiers : un script à part, `npm run test:contract`, qui reprend le lancement de l'appli du banc `test:main-diff`, avec un faux `claude`, appelle la CLI et vérifie les réponses attendues ; lancé à la main, comme le banc (décidé : on réutilise le banc sans changer sa comparaison ; la version de base n'a pas de CLI à comparer).

## Ce que ça ne doit pas faire

- Écrire le jeton d'un robot (pas le jeton extérieur, qui est distinct) sur le disque (`live.json` compris) → invariant
- Qu'un robot trouve l'appli par `live.json` (son port et son jeton viennent de son environnement) → invariant
- Écrire le jeton extérieur ailleurs que dans `live.json`, ou l'y écrire quand le réglage est désactivé → invariant
- Envoyer un jeton d'agent (d'un robot ou extérieur) à la page (par un canal, un relevé, un message) → invariant
- Écrire le jeton de l'écran sur le disque, `live.json` compris, ou le donner à la page → invariant (I-50, existant)
- Écouter ailleurs que sur `127.0.0.1` → invariant (I-49, existant)
- Laisser `live.json` après la sortie de l'appli, ou le jeton extérieur sur le disque → invariant (I-43 ; `app/tests/invariants/live-file.test.ts`, le test existant n'étant qu'un variant)
- Lancer, à une porte d'agent, ce que cette porte n'autorise pas (une commande fermée aux agents) → invariant (celui de l'exécuteur, existant ; qu'un robot et un agent extérieur passent bien par la porte agent : `app/controllers/tests/invariants/agent-doors.test.ts`)
- Accepter un agent extérieur quand le réglage est désactivé (par défaut) → invariant
- Faire agir un agent sur un autre robot que le sien : celui de son jeton, ou celui de son dossier courant pour un agent extérieur → invariant
- Un shell, dans la CLI comme dans l'appli → structure (I-27, `tests/structure/no-shell.test.ts`)
- Poser une question interactive, ou rendre 0 sur un refus → variant suffit
- Garder deux chemins : une demande par fichier encore lue, ou `actions.json` encore écrit, après le passage à la CLI → variant suffit
- Refuser une demande qui doit seulement attendre, au lieu de la mettre en attente → variant suffit
- Laisser une demande en attente bloquée parce que le panneau est caché ou l'écran verrouillé (T-31) → variant suffit
- Une consigne qui ne dit pas le rôle affiché, ou en dit un ancien → variant suffit

## Forme

**Du dedans vers le dehors.** Le pur d'abord : ce que la CLI lit (`live.json`,
son environnement, sa ligne de commande) et qui appelle sur quel robot. Puis
le socket : plusieurs jetons, une réponse qui peut attendre. Puis l'exécuteur
(`run.wait`, la file d'attente lue par `runs`), le relevé d'un robot non
affiché, et les portes (robot, extérieur). Puis le script `vibecoder`,
l'environnement des robots, le réglage, les skills, le retrait de la boîte aux
lettres, T-19, `test:contract`, la doc.

**Les jetons.** Le serveur reconnaît un jeton parmi une table et rend le nom
de celui qui appelle : `screen` (le jeton de l'écran, tiré par le serveur,
inchangé), l'id d'un robot (son jeton, tiré à sa première demande, en mémoire
seulement), `outside` (le jeton extérieur, tant que le réglage est activé).
`commandFromSocket` en déduit le robot et la porte (pur : `callerRobot`). La
porte de l'exécuteur ne change pas : `'screen' | 'agent'` ; un robot et un
agent extérieur passent tous deux par la porte agent.

**En attente, à la porte des agents seulement.** `runCommand` et l'exécuteur
refusent toujours `busy` et `changing` (le test protégé `commands-guards`
l'attend). C'est `commandFromSocket` qui, à la porte agent, met en file un
`run.start` (ou `vibe`, `guide`, `new-request`, `propose-run`) refusé
`busy` ou `changing` et répond `{ ok: true, result: { queued: true, by } }` :
la CLI sort avec 0 et dit que la demande attend. La file (`waits` de
`controllers/runs`) part seule quand la voie est libre ; `run list` la montre.

**Tests protégés.** `core/runner/tests/invariants/runner.test.ts` : les cas de
`requestsOf` (demandes `run/<nom>.stop`, `.restart`) partent avec la boîte aux
lettres (accordé) ; le reste du fichier ne change pas. Ceux du jeton de
l'écran (`server.test.ts`, `socket-token.test.ts`) restent tels quels :
`listen(handle)` garde sa forme à un argument et `Server.token`.
`commands-guards`, `runs` et `reviewer` (invariants des contrôleurs) ne
changent pas : leur `orchestratorAsks` vient du décor, rebranché sur
`commandFromSocket` (une retouche du décor, signalée dans la PR, comme celle
de `tests/structure/`).
