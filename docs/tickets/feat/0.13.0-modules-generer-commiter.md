# 0.13.0 — L'étape Modules : générer, puis commiter, et c'est tout

## Ce que ça fait

- En pratique, on ne commite pas module par module, et on génère rarement
  module par module : on génère tout, on vérifie, on ajuste, puis on laisse
  les commits à l'agent. Ranger un module avec un autre est compliqué pour
  le dev, simple pour l'agent.
- L'étape Modules n'a plus que deux actions, à côté du titre de la carte :
  - *Générer les modules* (renommé : « restants » n'avait plus de sens) :
    ceux pas encore générés, par des agents Sonnet en parallèle, dans
    l'ordre de la Forme, chaque diff relu ; masqué quand tous le sont ;
  - *Commiter les modules* : un commit par module (ou un fixup), rangés par
    l'agent, s'il y a un module pas commité.
- *Générer* reste sur la ligne de chaque module : on peut générer un à un
  si on le souhaite, relire (la relecture part seule après), ajuster.
- Retirés :
  - *✓ Valider → commit → suivant* (et son skill `suivant`) ;
  - *Commiter* sur la ligne d'un module (l'action *Commiter ce module*) ;
  - *Préparer le commit* dans l'étape Modules : il reste pour le premier
    commit (Invariants) et les fixups de la note (Forme).
- La prochaine action de l'étape : *✓ Commiter* (un commit préparé), sinon
  *Générer les modules* tant qu'un module n'est pas touché, puis *Commiter
  les modules*.

## Ce que ça ne doit pas faire

- Les commits restent un par module, dans l'ordre de la Forme, chacun
  vérifié (il compile) : seul le geste change, pas l'historique. → vu en
  review (skill `commiter-modules`, inchangé)
- *Vibe* ne change pas : il passait déjà par *Générer les modules* puis
  *Commiter les modules*. → vu en review

## Pistes pour plus tard

- Le guide (§4.1 : un module par génération, relu avant le suivant) dit
  autre chose : la plus-value est dans la note, les invariants et la forme,
  moins dans la relecture du code de chaque module. À revoir à part.
