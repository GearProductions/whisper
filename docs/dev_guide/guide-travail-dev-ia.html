Comment lire ce guide

Ce sont des bonnes pratiques, pas des règles. Elles décrivent ce qui a marché pour une équipe de trois développeurs full-stack qui maintient un produit dans la durée, avec des cycles courts. Chaque ticket est différent : on prend ce qui sert, on allège ce qui ne sert pas, et on en discute quand ça coince.

Le guide se lit dans l'ordre la première fois. Ensuite, les sections 4 et 5 et les annexes servent de référence. Les sections 6 et 7 déroulent deux tickets réels.

L'idée centrale
L'effort humain n'est plus proportionnel à la quantité de code à écrire. Il est proportionnel à ce qu'un changement peut casser sans que personne ne le voie.

1. Principes

Le temps humain va à la vérification

Générer 400 lignes prend deux minutes ; s'assurer qu'elles ne sortent pas de données du mauvais tenant en prend vingt. La question utile n'est pas « est-ce de l'architecture ou du code ? » mais « est-ce que je verrais le problème rapidement s'il y en avait un ? ». Ce qui se voit vite se délègue ; ce qui ne se découvre qu'en production mérite l'attention d'un humain.

Décider la forme avant de générer

L'IA remplit très bien une forme qu'on lui donne, et invente mal une forme cohérente avec une codebase qu'elle voit à moitié. Nommer les modules, leurs signatures et ce qu'ils ne doivent pas connaître prend quelques minutes ; ranger du code après coup prend des heures.

Séparer ce qui est jetable de ce qui dure

Le code des features bouge vite et peut être régénéré. Les quelques propriétés critiques du produit (isolation des données, secrets, coûts) ne bougent pas : leurs tests sont protégés de la régénération. Une démo vit à part et n'entre pas telle quelle dans le produit.

Des lots petits

Un module par génération, quelques centaines de lignes au plus, relu avant de passer au suivant. Quatre diffs de 300 lignes se relisent ; un diff de 1 200 lignes non.

Garder un morceau à la main

Sur une feature qui compte, on écrit soi-même le morceau où l'on est le plus ignorant. C'est ce qui entretient le jugement (section 8).

Savoir quand alléger

SituationApproche
Script one-shot, outil interne à deux utilisateurs, prototype de démo« Fais-moi ça », on teste, on passe à autre chose.
Territoire technique inconnuUn spike jeté (quelques heures, non commité) qui répond à une question précise et rend un chiffre.
Code qui touche les données clients, l'argent, ou vivra longtempsLe flow complet (section 4).
Prototype validé qu'on décide de garderOn repasse par la note et la forme avant de l'intégrer.

2. La note de ticket

Le développement technique d'un ticket tient dans un fichier Markdown, docs/tickets/<type>/<TICKET>-<slug>.md, où <type> reprend le type Conventional Commits (feat, fix, refactor, chore). On l'écrit avant de générer, on la corrige pendant le développement, on la commite avec le code. Un mini bug n'en a pas besoin.

Les rubriques

On ne remplit que celles qui servent le ticket.

RubriqueContenu
Ce que ça faitLe comportement vu de l'utilisateur, en quelques lignes.
Ce que ça ne doit pas faireLes contraintes. Seules les plus critiques deviendront des tests d'invariants ; les autres se vérifient à l'écran, en review ou par un lint (section 3).
Où ça casseLe volume ou la charge attendus. Si on ne sait pas répondre, on mesure avant de coder.
Ce que ça toucheLes modules, collections, endpoints existants concernés.
FormeLes modules créés ou dont la frontière change (voir plus bas).
Pistes pour plus tardCe qui a été envisagé et reporté : trop coûteux pour une v1, ou utilité pas encore sûre. Point de départ du ticket suivant.

Une note vivante

La note ne montre que son état final : pas de journal des modifications, le cheminement pendant le dev appartient au développeur. Quand le pourquoi d'un choix mérite de rester, une parenthèse suffit (« pas de verrouillage de compte : un attaquant pourrait bloquer un utilisateur »).

Les questions ouvertes ne sont pas une rubrique. On les règle dans un appel entre développeurs, et seule la réponse atterrit dans la note, à sa place. On ne conçoit pas seul.

La forme : dans la note et en tête des fichiers

Pour chaque module créé ou modifié dans sa frontière, trois lignes suffisent : ce qu'il expose, ce qu'il ne connaît pas, qui l'utilise. On les écrit à deux endroits qui se complètent :

  • Dans la note, rubrique « Forme » : tous les modules du ticket sur une page. C'est la trace de la décision.
  • En tête de chaque fichier, un court commentaire : l'état actuel, lisible en trois secondes par un développeur ou par l'agent, sans fouiller les notes passées. On le met à jour quand la frontière change ; un en-tête faux induit tout le monde en erreur.

Variante qui marche aussi bien : poser directement le squelette de code (signatures typées, commentaire dans chaque fonction sur ce qu'elle fait et ne fait pas), puis générer. Pratique sur un ou deux modules. L'en-tête de fichier reste utile pour les frontières entre modules.

Dans les deux cas, c'est le développeur qui fixe les noms et les signatures. L'IA implémente un contrat ; elle ne l'invente pas. Si l'implémentation révèle qu'une signature est mauvaise, le développeur la change. Une frontière qui devient une règle durable peut migrer dans AGENTS.md, voire dans un lint (no-restricted-imports).

AGENTS.md

Le fichier à la racine du repo que lisent la plupart des agents (Claude Code via un import depuis CLAUDE.md). Ce sont des instructions pour la machine, pas de la documentation : commandes de build et de test, règles d'architecture qu'aucun lint n'applique, frontières de sécurité, fichiers à ne pas toucher. Court (moins de 150 lignes), écrit à la main, mis à jour dans la PR qui change la convention. Quand l'agent répète la même erreur, c'est souvent une ligne qui manque ici. Squelette en annexe A.4.

3. Les tests : invariants et variants

3.1 Un invariant, c'est le critique invisible

Un invariant est une propriété qu'on ne voudra jamais abandonner, que seul notre code peut casser, et qu'on ne verrait pas en testant à la main. On le réserve à ce qui compte vraiment :

  • Sécurité : un mot de passe n'apparaît jamais en base ni dans les logs ; deux réponses de login ne trahissent pas qu'un email existe.
  • Intégrité et isolation des données : aucune requête ne renvoie de données d'un autre tenant ; une image supprimée n'apparaît plus dans aucun export.
  • Argent et ressources : un tenant ne dépasse jamais son plafond de crédits GPU.
  • Performance et robustesse critiques : un appel externe ne reste jamais suspendu au-delà du délai ; un upload est coupé avant de lire au-delà de la limite.

Tout le reste n'a pas besoin d'un test d'invariant, même si la note le formule en « ne doit pas ». C'est le point le plus souvent mal appliqué : la rubrique « Ce que ça ne doit pas faire » n'est pas une liste de tests à écrire.

Ce que dit la ligneExempleComment on le vérifie
Critique et invisible à l'écranMot de passe absent des logsTest d'invariant
Comportement visible par l'utilisateurLe carrousel ne saute pas d'imageTest manuel en review
Structure du codeUn composant générique n'importe rien du storeReview, en-tête de fichier, lint
Comportement d'un service qu'on ne contrôle pasLe LLM « refuse » de donner un secretPas un invariant : on teste ce que notre code envoie (3.3)

3.2 Trois questions pour trancher

  1. Si on réécrivait le module de zéro, voudrait-on que ça tienne encore ? « Redirige vers /dashboard » : on pourrait changer d'avis. « Le mot de passe n'est pas dans les logs » : toujours.
  2. Seul notre code peut-il le casser ? Si un changement de modèle ou de prestataire suffit, l'invariant est un cran plus bas, sur ce que notre code fait.
  3. Le verrait-on en testant à la main ? Si oui, un test manuel en review suffit en général.

Les invariants business (projet archivé, rôle lecteur, crédits) sont souvent les plus précieux : ils ne se déduisent pas du code et disparaissent à la première refonte si personne ne les écrit. Comme ils engagent le produit, on les décide à plusieurs.

3.3 Deux pièges

Le chiffre n'est pas l'invariant. « Jamais plus de 500 Mo » : l'invariant est « jamais au-delà de la limite configurée, refusé côté serveur ». Le 500 va dans la config ; le test tourne avec une limite à 1 Mo.

Une intention n'est pas encore un invariant. « Ne jamais envoyer d'information sensible au LLM » devient testable quand on nomme la liste (mots de passe, hashs, tokens, clés, données d'un autre tenant) et qu'on vérifie la requête réellement envoyée au modèle. On complète par la structure : le contexte est construit à partir d'objets déjà filtrés, de sorte que ce qui n'est pas dans le type ne peut pas partir.

3.4 Variants et parcours

Les variants sont les tests ordinaires, générés à partir du code : « 400 si email manquant », « 200 si valide ». Ils détectent les régressions et se régénèrent avec leur module.

Les parcours end-to-end sont un bonus. Ils cassent à chaque changement d'écran ; on en garde éventuellement deux ou trois pour tout le produit, sur les chemins où une panne coûte cher (se connecter, lancer un workflow).

3.5 Écrire un invariant

  • Avant le code, depuis la note, pour qu'il ne soit pas façonné par l'implémentation. Il peut être généré ; un humain relit chaque assertion et se demande si elle observe vraiment la propriété.
  • Une relation, une absence ou une borne, plutôt qu'une valeur : expect(a.body).toEqual(b.body), not.toContain(password), toBeLessThan(timeout). Le code HTTP exact relève d'un variant.
  • Sur du réel pour ce qui fait partie du système (vraie base, vrai Redis, vrais cookies) ; un serveur factice pour ce qui est externe (Ollama, ComfyUI). Un mock de la base teste le mock. Une fonction pure se teste simplement en isolation.
  • Protégé de la régénération : si un invariant échoue, on corrige le code, pas le test. On ne le modifie qu'en changeant la note, en le disant à l'équipe.

3.6 Où ils vivent

services/auth/
  login.ts
  password.ts
  tests/
    invariants/   ← protégés, jamais régénérés
    variants/     ← générés
tests/invariants/ ← invariants produit qui traversent plusieurs modules (tenant, secrets)

Un script test:invariants (vitest run **/tests/invariants/**) permet de les lancer seuls. AGENTS.md interdit à l'agent de modifier ces dossiers sans demander.

Démarrer sans CI

On peut commencer modestement : le dossier, le script, la règle AGENTS.md, et un profil test dans le compose (Mongo, Redis, l'app). On lance test:invariants à la main avant une PR sensible et avant chaque release. Quand le profil est stable, le job CI n'est qu'une copie. Les rares invariants qui dépendent d'un vrai service externe (tag @external) tournent hors du cycle PR, en nightly ou avant release.

4. Du ticket au code

4.1 Le flow complet

Pour une feature qui touche aux données, à l'argent, ou qui vivra longtemps. Les durées sont des ordres de grandeur.

  1. Décider (≈ 30 min) : la note. Les questions ouvertes en appel avec l'équipe.
  2. Poser la forme (≈ 30 min) : modules, signatures, frontières, dans la note et en tête des fichiers.
  3. Écrire les invariants, s'il y en a, rouges.
  4. Générer un module à la fois, de l'intérieur vers l'extérieur : fonctions pures, puis orchestration, puis routes, puis UI.
  5. Relire chaque diff (5.1) avant le module suivant.
  6. Écrire un morceau soi-même : celui qu'on connaît le moins, ou celui qui porte la logique métier.
  7. Ajuster la note au fil de l'eau ; reporter dans « Pistes » ce qu'on découvre et qu'on ne fait pas maintenant.

4.2 Par type de ticket

TicketDossierLe geste qui compteCe qui se délègue
Bugfix/Reproduire et écrire un test qui échoue avant le fixLe fix. On vérifie qu'il corrige la cause, pas le symptôme (un if autour du crash est un masque).
Améliorationfeat/Lire le code existant avant de demander quoi que ce soitL'écriture. Le risque principal est la duplication d'une logique existante.
Featurefeat/Note, forme, invariants critiques, un morceau à la mainLe remplissage et les variants.
Migrationchore/S'assurer que les tests couvrent ce que la lib fait pour nous ; lire le changelog à la mainLa migration. Ce qui mord, ce sont les changements de valeurs par défaut, pas d'API.
Refonterefactor/Décider le comportement cible et ce qu'on accepte de casserLe portage de chaque appelant sur le module commun.

Pour une refonte, l'IA laissée seule préserve les deux comportements existants et produit un module plein de flags. Écrire noir sur blanc lequel des deux est le bon, et ce qu'on a la permission de casser, change tout.

4.3 Démo et produit

Valider un concept en direct avec du code généré sans contrainte est une bonne méthode : après une démo, on sait ce que la feature doit faire. Mais la démo vit sur une branche ou un repo à part, pour éviter la tentation du « ça marche déjà, on garde ». On récupère l'UI, les fonctions pures et surtout ce qu'on a appris ; on refait ce qui touche aux données, aux droits et aux sessions, avec la démo ouverte à côté comme référence. Pour le management : « la démo, deux jours ; la version vendable, quelques jours de plus ».

5. Commits, PR et review

5.1 Relire un diff

Après chaque génération, une lecture de conformité plutôt qu'une chasse aux bugs, avec quatre questions :

  1. Est-ce que ça sort du périmètre prévu ?
  2. Une dépendance a-t-elle été ajoutée ?
  3. De l'I/O dans une boucle, un N+1, une opération synchrone bloquante ?
  4. Quelque chose est-il lu ou écrit sans scoping tenant ?

Si un diff dépasse largement 400 lignes, le module était probablement trop gros.

5.2 Les commits racontent le design

Le reviewer lit la PR commit par commit. On vise donc :

  • un premier commit avec la note, la forme et les invariants (rouges) : il montre que la conception a précédé le code ;
  • puis un commit par module, avec ses variants, et son contrat en quelques lignes dans le message ;
  • pas de commits « wip » ou « retry » dans la PR ouverte.

Si le ticket a des subtasks, une par module tombe naturellement une fois la forme posée ; c'est aussi ce qui permet à deux développeurs de travailler en parallèle sans se marcher dessus.

Avec Conventional Commits, les commits de module sont des chore(TICKET) et le merge se fait en squash, en un seul feat(TICKET) sur la branche principale, dont le corps liste les modules :

feat(G2-0431): carrousel de filage avec historique

- lib/history — pur, sémantique navigateur, 50 entrées max
- components/carousel — générique, virtualisé, ne connaît pas le store
- features/viewport/ImageFilmstrip — colle, seul fichier qui connaît Gear
Note : docs/tickets/feat/G2-0431-filmstrip.md

5.3 Corriger un commit précédent

Cas fréquent : en branchant le front, on découvre qu'il manque un endpoint dans le commit back-end. Avant d'ouvrir la PR, on replie la correction dans le bon commit :

git commit --fixup <sha-du-commit-backend>
# ... on continue ...
git rebase -i --autosquash <base>     # base = main, master ou develop

Le rebase est ce qui replie les fixups ; sans lui, ils restent visibles dans la PR. Un alias aide à ne pas l'oublier : git config --global alias.fixups '!GIT_SEQUENCE_EDITOR=true git rebase -i --autosquash', puis git fixups <base>. Une fois la PR ouverte, on ne réécrit plus l'historique : on ajoute un commit normal, et le squash final nettoie tout.

5.4 La review

Idéalement, celui qui relit n'a pas conçu la feature : c'est la seule vérification indépendante d'une petite équipe. Un ordre qui fonctionne :

  1. La note : est-on d'accord avec les décisions ? Si non, inutile de lire le code.
  2. Les invariants : les points critiques de la note sont-ils couverts ?
  3. Le diff, commit par commit, avant tout résumé IA : les quatre questions, la duplication avec l'existant, les en-têtes encore justes. Le code de colle et ce qui touche aux droits se lit en entier ; un module générique se juge souvent à ses imports.
  4. À l'écran : tester le parcours à la main. L'œil voit en deux secondes ce qu'aucun test ne capture.
  5. Le tenant : est-ce que ça peut sortir des données hors du tenant ?

6. Exemple back-end : login utilisateur

Node.js, Express, MongoDB, sessions serveur, hashage avec node:crypto. Ici presque toutes les contraintes sont critiques et invisibles à l'écran : c'est le cas où les invariants pèsent le plus.

Ticket G2-0412
Ajouter un login par email + mot de passe. Après connexion, l'utilisateur a une session et accède à son espace.

6.1 La note

# G2-0412 — Login utilisateur

## Ce que ça fait
Email + mot de passe sur /login. Si valide : session (7 jours glissants)
et redirection vers l'espace. Sinon, un message d'erreur unique.
Après 10 échecs en 10 min par (IP, email) : 429.

## Ce que ça ne doit pas faire
- Stocker ou logger un mot de passe en clair.                 → invariant
- Distinguer « email inconnu » de « mot de passe faux ».      → invariant
- Créer une session dont le tenantId ne vient pas de la base. → invariant
- Ouvrir une session avec un mot de passe vide.               → invariant
- Émettre un cookie sans httpOnly / secure / sameSite.        → variant suffit
- Afficher un message d'erreur technique à l'écran.           → vu en review

## Où ça casse
scrypt coûte ~100 ms. Le rate limit protège aussi le pool de threads.

## Forme
services/auth/password.ts  hash / verify. Ne connaît ni Express ni Mongo.
services/auth/login.ts     login(email, plain) → user | null. Ne crée pas
                           la session. Même coût de temps si email inconnu.
routes/auth.ts             POST /login, POST /logout. Régénère la session.

## Pistes pour plus tard
- Reset par email.
- Verrouillage de compte : écarté (un attaquant pourrait bloquer un compte).

6.2 Les invariants

Sur une vraie base et un vrai Redis de test, écrits avant le code. Les deux premiers suffisent à illustrer la forme :

// services/auth/tests/invariants/login.test.ts
it("email inconnu et mauvais mot de passe : réponse identique", async () => {
  const bad = await post("/login", { email, password: "faux" });
  const unknown = await post("/login", { email: "x@nope.test", password: "faux" });
  expect(bad.status).toBe(unknown.status);        // égalité, pas « 401 »
  expect(bad.body).toEqual(unknown.body);
});

it("le mot de passe n'apparaît ni en base ni dans les logs", async () => {
  const logs = captureLogs();
  await post("/login", { email, password });
  expect(JSON.stringify(await findUserRaw(email))).not.toContain(password);
  expect(logs.join("\n")).not.toContain(password);
});

Les variants (400 si email manquant, 429 exact, attributs du cookie) seront générés avec les modules.

6.3 Génération et relecture

Lis AGENTS.md et docs/tickets/feat/G2-0412-login.md.
Implémente uniquement services/auth/login.ts selon la note.
password.ts existe déjà, ne le modifie pas.
- login() ne crée pas de session et n'importe rien d'Express.
- Email inconnu : vérifie quand même contre un hash factice (même temps de réponse).
- Aucune trace du mot de passe dans les logs.
Fais passer les invariants de services/auth/tests/invariants/.

En relisant, quelques points que l'IA rate souvent : le chemin « email inconnu » répond-il en 2 ms ? La clé de rate limit inclut-elle l'email (sinon le NAT d'un studio bloque tout le monde) ? session.regenerate() est-il appelé avant d'écrire l'utilisateur ? Le tenantId vient-il de la base et pas du corps de la requête ? Un console.log(req.body) traîne-t-il ?

6.4 Le morceau écrit à la main : password.ts

/** password — hash et vérification, scrypt natif.
 *  Ne connaît pas : Express, Mongo, les sessions. Utilisé par : login.ts. */
import { randomBytes, scrypt as _scrypt, timingSafeEqual } from "node:crypto";
import { promisify } from "node:util";
const scrypt = promisify(_scrypt);
const P = { N: 2 ** 15, r: 8, p: 1 };

// Paramètres stockés dans la chaîne : on pourra les augmenter sans casser l'existant.
export async function hash(plain: string) {
  const salt = randomBytes(16);
  const key = (await scrypt(plain, salt, 64, P)) as Buffer;
  return `scrypt$${P.N}$${P.r}$${P.p}$${salt.toString("base64")}$${key.toString("base64")}`;
}

export async function verify(stored: string, plain: string) {
  if (!plain) return false;
  const [algo, N, r, p, s, k] = stored.split("$");
  if (algo !== "scrypt") return false;
  const expected = Buffer.from(k, "base64");
  const actual = (await scrypt(plain, Buffer.from(s, "base64"), expected.length,
    { N: +N, r: +r, p: +p })) as Buffer;
  return timingSafeEqual(actual, expected);       // jamais === sur un secret
}

Ce qu'on apprend en l'écrivant plutôt qu'en le lisant : pourquoi les paramètres sont dans la chaîne, pourquoi timingSafeEqual, pourquoi un hash factice pour les emails inconnus.

7. Exemple front-end : carrousel de filage

React + TypeScript, un store d'images existant, un Viewport qui affiche l'image courante. Ici, l'inverse du login : presque tout se voit à l'écran, donc presque rien ne mérite un invariant. L'effort va dans la forme, parce qu'on veut un carrousel réutilisable.

Ticket G2-0431
Un carrousel de vignettes sous le viewport (clic et clavier), avec un historique des images consultées. Réutilisable dans la vue batch.

7.1 La note

# G2-0431 — Carrousel de filage + historique

## Ce que ça fait
Bande de vignettes (96 px, lazy) sous le viewport. Clic ou ← → pour changer
d'image. Boutons « précédente / suivante consultée », comme un navigateur.
Historique en mémoire, 50 entrées, perdu au rechargement.

## Ce que ça ne doit pas faire
- Monter toutes les vignettes dans le DOM (projets de 5 000+ images).
                                         → vérifié en review sur un gros projet
- Appliquer des règles de droits : la liste arrive filtrée du store.
                                         → structure, review
- Mettre de la logique Gear dans le carrousel générique.
                                         → structure, lint sur les imports

## Forme
lib/history/history.ts        pur : push / back / forward / current
components/carousel/          générique : items { id }, selectedId, onSelect,
                              renderItem. Ne connaît ni le store ni Gear.
features/viewport/ImageFilmstrip.tsx
                              la colle, seul fichier qui connaît Gear

## Pistes pour plus tard
- Persister l'historique si les utilisateurs le demandent.

Aucune ligne n'est un invariant : rien n'est critique pour la sécurité ou les données, et tout se voit en cliquant. La sémantique de l'historique, logée dans une fonction pure, se couvre par quelques tests ordinaires, écrits en cinq minutes.

7.2 La forme, l'étape clé

Le test d'un module générique
Pourrait-on monter Carousel dans la vue batch sans le modifier ? Si on l'avait laissé émerger d'un « fais-moi un carrousel pour le viewport », il connaîtrait le store, et on le découvrirait au moment de le réutiliser.
Implémente uniquement components/carousel/ selon la note.
- Aucun import depuis features/ ou store/ ; il ne connaît que { id }.
- Virtualisation horizontale : seuls les items visibles sont dans le DOM.
- scrollIntoView uniquement quand selectedId change.
- Accessible : listbox / option, navigation clavier.

7.3 Relire et tester à l'écran

  • Les imports de Carousel d'abord : un seul import du store et il n'est plus générique.
  • La liste est-elle vraiment virtualisée ? Ouvrir un projet de 3 000 images, compter les <img> dans l'inspecteur.
  • Un useEffect dépend-il d'un objet recréé à chaque render ? Le scroll sauterait en boucle. Pas besoin de savoir l'écrire de tête ; il faut savoir le repérer dans un diff.
  • Cliquer, flèches, précédente, suivante. Deux minutes.

7.4 Le morceau écrit à la main : l'historique

export type History = { entries: string[]; index: number; max: number };
export const empty = (max = 50): History => ({ entries: [], index: -1, max });

export function push(h: History, id: string): History {
  if (h.entries[h.index] === id) return h;                 // pas de doublon consécutif
  const entries = [...h.entries.slice(0, h.index + 1), id].slice(-h.max);
  return { ...h, entries, index: entries.length - 1 };     // écrase le « suivant »
}
export const back = (h: History) => h.index > 0 ? { ...h, index: h.index - 1 } : h;
export const forward = (h: History) =>
  h.index < h.entries.length - 1 ? { ...h, index: h.index + 1 } : h;

Ce qu'on apprend en l'écrivant : un historique n'est pas une pile, et renvoyer la même référence sur un no-op évite un re-render.

8. Entretenir son jugement

Ce qui s'atrophie avec l'IA, ce n'est pas la capacité à corriger, c'est la capacité à remarquer qu'il y a quelque chose à corriger (le rapport compagnon détaille ce que dit la recherche). Quelques habitudes qui aident :

  • Un morceau à la main par feature, là où l'on est le plus ignorant.
  • Un quart d'heure sans IA quand quelque chose casse, avant d'ouvrir l'assistant.
  • Lire le diff avant le résumé.
  • Mesurer plutôt que se souvenir : un banc de test donne en une après-midi ce que la production apprenait en six mois.
  • Demander des options, pas une solution : « trois approches et à quel volume chacune casse » construit un modèle mental ; « corrige les perfs » n'en construit aucun.

Et quelques fausses bonnes idées : apprendre un langage « pour s'entraîner » sans besoin réel, dicter le code ligne à ligne à l'IA (lent, et ça n'apprend rien), ou se réfugier dans l'architecture pour ne plus toucher au système.

A.3 Avant d'ouvrir une PR

  • La note est à jour et reflète ce qui a été livré.

  • Chaque diff a été relu avec les quatre questions.
  • Un commit par module, fixups repliés.
  • AGENTS.md mis à jour si une convention a changé.

A.4 Squelette d'AGENTS.md

# AGENTS.md
## Commandes
- Tests : npm test · invariants : npm run test:invariants · Lint : npm run lint

## Règles d'architecture
- Toute requête Mongo passe par un repository scopé tenant (src/repositories/).
- Toute vérification de secret passe par services/auth/password.ts.
- components/ n'importe jamais depuis features/ ni store/.
- Le front n'est jamais seul à empêcher une action.

## Ne pas modifier sans demander
- **/tests/invariants/**   (protégés : si un invariant échoue, corriger le code)
- src/middleware/session.ts, infra/**

## PR
- Un commit par module : fonctions pures → orchestration → routes → front.
- Lien vers la note dans docs/tickets/<type>/.
